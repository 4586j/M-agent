## 1. 目标与总体判断

### 1.1 用户希望完成的协作闭环

1. 人进入一个项目，提出需求。
2. 人与 AI 对话澄清，AI 起草需求文档，保存对话和版本。
3. 人审核确认某一个确定版本，而不是笼统确认整段对话。
4. 项目大脑依据已确认文档拆解任务，按项目成员的职责分配给对应人的 Agent。
5. 每个 Agent 同时收到子任务说明、完整原始需求的冻结副本、相关参考文档和验收标准。
6. Agent 执行，有疑问通过大脑发起澄清；执行完成由负责人确认后回传大脑。
7. 大脑汇总、验证依赖和集成结果，向需求提出人交付。
8. 需求提出人最终验收或退回；验收后才算需求完成。

同一个人的同一个逻辑 Agent 可以参与不同项目，但每个项目内的职责、权限、人设、记忆、会话、工作目录、凭证和产物必须隔离。

### 1.2 推荐方案

**新增独立的协作业务层，复用现有 Agent 内核，不把旧的单任务系统直接改成多人系统。**

- 旧 CLI、单 Agent 面板、编排面板、brain/worker 接口和数据继续按原方式运行。
- 协作层负责身份、项目、需求版本、业务审批、持久任务依赖图、负责人收件箱和交付验收。
- 初期使用独立服务进程、独立数据目录和独立认证入口，不能把原有全局 API 直接暴露给团队成员。
- Worker 新增协作运行入口，运行同一套 `AgentKernel`；不复用旧 Worker 的共享密钥、全局面板状态和共享缓存。
- 第一阶段采用“一份项目身份绑定对应一个隔离执行实例”；产品上仍展示为同一个 Agent 在不同项目的身份，不要求同一进程热切换所有身份。
- 需求审核通过后正常自动拆解、派发，不新增所有任务都必须由管理员二次审批的障碍；仅对歧义、越权、超预算、身份不匹配等异常挂起。

代价是增加服务和执行实例的管理成本，但能显著缩小对旧能力的改动范围；后续只有在隔离测试充分后，才评估单进程承载多个项目身份。

### 1.3 本期范围与非目标

**本期必须闭环**：实名身份、项目成员、身份绑定、AI 澄清与版本化原文、需求确认、服务端任务拆解、依赖执行、完整原文传递、执行者确认、大脑集成审核、提出人验收、撤销/失败/离线/恢复、审计和回归测试。

**本期不做**：企业 SSO、跨组织公开市场、跨项目自动共享知识、通用流程设计器、多大脑主节点高可用、自动上线生产、任意个人电脑远程终端管理、智能自动解决所有代码合并冲突。

AI 减少重复沟通，但不能替人决定相互矛盾的业务诉求。歧义必须转为可追踪的澄清事项，不能靠模型猜测后继续执行。

## 3. 兼容红线：先保护旧能力

### 3.1 对现有用户的承诺

1. 不启用协作服务时，原有启动方式、配置默认值、请求形状、CLI 命令和面板行为不变。
2. 不要求旧用户注册团队账号、创建项目或迁移历史任务才能继续使用。
3. 不改旧 `TaskRecord` 的状态语义，不在其状态枚举中塞入业务审批状态。
4. 不移动、改写或自动导入现有任务、会话、记忆、知识、经验、预算和 Provider 数据。
5. 协作服务不能失败后回落到旧全局 store、旧 persona、旧 Provider 或任意可用 Worker。
6. 协作执行继续具备安全检查、工具策略、输出校验、超时、取消、预算和可观测性；新入口不能成为绕过旧守卫的捷径。
7. 不将旧管理密钥下发给团队成员，不以“兼容”名义让旧管理接口读写协作数据。
8. 任何共享内核修改必须独立成小批次，并证明旧路径行为不变；不顺带清理无关代码。

这里的“保证不受影响”是必须通过的工程验收条件，不是仅凭设计能够作出的绝对保证。本次文档变更不改变运行代码；后续实现必须逐阶段拿到测试证据。

## 4. 目标架构与部署边界（提议）

### 4.1 三个相互分离的职责层

| 层次 | 职责 | 不承担的职责 |
| --- | --- | --- |
| 协作交互层 | 项目切换、需求对话、版本对比、成员身份、待办、审核、交付 | 不在前端决定权限，不保管 Worker 管理密钥 |
| 协作大脑服务 | 用户授权、需求/计划状态机、LLM 规划、确定性调度、交付聚合、审计、通知 | 不把模型输出直接当授权，不在会话上下文中保存唯一调度状态 |
| 项目执行实例 | 接收指定绑定的任务、校验任务包、运行现有内核、记录执行事实并回报 | 不自行转派他人，不调用旧全局记忆工具，不越项目执行 |

旧 brain/worker 服务继续提供旧功能。协作大脑最初以独立应用工厂和进程部署，不在旧 `create_brain_app()` 中默认挂载带新依赖的路由；协作实例也不挂载旧 `/agent/terminal`、全局 workspace 和共享密钥入口。

界面可在旧管理面板增加“团队协作”入口，但进入的是独立认证的协作界面；普通成员不因能使用协作界面而获得旧面板管理权。初期建议管理与协作使用独立 Web origin 和会话存储，避免把旧 localStorage 管理密钥暴露在团队页面运行环境中。

### 4.2 复用边界

- 复用 `AgentKernel` 的执行、超时、取消、用量、输出守卫及 persona 解析等已验证能力。
- 复用安全检查、上下文构造、HTTP 传输等明确可隔离的部件；复用前用测试证明没有隐式读取旧全局目录。
- 不把协作请求转换为调用旧 `/dispatch`：旧入口缺少项目授权、身份绑定、版本快照和幂等协议。
- 新协作调度适配器负责协议和状态，不复制一份 SDK/LLM 执行内核。
- 如需提取共有的安全派发逻辑，先在独立批次提取并验证旧行为，再由新层调用；不大幅重写旧派发器。
- 旧 AI 顾问和 `planning.py` 可提供提示模板、输出校验思路；团队规划结果必须经过新的业务校验器。

### 4.3 数据落地选择

新增协作元数据推荐使用 SQLite 的事务、外键、唯一约束和版本号；部署假设为单个协作大脑写入、本机磁盘，不把数据库放在共享网络目录上，不承诺初期多主 HA。

- 新元数据包括成员、需求、版本、计划、任务、执行尝试、审批、通知、审计和 outbox。
- 原文和产物存放在协作服务独立文件目录，元数据保存摘要、长度、项目和版本关联。
- 项目知识/经验/记忆可先复用现有 store 实现，但必须按项目构造独立实例和目录，并经过统一授权入口访问。
- 协作数据库与旧 JSON store 不双写同一条任务，不让两套系统共同拥有一个任务状态。
- 文档入库按“先写临时文件并校验、原子落盘、再提交数据库引用”处理；未引用文件可回收，不能提交指向半写文件的可用版本。
- 存储迁移有 schema_version 和兼容检查；旧二进制不允许盲写更新版本的数据库。

## 5. 身份模型：人、权限、Agent 人设、机器分开

### 5.1 必须区分的实体

| 实体 | 核心字段（提议） | 约束 |
| --- | --- | --- |
| User | user_id、display_name、status | 由认证系统识别，不取信前端自报的 user_id |
| Project | project_id、name、owner_id、status | 是协作数据边界；不是本机目录字符串 |
| ProjectMember | project_id、user_id、access_role、status | `(project_id,user_id)` 唯一；负责访问权限 |
| Agent | agent_id、owner_user_id、name、status | 人持有的逻辑 Agent；不等于进程或 IP |
| AgentProjectBinding | binding_id、project_id、agent_id、member_user_id、duty、persona_version、allowed_tools、workspace_ref、provider_ref、version | 初期一个 Agent 在同一项目只有一个有效绑定；变更版本化 |
| ExecutionInstance | instance_id、binding_id、node_id、protocol_version、capacity、heartbeat、status | 一份绑定可以有多个授权实例，但不能跨绑定轮询 |
| Requirement | requirement_id、project_id、requester_id、reviewer_id、status、approved_revision_id、active_plan_id、version | 业务需求不是执行任务 |
| RequirementRevision | revision_id、requirement_id、number、content_hash、document_ref、author_id、created_at | 文档快照不可变；已确认版本不能原地修改 |
| Plan / WorkItem | plan_id、revision_id、version；work_item_id、binding_id、assignee_user_id、dependencies、acceptance_ids、status | 都携带 project_id；依赖仅能指向同项目同一执行计划的工作项 |
| ExecutionAttempt | attempt_id、work_item_id、instance_id、lease_epoch、input_hash、status、execution_task_id、result_hash、usage | 区分业务任务、执行尝试与旧任务 ID；有效执行权不能重复 |
| Review / Delivery | review_id、target_type、target_id、target_version、reviewer_id、decision；delivery_id、manifest_hash、status | 审核必须绑定版本和内容摘要，不只保存一个布尔值 |
| Clarification / Notification / Audit | 来源对象、接收人、project_id、状态、时间、事件 ID | 通知和审计必须可追溯、可重放且不越权 |

所有对象 ID 由服务端生成。关系表使用组合外键或等效事务校验防止跨 project_id 引用；不能只依赖 ID 足够随机。

默认必须满足 `Agent.owner_user_id = AgentProjectBinding.member_user_id = WorkItem.assignee_user_id`，同时校验绑定、成员和任务属于同一项目。创建绑定、发布计划、派发、转派及恢复执行时都检验此约束，不能仅分别检查三个对象存在。初期不开放代管他人 Agent；将来代管需独立的限范围、限期、可撤销授权，不能靠修改 owner 字段实现。

### 5.2 同一个 Agent 的两个项目身份示例

- 用户甲拥有逻辑 Agent `agent-jia`。
- 在项目 A：项目权限为 member，职责为前端，人设版本为 frontend-v3，绑定 A 的仓库与凭证。
- 在项目 B：项目权限为 reviewer，职责为测试，人设版本为 tester-v2，绑定 B 的仓库与凭证。
- 两个项目对应两个绑定、两个执行上下文和独立目录；切换项目只是改变所选绑定，不修改进程级全局 persona。
- A 项目的前端身份不会因为 B 项目拥有 reviewer 权限而获得 A 项目的审核权。

`access_role` 决定能做什么业务操作；`duty/persona` 决定擅长什么任务；`allowed_tools` 决定执行工具范围。三者不互相推导。

### 5.3 权限默认值

- 项目 owner/manager 管理成员、职责映射和受控转派；平台运维不默认拥有所有项目文档读取权，紧急访问需显式授权并审计。
- 项目成员可以提交需求；只可修改自己有编辑权的草稿，不能改变其他人的已审核原文。
- 草稿对话默认仅提出人及指定审核人可见；确认并派发后的需求原文在项目成员范围内可见，初期不提供同项目逐段密级控制。
- reviewer 执行指定的需求审核或交付审核；默认需求提出人可以审核自己的需求，不强制四眼审批。
- 执行负责人确认自己的 Agent 产出；项目 manager 可以受控转派，但不能伪造负责人确认记录。
- 需求提出人或预先授权的代理人执行最终验收；AI 不能代表人签字。
- Agent 凭证仅可领取/读取被分配的任务包、授权上下文及上报结果，不可修改成员或自行授予权限。

## 6. 需求、任务与交付状态机（提议）

### 6.1 需求状态

| 状态 | 进入条件 | 允许的后续行为 |
| --- | --- | --- |
| draft | 提出需求，AI 澄清、生成草稿 | 编辑、保存版本、请求审核、撤销 |
| in_review | 指定审核人收到确定版本 | 确认进入 approved；退回 draft；不能修改正在审核的版本 |
| approved | 审核动作绑定 revision_id 和 hash | 写入规划 outbox，进入 planning |
| planning | 大脑生成候选计划并校验 | 合格进入 executing；不合格进入 planning_blocked |
| planning_blocked | 缺成员、歧义、循环依赖、超预算或计划越界 | 澄清/修改计划后重检；改变需求内容必须重新审核版本 |
| executing | 至少存在有效计划，按依赖执行 | 继续调度、暂停、撤销；全部子任务合格后进入 integrating |
| integrating | 大脑核对需求覆盖与集成交付 | 通过进入 awaiting_acceptance；失败进入 rework |
| awaiting_acceptance | 完整交付包已持久化 | 提出人验收进入 completed，或拒绝进入 rework |
| rework | 指明未满足的验收项 | 在当前批准范围内追加有版本的返工计划；范围变化需新需求版本 |
| paused | 人工暂停或持续阻塞 | 恢复到记录的前态；不得丢失原阻塞原因 |
| cancelling / cancelled | 撤销请求已记录 / 无可继续派发的执行权 | 尽力停止在途任务，保留副作用与迟到结果，不自动恢复 |
| completed | 提出人接受当前交付版本 | 只读归档；后续新诉求创建新版本或新需求 |

失败子任务不直接把整个需求永久置为失败，也不自动算作完成；展示失败原因、受影响下游和待负责人处置项。未取得执行停止确认的尝试保持不确定记录，不能因 UI 显示 cancelled 就宣称外部操作已撤回。

### 6.2 工作项状态

`pending_dependency → ready → waiting_agent → running → awaiting_owner_review → submitted → accepted`

- 依赖未验收、负责人待确认或节点离线时不派发。
- 合法在线实例就绪时可从 ready 直接到 running；waiting_agent 表示可执行但暂无可用实例。
- running 完成的是机器执行，不是业务成功；通过产物守卫后进入 awaiting_owner_review。
- 负责人退回进入 changes_requested，随后以新 attempt 重做；旧结果不可覆盖。
- submitted 由大脑按验收条件判定 accepted 或进入 changes_requested；安全裁决 block 必须独立处理，不能被大脑业务验收覆盖。
- 下游只消费 accepted 工作项的固定产物版本，不消费尚未确认的临时文件。
- `blocked`、`failed`、`cancelled` 是显式分支；失败重试需要保留尝试链、失败分类与预算。
- 安全待审批是独立 gate 记录，可阻止工作项前进，不借用旧 TaskRecord 的业务含义。

### 6.3 审核与并发规则

- 需求审核、任务产出确认、最终验收、安全放行是四种不同操作，各自拥有权限和审计记录。
- 所有可变对象带 version；修改和审批必须提交 expected_version，冲突返回 409。
- 两次并发确认只能成功一次；同一幂等请求重复提交返回原结果，不再派发任务。
- 需求原文发生改变后创建新 revision；原审批仍指向旧版，不自动认可新版。
- 新版审批通过前不改变执行中的旧版；批准切换后先暂停未开始的旧任务，评估在途影响，再发布新计划。
- 旧版结果可作为历史证据；若要复用于新版，必须显式关联并重新验证相关验收项，不能静默计入新版完成度。

### 6.4 协作安全放行契约

协作服务维护独立 SecurityGate/Review 记录，不调用旧 `/tasks/{id}/approve` 或把需求确认映射成 force。放行需要项目范围的 `security:approve` 权限，默认仅项目 owner 持有并可显式授权指定人工审核人；普通 manager、需求提出人、执行负责人和 AI 不因其身份自动获得此权限。

每次安全裁决绑定 project_id、attempt_id、input_hash、requirement_revision_id、binding_version、tool_policy_version、命中规则和有效期。人工放行或拒绝须记录审核人、理由、原裁决与 expected_version；重复提交幂等，过期或已处理裁决返回冲突。输入、文档、绑定、工具策略变化或开启新 attempt 后，原放行失效，必须重新检查。

只有被策略明确标记为可人工裁决的安全规则可放行；项目授权、身份一致性、原文摘要校验、沙箱边界和预算限制不可被放行覆盖。放行只消除对应规则的阻塞，不扩大工具集，不关闭后续执行守卫；人工拒绝后只能修订输入并重新检查，不能直接重派绕过。

## 7. 需求文档与任务包契约

### 7.1 AI 澄清与需求文档

需求对话是独立的“起草模式”：只开放项目内资料读取、草稿写入和澄清工具，不允许调用业务执行、任意 shell、部署或安全放行接口。此模式是固定权限边界，而非仅在提示词中要求“不要执行”。

确认前至少具备：目标、背景、范围、明确不做的事、可验证验收项、约束、依赖、资料清单、期望交付、预算/截止时间，以及未解决问题。预算或时间未知须明确记录，不能让 AI 默填承诺。

每个验收项有稳定 ID，例如 AC-001；计划中的任务必须引用对应验收项。AI 的历史对话摘要不能替代最终需求快照。

### 7.2 完整原文交付

每次派发包含以下对象：

| 字段组 | 必需内容 |
| --- | --- |
| 标识 | schema_version、project_id、requirement_id、revision_id、plan_id、work_item_id、attempt_id |
| 身份 | assignee_user_id、binding_id、binding_version、instance_id、control_epoch、lease_epoch |
| 原文 | 原始上传文件（如有）、审核后的完整需求文档、各自 hash/size/type，以及文档之间的来源关系 |
| 子任务 | objective、scope、non_goals、acceptance_ids、输入与期望输出清单 |
| 依赖 | 依赖工作项及已接受产物的固定版本和 hash |
| 执行策略 | 工具白名单、受控 workspace_ref、预算、超时、取消与回报凭证范围 |

Worker 先下载/接收文件，校验项目、版本、长度和摘要，再确认任务包接收成功；文件缺失或 hash 不符不得执行。完整原文放进任务只读输入区，Agent 通过受限读取工具分段查看；prompt 只放任务目标、强制约束、验收项和文件索引。

- 原文必须完整可读，不因 context 限幅或检索遗漏被截断。
- 大文档采用分段读取并返回覆盖范围；可记录读取回执，但“已读文件”不等于模型真正理解全部内容。
- RAG 仅用于定位相关参考资料，不能取代批准版本的权威原文。
- 不向其他成员默认传递提出人的私人澄清对话、个人记忆或未批准草稿。
- 缺关键输入、超出允许文件大小时给出明确阻塞信息；不能静默换成摘要后执行。
- 文档中的命令、网页内容、任务输出均作为不可信资料，不具有修改权限、转派或取消安全检查的效力。

### 7.3 执行与交付回报

机器结果需包含：attempt_id、control_epoch、lease_epoch、input_hash、执行状态、摘要、验收项证据、产物 manifest、变更清单、测试命令及真实结果、未解决问题、用量、trace_id。

负责人确认需绑定 result_hash。最终交付包包含：需求原文版本、任务完成矩阵、固定产物版本、集成测试证据、安全状态、成本摘要、已知限制和完整审核链。

禁止只用“已完成”文字或所有 Worker 都返回 done 作为最终验收依据。

## 8. 服务端规划、可靠调度与异常处理

### 8.1 模型规划与确定性执行分离

LLM 只生成候选计划，不拥有创建用户、提升权限、绕过守卫或直接发送任意节点请求的权力。服务端验证通过后，才将计划、工作项和调度事件在同一数据库事务中提交。

校验至少包括：

1. 图无环、依赖存在、所有工作项属于同一项目和原文版本。
2. 所有必需验收项有工作项覆盖，无超出批准范围的额外目标。
3. assignee 为有效项目成员，binding 有效且职责匹配；不能按任意全局 role 选人。
4. 工具、Provider、工作区、资料可见性和成本上限均在授权范围内。
5. 前后端等跨角色任务使用同一版契约；不可凭个人 Agent 自行变更公共接口。
6. 模型输出缺字段、解释不清或出现不存在的成员时，有限次修正后挂起，不能无限重规划。

已有 `PlanStep` 的本地依赖模型可参考，但新的工作项是持久业务对象。LLM 无需常驻占用会话；后台调度服务常驻，按需调用 LLM 生成或修订计划。

### 8.2 幂等、租约与回调

- “批准需求 + 写入规划事件”“接受任务结果 + 推进依赖 + 写入通知”各自在同一数据库事务中完成。
- Outbox 在事务提交后发送，失败可重试；网络层只承诺至少一次投递，不承诺外部副作用恰好一次。
- 派发使用固定 attempt_id/input_hash。Worker 必须持久记录接收与执行状态：相同 attempt_id、相同输入返回已有状态；相同 ID、不同输入返回 409。
- Worker 开工前先持久占位；两个并发投递只能启动一个执行者。内存字典去重不满足重启要求。
- 大脑为每个执行尝试维护租约和单调递增的 lease_epoch；过期或被撤销的执行权不能推进业务状态。
- 回调必须匹配 project、binding、attempt、instance、lease_epoch 和输入摘要；重复回调幂等，伪造或不匹配回调拒绝。
- 回调中的 metadata 不能覆盖服务端确定的 project、assignee、persona 版本和权限字段。
- 旧 attempt 的迟到结果可归档为证据，但不覆盖当前尝试或 completed/cancelled 状态。
- 大脑重启从数据库与 outbox 恢复；Worker 重启从本地执行日志恢复查询能力。禁止用“进程重启所以重新执行全部任务”恢复。

### 8.3 离线、失败与重派

| 情形 | 默认处理 |
| --- | --- |
| 派发前节点离线或熔断 | waiting_agent，保留负责人；重连再发送，不改派别人的 Agent |
| POST 超时，不知是否收到 | 查询同一 attempt_id；必要时重投同一个幂等请求，不创建新尝试 |
| 执行失败且确定未产生副作用 | 按明确的失败分类、次数与预算决定新 attempt；默认最多一次自动执行重试 |
| 执行状态不明 / 网络分区 | 标记 reconciliation_required；核验旧执行是否停止，不自动换节点执行 |
| 必须换人 | manager 发起受控转派，记录原因，新负责人确认；旧授权撤销，重新校验输入 |
| 某个上游失败 | 仅阻断依赖它的下游；独立分支按预算继续，需求整体不提前 completed |
| 负责人长时间不审核 | 站内提醒、超时升级到项目 manager，不让 AI 代签 |
| 大脑规划失败 | 保留已确认文档，进入 planning_blocked，可人工修订计划后重新校验 |
| 用户撤销 / 成员权限撤销 | 停止新派发，撤销租约/访问权，尽力取消在途执行；记录不能撤回的副作用 |

租约只能防止旧结果写入新状态，不能撤销已发出的外部写操作。涉及支付、发信、生产发布等非幂等副作用的任务，本期默认不自动执行；需要后续专门的操作审批与补偿设计。

### 8.4 成本、容量与资源竞争

- 协作服务必须有自身全局、项目、需求、尝试的预算约束；规划、修订、评审等 LLM 调用也计入预算。
- 并发派发需要原子预算预留，完成后按 attempt 唯一键结算；重复回调不重复记账，结果未知时不提前释放全部预留。
- SDK 的任务预算继续生效，但费用上报延迟意味着不能承诺精确到分的瞬时硬上限；保留安全余量并显示未结算成本。
- 旧 `budgets.json` 仍只统计旧服务口径，不让两个进程直接共同写这个 JSON 文件。
- 若旧服务与协作服务共用付费账号，管理员必须明确分配两边额度或采用提供方硬额度；缺少额度分配不能宣称覆盖了整个账号的预算总闸。
- 对执行实例设置并发、队列长度、任务大小限制。同机共存必须测 CPU/内存/磁盘和旧任务延迟；进程隔离不自动消除资源争抢。

## 9. 项目隔离与安全边界

### 9.1 应用级隔离清单

| 对象/入口 | 必须做到 |
| --- | --- |
| 需求/任务/版本/产物 | 列表、详情、修改、下载都先验证项目成员与资源归属；跨项目 ID 不能借用 |
| 对话/持久会话 | 私人草稿会话与项目执行会话分离；SDK resume ID 按绑定和执行会话隔离 |
| 核心记忆/经验/知识 | 按项目独立 store；检索、自动注入、自动写回、反思、归档和删除都限定项目 |
| 程序记忆/技能/persona | 系统模板只读；项目修订写项目副本并版本化，不覆盖共享 `.claude/agents` 或全局技能 |
| SDK/MCP | 只挂项目批准的工具，工具调用服务端注入 project 上下文；不接受模型自报其他 project_id |
| Provider/环境变量 | 绑定指定凭证与允许的故障切换池；不继承个人 `.env`、全局 MCP、其他项目 Provider |
| workspace / 文件 | 服务端解析 workspace_ref，限制 realpath、符号链接和解压路径；不接受任意绝对目录作为授权 |
| 注册/心跳/状态 | node 凭证证明节点身份，owner 与 binding 来自已批准的登记关系，不信任注册体自报归属 |
| 终端/代理/trace/SSE | 不能作为跳过项目授权的入口；返回和订阅仅限当前有权资源，撤权后终止后续访问 |
| 通知/webhook/日志 | 默认只发最少摘要；原文通过授权读取；订阅方只能收到已授权项目的事件 |
| 缓存/索引 | key 至少包含 project_id、binding/persona_version、必要的文档版本；禁止跨项目复用上下文缓存 |
| 旧 API / CLI / MCP | 仅能操作旧存储；协作资源不挂到无项目维度的旧入口，不能用旧 token 调协作 API |

不采用“查出全库再在前端过滤”。授权上下文由登录身份和项目成员关系计算，后台任务也必须显式携带该上下文；缺失上下文应失败，而不是回落到默认项目。

### 9.2 认证与授权建议

- 初期使用管理员邀请的用户账号；口令采用成熟的自适应哈希，不自行设计密码算法。
- Web 使用安全会话 Cookie（HttpOnly，生产 HTTPS 下 Secure，合适的 SameSite），状态变更具备 CSRF 防护；不把长期 token 放 URL 或团队页面 localStorage。
- CLI/自动化后续使用可撤销、有限期、最小权限的个人令牌；摘要保存，不保存明文令牌。
- Worker 使用单独的节点凭证；每次执行另有绑定 project/attempt/资源/有效期的最小权限授权，不下发平台管理员凭证。
- HTTPS 或受控加密网络保护跨主机传输；Cookie/token 日志脱敏。
- 未认证返回 401，已认证但操作权限不足返回 403；不可见资源按统一策略返回 404，避免泄露存在性。
- 文档附件下载、SSE 建连/续连、运行中的工具请求都要重新检验授权，不能只在页面打开时校验一次。

### 9.3 操作系统级隔离的真实限制

**换目录、改 persona 或传入 project_id 都不是沙箱。** 同一 OS 账号下的两个进程，若都能读取对方目录或使用同一 MCP 凭证，仍可能跨项目泄露。

团队执行实例在承载真实数据前必须提供并验证隔离策略：独立 OS 账号/ACL、容器或 VM，项目专属工作目录和用户 HOME、环境变量白名单、受控工具与网络凭证。Windows 和 Linux 分别验证，不能把 Linux 容器结论当作 Windows 保证。

初期不做完整容器编排平台，可以由部署人员准备隔离实例并登记；但没有通过隔离验证的节点只能用于无敏感数据的测试，不能宣称满足用户要求的项目安全隔离。共享物理主机不等于共享文件权限。

## 10. 代码与产物协作

- 每项任务从固定代码基线执行；记录 repository_ref、base_commit、分支或 worktree/独立 checkout、产物摘要。
- 同一个仓库的并行任务不能直接写同一个工作目录。Git worktree 解决工作区冲突，不解决安全隔离；跨项目仍需独立权限边界。
- 前后端先生成并确认共享契约版本，再按依赖推进；契约变更进入变更记录并通知受影响工作项。
- 执行者提交 patch/commit/文件产物，不默认推送远端、修改主分支或发布生产。
- 大脑只调度集成、汇总证据和作出验收判断，不在控制面检出或运行项目代码。普通业务工作项全部 accepted 后进入 integrating，创建依赖于这些固定产物的集成工作项，由同项目授权绑定的隔离 Worker 在独立目录完成合并与测试；集成项不依赖自身，验收通过后才进入 awaiting_acceptance。
- 集成 Worker 使用项目级最小权限，不持有大脑数据库、其他项目目录或控制面凭证。冲突由集成工作项处理，不能“任务都 done 所以直接完成”。
- Worker 本地路径不是可长期交付的文件地址。提交阶段必须把产物复制到协作服务的持久存储，校验 hash 后才允许 submitted。
- 产物预览默认不执行主动内容；HTML/SVG 等使用隔离预览或下载，文本按文本展示，避免把 Agent 输出变成浏览器脚本。
- 文件类型、大小、路径、压缩包解包和凭证泄露检查在系统边界执行；敏感文件不得自动加入交付。

### 11.2 机器协议

在独立协作 Worker 入口提供版本化的任务提交、查询、取消和状态对账协议。请求使用第 7.2 节任务包；响应区分 accepted、duplicate、running、finished、rejected 以及明确错误原因。

- 初期仍使用 brain push，不强制把旧集群改为 pull。
- 大脑维护等待队列，节点上线再投递；个人电脑必须通过团队授权的网络通道可达。
- 节点地址由登记关系解析，不接受任意用户请求携带 callback URL、下载 URL 或目标主机。
- Worker 回报路径与任务授权绑定；callback、轮询对账具有相同幂等与权限校验。
- 旧 Worker 不支持新协议时显示“需部署协作实例”，拒绝派发；不能静默丢弃项目字段后降级调用旧 `/task`。

### 11.3 必须新增的交互

1. 项目选择器：清晰显示当前项目、人的权限和 Agent 的项目职责。
2. 需求工作台：对话、完整原文、版本对比、验收项、确认按钮；审批前显示正在确认的版本。
3. 任务图/列表：负责人、依赖、阻塞、当前尝试、原文入口、成本及进度。
4. 我的收件箱：待澄清、待需求审核、待产出确认、待最终验收、离线/超时提醒。
5. Agent 身份页：同一个 Agent 在各项目的不同绑定与在线状态，不能一个全局开关覆盖所有项目。
6. 交付页：验收项到证据的映射、产物、集成测试、遗留问题及最终验收动作。

切换项目必须取消旧请求和订阅、清空受限缓存，防止前一个项目迟到响应显示在新项目页面。URL 中的 project_id 只是导航，不是授权。

## 13. 分阶段实施与停止条件

| 阶段 | 实施内容 | 保护/解锁的业务路径 | 必须获得的验证信号 |
| --- | --- | --- | --- |
| P0：基线与契约 | 记录 Git 基线，执行原有测试，确定样例旧数据和启动方式；核验 CI 触发 | 保护全部现有单人/多机能力 | 保存平台、命令、通过/失败/跳过和失败原因；旧数据可正常加载；未解决的相关基线失败不得当作通过 |
| P1：身份与隔离基础 | 独立服务、账号/项目/绑定、最小授权、独立存储和隔离实例验证 | 同一人/Agent 在两个项目有不同身份，互不越权 | A/B 项目接口与文件/MCP泄露测试通过；旧 token 无法访问新数据；旧启动链不依赖新服务 |
| P2：需求确认 | 只读澄清 AI、版本化原文、审核和待办 | 人提需求到确认一个完整版本，尚不自动执行业务任务 | 审核前无执行；并发审批不重复；原文与摘要一致性；新版本需重新审核 |
| P3：可持久化计划 | 结构化规划、校验、DAG、outbox、模拟执行端 | 自动拆解并匹配项目负责人，可恢复等待状态 | 覆盖缺人/循环/越权/超预算及 owner/绑定/负责人错配；重启恢复不产生重复任务；原文版本不漂移 |
| P4：协作执行闭环 | Worker 新协议、持久去重、租约、原文下载、负责人确认、产物入库 | 对应人的 Agent 执行并回传，离线可等待 | 真进程/真 HTTP + Fake runner 闭环；重复 POST/回调只推进一次；跨项目文件不可读；越权或过期安全放行被拒绝 |
| P5：集成与最终交付 | 隔离执行的集成工作项、验收证据、返工、最终验收和通知 | 所有必要结果完成后交回提出人，提出人确认结束 | 至少两人两项目、多角色、含依赖的完整 UI 流程；失败和返工不会提前 completed；集成代码无法读取控制面凭证 |
| P6：小团队试用 | 受控真实 SDK、预算、运行恢复、跨平台、同机资源回归与备份演练 | 验证真实 Agent 能完成，而不仅是 mock 能完成 | 真实模型冒烟和人工验收记录；旧系统黄金路径复测；旧快照恢复不复活已撤销权限，事件重放无重复执行；隔离、回滚与成本证据完整 |

P1 是安全前提，P4 不能在 P1 的隔离测试未通过时接真实项目数据。P0-P5 的自动化尽量使用确定性替身，P6 使用真实模型且需批准预算。

每阶段独立评审、独立回归；文档不是自动提交或推送代码的授权。CI/CD、权限和部署变更另行确认后实施。

端到端最低样例：甲提出项目 A 的“后端接口 + 前端页面 + 集成测试”需求；乙的 Agent 执行后端，甲的 Agent 执行前端；在项目 B 同一 Agent 担任测试。期间模拟离线、一次返工和一次跨项目读取。最终由甲验收 A，B 的身份和资料不发生变化。

### 14.4 测试分层与证据

1. 单元测试：权限、状态迁移、DAG 校验、版本冻结、幂等键、预算与摘要校验。
2. 集成测试：真实 SQLite/文件存储，验证事务崩溃窗口、重启恢复和数据隔离；不能只 mock store。
3. 协议测试：真进程/真 HTTP + Fake runner，故障注入重放、取消、断网、乱序。
4. UI 测试：真实浏览器操作需求、审批、原文查看、收件箱和最终验收，使用确定性模型替身确保可重复；检查控制台和截图。
5. 受控真实模型：批准小额预算后验证完整任务包、工具调用、实际产物与回传；不以此替代确定性回归。
6. 旧能力回归：每阶段重复运行第 3.2 节相关用例，共享内核/前端框架改动须跑全套。

记录命令、平台、基准提交、通过/失败/跳过、日志和截图。测试未执行、只用了 mock、只跑了页面结构，都必须在验收报告中明确。

## 15. 数据迁移、试用与回滚

### 15.1 初期无需迁移旧数据

- 旧任务继续属于旧控制面，不自动归入某个新项目，也不把所有旧数据作为“默认公共项目”。
- 团队项目从新存储开始。若以后需要导入，管理员和目标项目授权人选择具体资料，预览范围、检查敏感内容、保留来源并逐项授权。
- 导入产生新项目版本，不直接复用旧记录的访问权限。历史个人会话不得批量公开。
- 系统通用技能可作为只读模板复用；跨项目经验共享需以后单独设计显式发布流程。

### 15.2 回滚与停用

1. 暂停协作新接单和新派发，保留状态查询与结果收集。
2. 核对在途 attempt，完成或受控取消；未确认停止的执行进入对账清单。
3. 对协作数据库与文件存储做一致性备份，记录 schema_version、原文和产物校验结果。
4. 撤销协作执行凭证、停止协作实例与服务，不能停止无关旧 Worker。
5. 旧服务因未迁移数据和未改变入口可继续运行；如果修改过共享内核，应回退对应发布版本并重跑旧能力冒烟。
6. 新 schema 不向旧版本程序直接回滚写入；需要配套的恢复版本或备份恢复步骤，不能覆盖数据库赌兼容。

停用协作只停止未来动作，不自动撤销已写入外部系统的副作用。回滚不使用 `git reset --hard`、删除任务目录或清空数据库作为默认操作。

### 15.3 从旧快照恢复后的执行权对账

备份恢复不是普通进程重启。恢复后默认冻结派发，生成新的 control_epoch 并轮换执行授权密钥，使旧快照中的租约、任务令牌和未决放行不能恢复执行权；不能只依赖数据库里可能回退的 lease_epoch。机器协议和回调同时核对 control_epoch 与 lease_epoch，旧代次的结果只能进入历史对账区。

- 所有用户会话和节点授权重新认证；成员、绑定和撤权状态根据备份之外的可信撤权记录核对，缺少记录时先禁用相关授权，由项目授权人重新确认，不能默认恢复已被移除成员的访问权。
- 按 attempt_id/input_hash 将数据库、Worker 持久日志、已接收产物和外部副作用凭据对账。已完成任务恢复事实但不重执行；状态不明的任务继续 reconciliation_required，不因旧数据库显示 pending 就重新派发。
- Outbox 重放保留原事件 ID 和幂等键，逐条确认所属计划版本及恢复后的授权；过期派发事件作废，通知与结果事件去重后处理。
- 对账完成、在途执行已处置且权限复核通过后，由管理员显式解冻；新执行使用新授权，未对清的任务继续阻塞。

### 15.4 归档与删除

归档项目后停止派发，保留可授权查询的需求、版本、审核和交付证据。删除/保留期限由项目策略确定，本期不设静默自动删除；删除需覆盖文档、副本、向量索引、缓存、通知和执行实例残留，备份按独立保留周期处理并明确告知。

用户退出项目立即撤销后续访问，但不伪造已经下载副本被远程抹除的保证；敏感项目必须同时依赖受控执行环境和数据使用约定。

### 18.4 T03 认证与项目授权

- 数据库以事务从 v1 升级到 v2，新增账号、会话、邀请、登录限流和不可变审计表；升级失败保留原数据与版本，不修改旧 JSON store。旧版协作程序会拒绝写入 v2 数据库。
- 账号采用管理员本地一次性引导和邀请注册，无公开注册、默认口令或旧 API key 登录。口令使用随机盐 PBKDF2-HMAC-SHA256（600000 次），长度 12–1024；用户名为 3–64 位 ASCII 标识，不以展示名认身份。
- 会话和邀请令牌仅保存 SHA-256 摘要；会话默认 8 小时、邀请 24 小时。退出、过期或用户版本变化会使原会话失效；账号重新启用不会复活旧会话或旧邀请。
- 登录默认按服务端取得的客户端地址限制每 5 分钟 10 次，状态持久化；不信任请求自报的转发地址。代理部署需另行评估共享出口的限流影响，当前不自动修改代理配置。
- 项目授权、业务写入和成功审计使用同一 SQLite 事务。平台管理员管理账号邀请、账号启停和平台审计，不默认获得他人项目读取权；项目资源操作检查当前有效成员关系，创建项目的 owner 只能是当前登录用户。manager 不得授予或修改 owner/manager 角色。
- 独立 HTTP 入口使用 `/collab/v1`，不挂载旧 `/dispatch`，不读取个人 `.env`。Cookie 为 HttpOnly、SameSite=strict、Path=/collab/v1，HTTPS 下设置 Secure；所有写请求要求精确 Origin，登录后的写请求另需 `X-CSRF-Token`。登录返回 CSRF、用户和到期时间，会话令牌仅写入 Cookie，不在 JSON 中返回。Host 必须与配置 authority 一致，不开启 CORS。

### 18.20 T08i 对账为失败时把工作项放回可重排队列（T08 进行中）

### 18.21 T08j 待办未读标记与计数（T08 进行中）

本轮改动：`collaboration/database.py`（`SCHEMA_VERSION` 8→9，新增 `inbox_acks` 表）、`collaboration/store.py`（`inbox_acks`/`ack_inbox`）、`collaboration/inbox.py`（`_identity`、`stamp`、`ack`）、`collaboration/app.py`（`GET /inbox` 为每条待办附上 `key` 与 `unread`，新增 `POST /inbox/ack`）、`collaboration/web/{index.html,app.js,styles.css}`（未读计数、「未读」标记与「标记已读」按钮）、`tests/test_collaboration_execution.py`（迁移 2 项 + 服务层 1 项）与 `tests/test_collaboration_app.py`（HTTP 2 项）。旧启动链、旧面板、旧数据、CI 未改动。

- 键的唯一来源是合并后的收件箱：`GET /inbox` 把草稿阶段待办（`requirements.inbox`）与执行阶段待办（`inbox.pending`）合并后统一 `stamp`，所以两条投影共用一套键，不会出现同一件事两个名字。
- 读过不等于裁定：`ack` 只写一行阅读状态，待办的 `action`/`href`/`expected_version` 一个字都不改，裁定仍然挂着。`known` 由 HTTP 层把当前合并结果交给服务，只能标自己此刻真的欠着的那条；陌生键、别人的键、已经消失的键一律 422（不是 404，避免用已读接口探测别人欠什么）。`ON CONFLICT DO NOTHING` 让重复标记无害，且第一次的时间戳不被覆盖。
- 计数放在面板而不是服务端：API 只给每条的 `unread`，面板对**它实际渲染出来的**待办求和。服务端不另发计数端点，是因为面板目前只渲染执行阶段待办（18.17 起），若把草稿阶段待办也计进红点，就没有任何入口能把它清掉。
- 分页本轮明确不做：待办查询仍是单条 `UNION ALL` 全表扫（18.16 已记），真实数据量与索引选择都没测过；先给分页只会给出一个没验证过的 `limit/offset` 契约。
