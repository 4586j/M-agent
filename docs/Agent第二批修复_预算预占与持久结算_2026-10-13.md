# Agent 第二批修复：预算预占与持久结算

日期：2026 年 10 月 13 日

实施基线：第一批提交 `6863572`。本记录随第二批代码一并提交，尚未部署。

## 1. 本批解决什么

第一批统一了各派发入口的预算检查，但检查已花费用与启动执行之间仍存在并发窗口；任务状态和费用账本分开写入，也不能仅靠终态保护处理崩溃、重复通知和取消后的真实费用。

本批将准入改为按执行 ID 原子预占，并增加持久费用报告与幂等结算。每个旧链路 task_id 对应一次执行；自动重试产生新的 task_id，因此分别预占和结算。同步远程、异步远程、本地 AgentKernel 执行、定时、自动重试和重派复用同一装配入口。

本批没有统一团队协作子系统的独立预算，也没有将所有模型调用费用纳入一个硬上限。预占额是估值，实际成本可能高于它；实际费用会如实结算，超限后拒绝后续派发。

## 2. 执行与结算顺序

1. 派发前严格重放已持久化但尚未结算的费用报告，再检查预算和安全规则。
2. 在 SQLite 写事务中读取“已花 + 未结算预占”，确认余额足够后写入本次执行预占。并发请求不能重复获得同一份剩余额度。
3. 派发器使用同一个执行 ID 创建任务记录，随后发送 Worker 请求或启动本地执行。
4. 结果到达后，先在任务 JSON 中原子保存 `cost_report`，再按执行 ID 将费用写入账本；最后通过已有条件更新提交任务终态。
5. Brain 启动和周期恢复都会重放费用报告。重复报告不重复收费；累计成本向上修正只增加差额，较小的迟到值不会回退已记费用。

费用报告独立于任务 status。任务已经 cancelled 后仍可补记真实成本，同时保留 cancelled 状态；补记过程不会重新发布 running 进度。

| 中断位置 | 恢复行为 |
| --- | --- |
| 预占成功，尚未创建任务时进程退出 | 预占保留，清单显示 missing；不凭超时自动释放 |
| 派发响应丢失或服务端 5xx | 保留预占，查询原执行 ID，不推断为零成本 |
| 费用报告保存后，账本提交前退出 | 启动或下次派发前重放报告 |
| 账本提交后，任务终态保存前退出 | 再次读取执行结果；同 ID 费用不会重复累计 |
| SQLite 事务尚未提交即进程退出 | SQLite 回滚未提交变化，预占和费用不出现半更新 |
| 执行中被取消，稍后返回实际费用 | Worker 保存最终执行回执并回调；Brain 补记费用，状态不复活 |
| 执行结果缺少有效成本，或执行体在报告前消失 | 保留预占并等待核对；不把未知成本当成 0 |

明确发生在执行前的拒绝可以释放预占：例如未找到可用 Worker，或者 Worker 返回 400/401/403/404/409/422/429。取消请求的 ACK 不证明执行体已退出，因此不会释放预占。

## 3. 账本与迁移

原 `BudgetStore` 的 JSON 文件路径配置继续有效，例如 `runtime/budgets.json`。新版本在相邻位置创建 **`budgets.json.sqlite3`**，并在初始化事务内一次性导入旧 JSON 的上限、累计费用和每日费用。

- 原 JSON 不覆盖、不删除，用于保留升级前快照。
- 初始化完成后，SQLite 是权威账本；继续手动修改旧 JSON 不会改变当前预算，应使用 `/budgets` API。
- 旧账本无法解析或金额非法时，初始化失败。不会重建为零余额。
- 新账本采用整数微美元，精度为 0.000001 美元；拒绝 NaN、Infinity、负成本、布尔值和超出范围的输入。
- 全局/每日上限为 0 或 None 时仍表示不限额。历史按日费用不在本批自动裁剪。
- 跨日未结算的预占继续占用新一天的可用额度，避免午夜释放仍在运行任务的额度。费用按报告首次在 Brain 保存的自然日结算；离线重放不会把它改成重放当天。
- `record_spend(cost)` 仅保留兼容接口；有预占的正式执行路径使用 `settle(task_id, cost)`，不会同时走兼容接口重复记账。

部署时应一起备份原 JSON、新 SQLite 和任务 JSON 目录。回滚到只读旧 JSON 的版本会遗漏升级后费用，不能直接把旧快照当作最新账本；需要先从新账本核对、导出后再回滚。本批未执行线上迁移或部署。

升级前应尽量等待旧版本在途任务结束并完成费用核对。旧 JSON 仅保存汇总金额，没有每次执行的结算标识；本批的按执行 ID 幂等保证适用于纳入预占的新执行，不能追溯证明旧版本未跟踪执行的结算唯一性。

SQLite 账本事务可协调同一数据库上的多连接、多实例访问，但整个 Brain 的任务 JSON 缓存和状态锁仍是单进程设计；不能据此宣布 Brain 已支持多副本运行，也不建议把数据库放在未经验证的网络文件系统上。

## 4. 配置与查询

新增环境变量：

```dotenv
ORCH_BUDGET_RESERVATION_USD=0.05
```

默认每次执行预占 0.05 美元，必须是有效正数，最小单位为 0.000001 美元。应按真实任务的成本估值调整；余额不足以预占完整金额时拒绝启动，不会自动缩小估值。即使未配置总上限，执行仍记录预占与结算，便于后续核对。

这是并发准入估值，**不是 SDK 或供应商账单的硬费用上限**，也不替代现有单次执行预算配置。单次实际成本、重试、辅助模型调用等边界仍需单独验收。

`GET /budgets` 在原有字段之外增加：

| 字段 | 含义 |
| --- | --- |
| `reserved_usd` | 当前未结算执行的预占总额 |
| `unsettled_count` | 未结算执行数 |
| `global_remaining_usd` | 全局上限减去已花费用和未结算预占 |
| `daily_remaining_usd` | 当日上限减去当日已花费用和全部未结算预占 |

`GET /budgets/reservations` 返回未结算执行的 task_id、预占金额、更新时间、任务状态及是否需要核对。接口沿用 Brain 现有鉴权。未找到任务记录时返回 `task_status=missing`，保留预占供检查。

`/dispatch` 和 `/dispatch/async` 在预算不足时返回 429，包括前置检查通过后又被并发请求占用额度的情况。原有审批仍不能绕过预算。

此处仅提供核对清单，没有新增“强制清空所有预占”的操作接口。未知副作用和未知费用需要结合 Worker 回执、产物和供应商用量核对；自动过期释放可能重新放大超支风险。

## 5. Worker 回执调整

取消 ACK 携带 `meta.execution_finished=false`；Runner 退出后回执携带 true，并保留其真实成本。SQLite 接收记录允许把“已取消但执行未结束”的记录更新为“仍取消且已执行结束”，用于跨重启读取费用。

最终 cancelled 回执也会回调 Brain。回调丢失时，Brain 可查询尚有预占的 cancelled/lost/failed 任务，不必将业务状态改回运行中。查询耗尽或完整结果仍无成本时标记需要核对，保留预占；有效的迟到回调仍可结算。

FakeAgentRunner 明确回传成本 0，因为它不调用模型。真实执行器缺少成本时保持未知，不套用 Fake 的零成本假设。第一批规定的“一个工作目录由一个 Worker 进程独占”仍然适用。

## 7. 下一阶段边界

已保存费用报告的重复提交和恢复有了确定性依据；执行体在产生成本后、保存报告前消失的情况，仍需要供应商账单或其他持久用量源核对。持有预占可以避免盲目释放额度，但不能凭空恢复丢失的真实费用。

后续建议依次补上：任务/attempt 聚合及人工核对操作、按任务类型估值或执行预算联动、辅助调用成本接入、账本与报告归档，以及团队协作的真实 Planner/Runner。协作子系统现有预算模型与本账本仍分别计费，尚未形成统一总账。
