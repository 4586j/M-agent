## 1. 目标与约束

优先贯通真实团队的需求分析、执行、交付和验收，让领导聚焦目标、计划、预算、监察和关键决策。个人理解沟通保持个人范围，不加入多 Agent/团队派发门槛。

状态使用“已实现（工作区）”“已提交”“进行中”“待开发”“待验证”。已实现不自动等于已提交、发布或部署；负责人尚未确定时写“待指派”。

## 4. 推荐阶段与完成出口

### 阶段 A：收敛边界与适配器契约

完成 PLAN-01 的模式/配置定义，明确 Planner/Runner 输入、输出、错误、预算、权限和产物契约；形成 [架构决策](templates/架构决策模板.md)。不同时重写旧 Brain 全部存储。

### 阶段 B：最小真实闭环

完成 PLAN-02—04。先做一条需求、有限职责、一个明确产物的受限场景，再增加角色和节点。模拟协议测试通过后，真实模型联调与业务验收仍分别记录。

### 阶段 C：多人及领导体验

完成 PLAN-05—07。打通个人到团队授权、按规则推进与项目成本，验证成员撤权、计划变更、预算耗尽和返工路径。

### 阶段 D：可靠性与规模化

推进 PLAN-08—10。针对已识别瓶颈改造，保留迁移/回滚和故障注入证据。未验收前不宣布多副本、高可用或强沙箱能力。

## 5. 执行与关闭规则

- 开始一个任务时记录 ID、范围、负责人、依赖、风险和完成条件；模板见 [开发任务模板](templates/开发任务模板.md)。
- 进行中发现范围变化时先修改工作项与相关架构记录；不把旧范围的测试结果沿用为新范围已通过。
- 关闭时附实现文件、测试命令/范围/日期/结果、真实业务验收状态、数据迁移和剩余限制。
- 提交/发布/部署状态有各自证据；没有证据就保持未提交/未发布/未部署。
- 持续更新 [CHANGELOG](../CHANGELOG.md)、[问题台账](问题修复与解决方法.md) 和 [文档中心](README.md)。
