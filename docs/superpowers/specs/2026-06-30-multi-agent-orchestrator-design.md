# 多 Agent 编排框架设计

> 将现有 data-expert 升级为通用多 agent 编排框架：1 个大脑 + 1 个执行 + 1 个安全检验，外加三方共识驱动的核心记忆。

---

## 1 背景与目标

现有 `data-expert` 是一个 Collectors → Analyzers → Generators 三层流水线的单 skill 数据分析工具。本次目标是把它纳入一个**通用多 agent 编排框架**：data-expert 成为框架首个被调用的执行能力，框架本身可承载后续更多任务类型。

框架由三个角色 + 一个记忆层组成，运行在 Claude Code 之上：

- **大脑（Brain）**：主会话，负责意图澄清、边界探索、prompt 优化、任务拆解、派发、结果审核、候选记忆提炼。
- **执行（executor）**：子 agent，完成任务、产出代码/文件/结论。
- **安全检验（security-guard）**：只读子 agent，对指令/关键中间产物/代码做安全检验，不通过反馈用户决定。
- **核心记忆**：三方共识（全票通过）才写入，用于指导后续任务。

### 已对齐前提

| 决策点 | 选定 |
|--------|------|
| 运行基底 | Claude Code 子 agent；大脑 = 主会话，执行/安全 = 派发的子 agent |
| 系统定位 | 通用编排框架，data-expert 为首个被调用能力 |
| 安全介入 | 全流程多关卡：指令 / 关键中间产物 / 代码 |
| 核心记忆共识 | 三方独立投票，全票通过才写入，任一否决丢弃 |
| 记忆载体 | 内置 memory（核心、自动加载）+ 框架自管任务上下文记忆（临时、按任务生命周期）分层 |
| 安全标准 | 默认规则 + 用户可覆盖 |
| 落地形态 | skill + 自定义 agent 类型（executor / security-guard），工具隔离物理保证安全角色边界 |

## 2 整体架构与角色分工

```
                        用户
                         │ 对话
                         ▼
              ┌─────────────────────┐
              │   大脑 (Brain)       │  主会话 = 一个编排 skill
              │  澄清意图/边界探索    │
              │  prompt优化/任务拆解  │
              │  派发/结果审核        │
              │  候选记忆提炼         │
              └──┬───────────────┬──┘
        派发执行  │               │ 派发审查
                 ▼               ▼
     ┌────────────────┐   ┌──────────────────┐
     │ executor       │   │ security-guard   │
     │ 全工具+技能     │   │ 只读工具+安全规则 │
     │ 完成任务、产出  │   │ 检验指令/产物/代码│
     └────────────────┘   └──────────────────┘
                 │               │
                 └───────┬───────┘
                         ▼
              ┌─────────────────────┐
              │   记忆层 (Memory)     │
              │  核心记忆: 内置memory │  ← 三方共识写入，自动加载
              │  上下文记忆: 自管目录 │  ← 按任务生命周期临时
              └─────────────────────┘
```

### 角色边界

| 角色 | 形态 | 工具集 | 职责 | 不做什么 |
|------|------|--------|------|----------|
| 大脑 | 主会话 skill | 主会话默认工具 | 意图澄清、边界探索、prompt 优化、任务拆解与派发、结果审核、候选记忆提炼 | 不亲自执行任务、不亲自写业务代码 |
| executor | `.claude/agents` 子 agent 类型 | 全工具 + 可调用 data-expert 等技能 | 执行大脑下发的子任务，产出代码/文件/结论 | 不决定任务目标、不自行与用户对话 |
| security-guard | `.claude/agents` 子 agent 类型 | 只读（Read/Glob/Grep/WebFetch 等，无 Write/Bash/Edit） | 对指令、关键中间产物、代码做安全检验，给出通过/否决+理由 | 不执行任务、不修改文件、不替用户决策 |

### 关键设计点

- 安全 agent 的「只审查不执行」靠**工具集物理隔离**，不靠 prompt 自律——它根本没有写文件和跑命令的工具。
- executor 与 security-guard 的并行/串行由大脑按关卡调度（见第 3 节）。
- 记忆层分两层：核心记忆（持久、自动加载、共识写入）和上下文记忆（临时、按任务、自管），职责分离、互不污染。

## 3 大脑工作流

大脑是主会话里运行的一个编排 skill，把用户的一条指令走完整个生命周期，分七个阶段：

```
1.意图澄清 → 2.边界探索 → 3.prompt优化 → 4.任务拆解
   → 5.安全关卡①(指令) → 6.执行调度 → 7.结果审核+安全关卡②(产物/代码)
                                                    │
                                              (循环回 5/6 直到通过)
```

### 各阶段职责

| 阶段 | 大脑做什么 | 产出 |
|------|-----------|------|
| ① 意图澄清 | 用举例、追问确认用户到底要什么，举反例排除歧义；一次只问一个关键问题 | 一句话意图陈述 |
| ② 边界探索 | 摸清环境约束：能改哪些文件、有无依赖、目标平台、数据范围、安全红线 | 边界清单 |
| ③ prompt 优化 | 把意图+边界转成给 executor 的精炼任务说明（含上下文记忆注入） | 优化后的任务 prompt |
| ④ 任务拆解 | 复杂任务拆成有序子任务，标注哪些产物需过安全关卡 | 子任务列表 |
| ⑤ 安全关卡① | 把任务 prompt 派给 security-guard 检验「指令」是否安全 | 通过 / 否决+理由 |
| ⑥ 执行调度 | 通过则派给 executor 执行子任务；不通过则停下来反馈用户决定 | 执行结果/产物 |
| ⑦ 结果审核 + 安全关卡② | 审核产出是否达意；对关键中间产物和代码再派 security-guard 检验 | 通过 / 回 ⑥ 修正 |

### 关键约束

- **安全不通过，永远停给用户**：security-guard 否决时，大脑不自行放行也不自行修正，而是把「否决理由 + 原始内容」呈现给用户，由用户选择放行/修改/放弃。这是硬约束，写进 skill 的前置规则。
- **关卡粒度可配**：默认每子任务的指令过①、代码过②；用户可在边界阶段声明「跳过产物关卡」之类，但①不可跳（指令必须验）。
- **结果审核的判定权在大脑**：security-guard 只管安全不管质量；产出是否达到用户意图由大脑判断，不达标回到执行调度修正，不甩给用户。
- **并行与串行**：无依赖的子任务可并行派多个 executor；security-guard 的检验之间相互独立也可并行。大脑维护子任务依赖图。
- **上下文记忆注入**：③阶段把当前任务相关的自管上下文记忆拼进 prompt；核心记忆已自动加载进主会话，无需额外注入。

## 4 安全检验机制

security-guard 是只读子 agent，靠**默认规则 + 用户可覆盖**判定。检验贯穿三个关卡，每个关卡输入不同、判定逻辑相同。

### 规则体系（两层）

```
security-rules/
├── default.yaml      # 框架自带默认规则，随版本更新
└── overrides/        # 用户覆盖/扩展（不改默认文件）
    └── user.yaml     # 用户的加严/放宽/自定义
```

合并规则：用户 overrides 中的同名规则**覆盖**默认；新增规则**追加**。两层最终合并成一份生效规则，security-guard 每次启动读取生效规则 + 固定角色 prompt。

### 默认规则类别（第一版内置）

| 类别 | 检什么 | 示例 |
|------|--------|------|
| 危险命令 | Bash 里的破坏性操作 | `rm -rf /`、`drop table`、强制 push、`git reset --hard` 到远程 |
| 路径越权 | 访问工作区外文件 | 读写 `..` 越界、系统目录、其他项目 |
| 注入与执行 | 代码里的注入面 | eval/exec、未参数化 SQL、shell=True 拼接用户输入 |
| 敏感数据外发 | 数据流向 | 把密钥/凭证写入文件、外发到网络、提交进仓库 |
| 凭证泄露 | 硬编码秘密 | 代码里出现 API key / token / 密码字面量 |

### 检验流程（每个关卡一致）

```
输入(指令/产物/代码) + 生效规则
        │
        ▼
security-guard 子 agent
  ├─ 逐条规则匹配（结构化判断）
  └─ 规则外的可疑情况用 LLM 补充判断
        │
        ▼
   结构化裁决
```

裁决统一为结构化结果：

```yaml
verdict: pass | block      # 二元，block 即不通过
reason: "命中 R-DANGER-03：rm -rf 路径含 /"
matched_rules: [R-DANGER-03]
suggestion: "改为限定到 workspace/ 下删除"
```

### 三个关卡的输入差异

| 关卡 | 输入 | 重点检 |
|------|------|--------|
| ① 指令关卡 | 大脑下发的任务 prompt | 任务目标本身是否越界（如「清空数据库」） |
| ② 产物关卡 | executor 产出的关键中间产物（文件路径清单、生成内容摘要） | 路径越权、数据外发、凭证泄露 |
| ③ 代码关卡 | executor 写入/修改的代码 | 危险命令、注入面、硬编码秘密 |

### 否决后的处理（硬约束）

- security-guard 返回 `block` → 大脑立刻停，把 `reason + suggestion + 原始内容` 呈现给用户。
- 用户三选一：**放行**（覆盖该规则一次，记入上下文记忆）/ **修改**（回 executor 按建议改）/ **放弃**。
- 大脑不自行放行、不自行改安全相关内容。与第 3 节约束一致。

### 安全 agent 的工具集（物理隔离）

- 有：Read、Glob、Grep、WebFetch（查规则文档）
- 无：Write、Edit、Bash、NotebookEdit、Agent——改不了任何东西、跑不了任何命令、派不了子 agent，只审查。

## 5 核心记忆与共识机制

记忆分两层，职责严格分离。

```
┌─────────────────────────────────────────────┐
│  核心记忆 (Core)  — 内置 memory 机制           │
│  持久 · 自动加载进每个会话 · 三方共识才写入      │
│  ~/.claude/projects/.../memory/*.md + MEMORY.md│
└─────────────────────────────────────────────┘
┌─────────────────────────────────────────────┐
│  上下文记忆 (Context) — 框架自管                │
│  临时 · 按任务生命周期 · 单任务内可读写          │
│  workspace/agent/memory/context/<task-id>/    │
└─────────────────────────────────────────────┘
```

### 两层职责

| 层 | 存什么 | 谁写 | 何时失效 | 怎么被读 |
|----|--------|------|----------|----------|
| 核心记忆 | 跨任务可复用的核心事实（项目约定、用户偏好、反复验证的结论） | 三方共识通过后由大脑写 | 永久（除非三方共识删除） | 自动加载进主会话上下文 |
| 上下文记忆 | 单次任务的过程信息（中间产物路径、已尝试方案、临时决策、用户一次性放行） | 大脑/executor 在任务中写 | 任务结束即归档/清理 | ③阶段 prompt 注入、executor 启动注入 |

核心记忆门槛高（共识写入）、自动加载、长期有效；上下文记忆门槛低（任务内自由写）、按需注入、任务结束即逝。互不污染。

### 核心记忆的共识写入流程

```
① 大脑在任务结束/关键节点提炼「候选记忆条目」
   （一条候选 = 一个事实陈述 + 拟写入的 memory 文件草稿）
        │
        ▼
② 并行派三个独立投票子 agent：
     · 大脑自身视角     → 是否「值得长期复用指导后续任务」
     · executor 视角    → 是否「可操作、与执行现实一致」
     · security 视角    → 是否「无敏感/错误/越权信息」
   每方独立投 pass/block + 理由，互不可见
        │
        ▼
③ 三票全 pass → 大脑写入核心 memory 文件 + 更新 MEMORY.md 索引
   任一 block → 丢弃该候选（不写入，理由可存入上下文记忆备查）
```

### 关键约束

- **全票通过才写入**：三票缺一不可，任一否决即丢弃。
- **独立投票**：三方 prompt 各自带自己的视角和判定标准，互不看对方结果，避免跟风。
- **大脑是唯一写入者**：executor 和 security-guard 只投票不写文件（security-guard 本就没写工具；executor 即使能写，共识写入这一动作也收敛到大脑，保证单一写入入口）。
- **删除同理**：核心记忆过时需删除时，也走三方共识（提候选 → 三票 → 通过才删），避免单方面抹掉。
- **候选提炼时机**：不每次任务都提，而是在大脑判断「这次出现了值得长期记住的东西」时才提，避免记忆膨胀。

### 与现有内置 memory 的关系

完全复用 Claude Code 内置的文件式 memory 格式（frontmatter + `MEMORY.md` 索引），不另造存储。区别只是写入门槛：内置 memory 默认谁都能写，这里加了一道三方共识闸门，只有共识通过的事实才落盘成核心记忆。上下文记忆则是内置机制之外、框架自管的临时层。

## 6 文件结构与扩展点

### 目录结构

```
d:\agent\agent\
├── .claude/
│   └── agents/
│       ├── executor.md              # executor 子 agent 类型定义（全工具+技能）
│       └── security-guard.md        # security-guard 定义（只读工具+角色prompt）
├── workspace/agent/
│   └── skills/
│       ├── data-expert/             # 现有能力（保留不动）
│       └── orchestrator/            # 新增：大脑编排 skill
│           ├── SKILL.md             # 七阶段流程 + 安全硬约束 + 派发规则
│           ├── memory/
│           │   └── context/         # 自管上下文记忆（按 task-id 分目录）
│           └── security-rules/
│               ├── default.yaml     # 默认规则
│               └── overrides/
│                   └── user.yaml    # 用户覆盖/扩展
└── docs/superpowers/specs/
    └── 2026-06-30-multi-agent-orchestrator-design.md   # 本设计文档
```

### 各单元接口

| 单元 | 是什么 | 怎么用 | 依赖 |
|------|--------|--------|------|
| `orchestrator/SKILL.md` | 大脑工作流定义 | 用户对话时由主会话加载 | 两个 agent 类型、规则文件 |
| `executor.md` | 执行角色定义 | 大脑用 Agent 工具 `subagent_type: executor` 派发 | data-expert 等技能、全工具 |
| `security-guard.md` | 安全角色定义 | 大脑用 Agent 工具 `subagent_type: security-guard` 派发 | default.yaml + overrides |
| `security-rules/` | 规则源 | security-guard 启动时读取合并 | 无 |
| `memory/context/` | 临时记忆 | 大脑按 task-id 读写注入 | 无 |
| 内置 `memory/` + `MEMORY.md` | 核心记忆 | 共识通过后写入，会话自动加载 | 三方共识流程 |

### 扩展点

1. **加新执行能力**：在 `skills/` 下加新 skill（如未来加代码审查助手），executor 自动可调用，无需改大脑。
2. **加新 agent 角色**：在 `.claude/agents/` 加定义文件（如未来加「测试 agent」「文档 agent」），大脑按需派发。每个角色一个文件、单一职责。
3. **加新安全规则**：往 `security-rules/overrides/user.yaml` 加条目，不碰默认文件；或新增规则类别后更新 default.yaml。
4. **加新记忆来源**：核心记忆目前来自大脑提炼，未来可让 executor/security 也能提候选，仍走同一共识闸门。

### 与现有 data-expert 的衔接

data-expert 作为 executor 可调用的技能保留不动。用户对大脑说「分析这个 CSV」，大脑走七阶段，executor 子 agent 在执行阶段调用 data-expert skill 产出报告，安全 agent 检验产出的文件路径与代码——data-expert 不感知多 agent 框架的存在，解耦干净。

## 7 部署形态与扩展点

### V1 部署形态：单机单进程

V1 是**单机、单 Claude Code 进程内**的子 agent 派发：大脑是主会话，executor 与 security-guard 是大脑用 Agent 工具在同一进程、同一文件系统内派发的临时子 agent，跑完即销毁。三者共享同一台机器的磁盘与代码，所谓「三角色」「三方投票」是**逻辑角色**，不是物理上的三台机器。

### 为跨主机演进预留的扩展点

V1 不实现分布式，但在架构边界上预留扩展点，使将来换底层实现不必重写大脑逻辑：

| 关注点 | V1 实现（单机耦合） | 预留的抽象边界 |
|--------|---------------------|----------------|
| agent 派发 | Agent 工具、`subagent_type` | 派发动作收敛到大脑的「调度步骤」描述，不把进程内调用细节写进业务流程；将来可替换为远程调度 |
| agent 定义 | `.claude/agents/*.md` | 角色定义（工具集、prompt、规则源）与派发机制分离，跨主机时角色定义可迁移为远程 worker 配置 |
| 记忆访问 | 直接读写本地文件/内置 memory | 记忆访问走「核心记忆接口 / 上下文记忆接口」两类语义，V1 落地为本地文件，将来可换中心化存储 |
| 安全规则 | 本地 YAML 文件 | 规则以「生效规则集」形式被 security-guard 读取，来源可替换为远程规则服务 |

**原则**：V1 不为分布式写任何代码，但在 SKILL.md 与文件结构中保持上述边界清晰——派发、记忆、规则三类关注点的「做什么」与「在哪做」分开描述。演进到跨主机时，替换的是「在哪做」（本地→远程），「做什么」（七阶段流程、共识投票、安全关卡）不变。

### 演进到跨主机的变更面（仅备忘，V1 不实现）

- 大脑从「主会话」变为「调度服务」，经消息总线（Redis/MQ）或 HTTP 派发到各主机 worker
- 记忆层中心化（共享存储 + 同步协议）
- security-guard 的工具隔离从「进程内工具集」升级为「物理机器隔离」
- agent 定义从 `.claude/agents/*.md` 迁移为远程 worker 配置

## 8 有意不做（YAGNI）

- 不做 agent 间自由对话：所有协作经大脑编排，executor/security 不互相直连。
- 不做记忆去重/向量化检索：第一版靠文件 + MEMORY.md 索引 + 按需注入，记忆量不大时足够。
- 不做 Web UI / 仪表盘：纯 Claude Code 原生交互。

- **角色隔离测试**：验证 security-guard 子 agent 确实无 Write/Bash 等工具，调用即被拒。
