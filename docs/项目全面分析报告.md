## 一、执行摘要

本项目是一套**单机与集群双形态的 Agent 编操作系统**：以统一执行内核（AgentKernel）为核心，
向上支撑三种运行形态（交互式 CLI / 本机服务+面板 / 跨主机集群），向下通过 skill/MCP
接入外部能力，并以**安全边界、四层记忆、事件可观测**三大横切体系贯穿。

| 关键指标 | 数值 |
|---|---|
| Python 代码 | agent_core 22,242 行（33 模块）+ runtime 12,469 行（30 模块）+ worker 2,659 行 |
| 前端代码 | 4,434 行（React 18 + Vite + TS，9 视图） |
| 测试用例 | agent_core 730 + runtime 421 + worker 71 + 前端 30+ ≈ **1250+**，全绿 |
| API 端点 | brain_api 45+ / agent service 20+（含 2 条 SSE、1 条 WebSocket） |
| 技能 | 4 个（orchestrator / data-expert / web-expert / back-expert）+ skillhub 仓库 |
| 提交 | 71 个，功能演进脉络清晰可追溯 |

**一句话评价**：这是一个完成度显著高于典型个人项目的 Agent 基础设施——安全纵深、
事件可观测、记忆分层、成本闸门等"基础设施级"能力都有真实实现与测试背书；
主要短板集中在跨层一致性与部分能力的实测深度。

## 二、系统架构

### 2.1 分层总览

```
交互层   Web 面板(React,9视图,SSE) · orch CLI(REPL) · Agent 面板(ZCode式) · MCP Server(18工具) · dispatch_cli
            │
编排层   brain_api（45+ 端点，FastAPI，SSE 事件流）
         ├ 派发：Remote / Async / LocalExecutor（统一 Dispatcher 抽象）
         ├ 集群：定点派发 · 多节点管理 · 连接存储/baseUrl
         ├ 调度：cron · 重试自愈 · 审批流 · 审计日志
         └ 记忆四层：经验 / 上下文 / 核心 / 程序（演化管线）
            │
执行层   AgentKernel（22k 行统一内核，三种形态共用）
         ├ run_oneshot / open_session / stream
         ├ Persona · Plan-Execute 引擎 · TaskRouter 自适应路由
         ├ 七道防线：prompt/output/plan/result/tool/tool_response/circuit-breaker
         └ 隔离执行 · 批处理 · 优先队列 · 重试策略 · trace
能力层   skills/：data-expert · web-expert · back-expert（+ skillhub 仓库对账）
```

### 2.2 三种运行形态（同一内核）

| 形态 | 入口 | 特征 |
|---|---|---|
| 交互 CLI | orch_cli / agent_core.cli | REPL、会话恢复、/cost、slash 命令 |
| 本机服务 | brain_api + ORCH_LOCAL_EXEC，或 agent_core.service | 面板可视化、SSE 实况、内嵌终端 |
| 跨主机集群 | brain(remote) + worker | 定点派发、心跳、审批、审计 |

形态切换不改安全与记忆逻辑——这是架构上最重要的不变量。

### 3.5 成本与性能控制

- 思考 token 上限（默认 1 万，实测最大成本项省 30-40%）/ 单任务美元硬预算 / max_turns
- context_memory 限幅（8k 字符截断保头部）/ 安全检验输入限幅（6k）
- KV-cache 友好前缀（system prompt 跨任务稳定，实测缓存命中 91%）
- 启发式模型路由（简单任务→便宜模型，opt-in）/ 面板缓存命中率可视
- 全链路用量可观测：usage/cost/duration 进 meta → stats → SSE → 面板

## 六、已知短板与风险（如实）

| # | 短板 | 影响 | 建议 |
|---|---|---|---|
| 1 | 跨层契约无守护：types.ts 与后端 Pydantic 模型靠人工同步 | 前后端字段漂移（已发生过 approval 字段） | openapi.json ↔ types.ts 契约比对脚本进 CI |
| 2 | E2E 全链路测试仍以脚本冒烟为主 | 回归靠手工 | Playwright 七视图 + brain remote↔worker 跨进程链路 |
| 3 | thinking 事件的 token 成本：thinking_delta 全量入 JSONL | 长任务事件文件大 | 持久化层压缩或聚合（展示层已截断） |
| 4 | 经验库并发写竞态 | 多 worker 同时完成时理论可丢条目 | SQLite journal 或文件锁 |
| 5 | `bypassPermissions` 双语义（集群 worker / 面板）依赖 Windows 替代方案 | 非 Windows 未实测 | 类 Unix 环境跑一轮权限方案回归 |
| 6 | 面板 iframe 预览仅覆盖常见入口文件名 | 非常规产物需手输路径 | 产物列表点选预览 |
| 7 | 双形态文档（编排面板 vs Agent 面板）易混淆 | 新用户上手成本 | README 顶部加形态选择引导图 |

## 七、与业界对标

| 维度 | 本项目 | 业界参照 | 差距评估 |
|---|---|---|---|
| 编排模式 | Orchestrator-Workers + 三形态 | LangGraph/AutoGen | 形态切换统一性更好；图编排灵活性略逊 |
| 记忆 | 四层+演化+淘汰 | Letta/Mem0/Zep | 分层设计同构；缺向量库规模化（SQLite JSON 起步） |
| 可观测 | SSE 事件流+审计+trace+用量 | Langfuse/Phoenix | 自建轻量版够用；缺 OTel 标准导出 |
| 安全 | 五层纵深+工作区边界 | Claude Code 权限模型 | 工作区 confirm 授权机制不输主流；缺策略配置化 |
| 终端 | WebSocket+持久 cwd | VSCode/ZCode 集成终端 | 无 xterm.js（无 ANSI 渲染），够用但视觉简陋 |
| 测试 | 1250+ 用例 | — | 高于典型开源 agent 项目 |

## 八、下一步建议（按优先级）

1. **P0 契约守护**：openapi↔types.ts 比对进 CI（防字段漂移，已发生过）
2. **P0 E2E**：Playwright 七视图 + brain↔worker 跨进程链路（脚本已有，产品化）
3. **P1 经验库并发安全**：多 worker 完成竞态（文件锁或迁 SQLite journal）
4. **P1 OTel 导出**：trace/事件接 Phoenix/Langfuse（自建可观测 → 标准生态）
5. **P2 策略配置化**：工作区边界规则、确认粒度抽成策略文件
6. **P2 xterm.js**：终端 ANSI 渲染升级（视觉+兼容性）
