# 协作模式定位与当前架构差距

日期：2026-10-18。根据当前仓库代码核查。本次实施范围为把理解沟通机制迁到个人单 Agent，移除多 Agent 编排入口；其他模式以现状分析和建议为主。

## 需要分开的两个维度

用户描述的重点是人的职责和协作关系。建议将其定义为个人协作、领导监督、团队协作三种产品模式；单机/多主机另外作为部署方式。

一台机器也可以运行多个职责 Agent；多台机器并不自然形成成熟团队。`Agent` 是逻辑身份，`AgentProjectBinding` 是项目职责及授权，`ExecutionInstance` 是运行实例，`ExecutionNode` 是机器。不要把一个终端窗口、一台主机和一个团队成员混为一谈。

| 模式 | 人承担什么 | Agent 承担什么 | 理解沟通是否启用 |
| --- | --- | --- | --- |
| 个人单 Agent | 与自己的 Agent 交流、理解需求、参与实现与决策 | 分析、解释、实现、测试与辅助学习 | 按需启用；用户主动申请，或独立分析发现有依据的严重偏差 |
| 领导监督的多 Agent | 提出目标和高层计划、明确验收条件与预算、监督、关键批准、最终验收 | 多个职责 Agent 完成需求细化、技术方案、开发、测试、安全检查和集成 | 不加入逐题答题门槛；信息缺失时提出业务澄清，不能要求领导通过代码知识考试 |
| 团队 Agent | 多个人各有个人 Agent，各自负责职责和交付，也有项目共同目标 | 个人 Agent 经项目授权参加协作，按职责交付和互相检查 | 可在个人私有协作中使用；团队派发与项目验收不强制加入核验 |

“人提出计划”应区分目标、里程碑与资源约束，和具体实现计划。领导可以提出前者；Agent 负责把它细化为可执行、有依赖、有验收条件的工作项。人的最终验收不能被 Agent 自报完成代替。

## 与项目现状逐项对照

| 能力 | 当前代码已有 | 与用户设想的差距 |
| --- | --- | --- |
| 个人 Agent | `agent_core` 的内核、CLI、HTTP、个人面板、流式/异步执行、会话、计划和工作区 | 本次把逐题沟通接入个人 HTTP/UI；CLI 与外部 MCP 尚无该交互入口。个人服务仍主要使用共享 Key/本机访问，不是完整的人员身份系统 |
| 多主机执行 | Brain/Worker、角色与节点选择、注册/心跳、远程派发、任务事件、审批与预算预占 | 更接近执行调度控制台，仍经常需要人填写具体任务/角色/节点；尚不能等同于领导只管里程碑与验收的自治项目团队 |
| 多职责 Agent | executor、security-guard、advisor 等人设；Agent 内核支持子代理 | 有角色不等于有完整职责流程。需求分析、开发、测试、集成的责任人、输入/输出契约和返工流还需要贯通 |
| 多人及个人 Agent 归属 | 独立 collaboration 子系统有 User、ProjectMember、Agent.owner_user_id | 是“每人拥有个人 Agent”的基础，但不强制每人只能有一个，也没有把个人面板的身份与协作登录自动打通 |
| 项目职责授权 | `AgentProjectBinding` 包含 member_user_id、duty、persona_version、allowed_tools、workspace_ref、provider_ref；实例与节点分离 | 模型已接近目标，需要把授权与实际个人 Agent/真实执行器贯通，不能把声明的工具范围当作完整运行隔离证明 |
| 团队需求与验收 | 需求版本、指定评审人、验收项、计划、工作项、审核/退回、状态流转、审计 | 已有协议与业务状态基础，但不能据此宣称真实模型从分析到交付的完整闭环已完成 |
| 真实团队规划 | `PlanService.planner` 为可注入接口；应用默认创建 PlanService | 默认 `planner=None`，缺少生产规划器接线 |
| 真实团队执行 | 协作 Worker 有协议、租约、结果和产物上报 | 当前 CLI 的 runner 仅 none/fake，默认 none；旧 Worker 可真实执行，不代表团队 Worker 已接通真实 AgentKernel |
| 领导监察 | 任务状态、SSE、审计、用量和预算面板 | 需要进一步按需求/里程碑聚合交付证据、阻塞原因、返工、预计费用与偏差，降低领导逐条操作的负担 |
| 成本 | 旧编排预算账本、团队预算服务、单次 SDK 执行预算 | 仍为不同口径。本次个人沟通另有本项目预算账本，未把所有执行和辅助调用统一成项目总账 |
| 经验与改进 | 运行经验、记忆和本次独立纠正记录 | 完成不等于验收通过；待核实意见不能直接成为项目事实或团队共享经验。个人私有讨论不自动公开 |

## 本次已经调整的边界

1. 移除 Brain 的理解核验路由、派发/重派/审批答题检查、顾问触发接线以及编排台答题组件。正常编排继续使用原有安全、审批和预算机制。
2. 在个人 Agent 的 `/agent/understanding/*` 提供独立出题、逐题回答、讨论、显式推进/跳过、纠正参考与核查导出。
3. 个人面板在服务明确声明 `personal_understanding` 能力后显示入口。Worker 节点虽然复用同一份 HTML，但不声明此能力，也不接入这套学习门槛。
4. 个人同步、SSE、异步、长会话消息入口统一检查已触发的核验；普通请求没有触发时不要求答题。单纯切换传输方式不能绕过。
5. 存储按当前工作区隔离，切换项目不会复用旧核验；已核实纠正仅在同操作者和同资料 hash 下供后续独立偏差分析参考。
6. 旧编排核验记录保留，不自动合并到个人记录；兼容导入仅供历史审计，不会重新安装 Brain 核验路由。

本次没有实现全部三种模式的统一登录、团队真实规划器、团队真实执行器或统一项目预算。也没有把人员领导职责悄悄改成逐步编码操作。

## 建议的后续实施顺序

1. 明确产品模式与部署方式的独立配置；个人工作区、项目团队和机器列表分别展示。避免通过“本地/远程”猜测人的职责。
2. 优先贯通团队真实规划与执行：需求/验收版本 → 需求分析 Agent → 计划及预算确认 → 开发/测试/安全 Agent → 集成交付 → 人工验收或退回。
3. 建立个人 Agent 到团队项目的明确加入/退出和授权流程；私有会话保留私有，仅把授权的交付物、决定及证据投递给团队。
4. 将领导工作台聚焦计划、预算、风险、里程碑、验收；日常无争议的子任务与返工由 Agent 按政策推进。业务澄清与人工高风险审批仍可保留。
5. 在项目、阶段、工作项与执行尝试之间统一预算和费用，包括规划、评审、解释、重试等辅助调用；费用未知时保留待核对状态。
6. 只让验收认可或核实过的内容进入可信参考层，区分 AI 建议、人工决定、验证证据与最终项目事实。

验收重点应是：同一需求能在有预算、明确权限和验收条目的情况下，由真实职责 Agent 完成，并在失败、返工、取消、断连时留下可核查记录；领导不需要手工分发每一步，成员也不会互相读到未授权的个人会话。
