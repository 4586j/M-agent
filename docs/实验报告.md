# 多 Agent 编排框架 实验报告

## 1 背景及功能概要

### 1.1 背景

随着大模型 Agent 能力的增强，单个 Agent 独立承担复杂任务时暴露出三个突出问题：一是**职责混淆**，同一个 Agent 既做意图理解又做执行又做安全审查，能力边界模糊、难以控制；二是**安全失控**，具备写文件、执行命令能力的执行体若缺乏独立、强制的外部审查，极易在"无监督"状态下造成破坏（递归删除、凭证外发、越权访问等）；三是**扩展受限**，单进程 Agent 的算力与执行环境固定，无法将任务分发到多台主机并行处理。

基于上述背景，本项目设计并实现了一个**多 Agent 编排框架（orchestrator）**。其核心思想是"**职责分离 + 强制安全 + 可扩展执行**"：将一个复杂任务的完成过程拆分为三个角色清晰、能力受限的 Agent，由一个"大脑"统一编排，并在执行前后设置不可跳过的安全关卡。框架同时提供单机（V1）与跨主机（V2）两种部署形态，后者通过 HTTP + Agent SDK 将执行体分发到多台 worker 主机，实现算力横向扩展。

本实验的目标是：部署并运行该框架，验证三角色协同、安全关卡、跨主机派发与产物回传的完整链路，并据此分析其系统设计。

### 1.2 功能概要

框架对外提供以下功能：

**（1）三角色编排**
- **大脑（orchestrator）**：运行在主会话，负责意图澄清、边界探索、prompt 优化、任务拆解、派发、结果审核与共识记忆提炼，**不亲自执行业务任务**。
- **executor**：执行子 agent（默认 model=sonnet，拥有全部工具），完成大脑下发的子任务并产出代码/文件/结论。
- **security-guard**：只读安全检验 agent（默认 model=haiku，**仅** Read/Glob/Grep/WebFetch 四个只读工具），对指令与产物做安全裁决，返回 `pass`/`block`。

**（2）两种部署形态**
- **单机模式（local，V1）**：大脑在主会话用 Claude Code 子 agent（Agent 工具）直接派发，无需启动任何服务。
- **跨主机模式（remote，V2）**：executor 派发到远程 worker 主机（HTTP + Agent SDK），支持多 worker 并行；security-guard 始终留大脑本地。

**（3）七阶段工作流**：意图澄清 → 边界探索 → prompt 优化 → 任务拆解 → 安全关卡①（指令）→ 执行调度 → 结果审核 + 安全关卡②（产物）。

**（4）两层安全检验**：确定性正则规则引擎（默认 10 条规则）+ 可选 LLM 增强（haiku 只读会话补判"规则之外"的可疑情况，异常时优雅降级）。安全不通过时大脑**不自行放行**，停给用户三选一（放行/修改/放弃）。

**（5）共识记忆机制**：复用 Claude Code 内置记忆，但只有大脑/executor/security-guard 三方独立投票全 `pass` 才写入核心记忆，避免单点误写。

**（6）任务全生命周期管理**：任务状态机（pending → running → done/failed/lost/cancelled），JSON 持久化，支持取消、重派、按 worker/状态查询。

**（7）Web 控制面板**：Vite + React + TypeScript 实现的图形化界面，提供状态总览、节点管理、命令台三大视图，5 秒自动轮询。

## 2 系统设计

### 2.1 概要设计

#### 2.1.1 总体架构

框架采用"**大脑为中心，执行与审查分离**"的星型架构。V2 跨主机部署形态涉及两类主机：**大脑主机**与一台或多台 **worker 主机**，二者通过 HTTP 通信。

大脑主机上运行四类组件。**主会话**加载 orchestrator skill，是用户交互入口与编排中枢，通过 Bash 调用 dispatch_cli 桥脚本发起派发。**dispatch_cli** 仅作转发，将派发请求以 HTTP 方式提交到 brain_api 的 /dispatch 端点，本身不持有任何状态。**brain_api** 是大脑运行时的核心 HTTP 服务（FastAPI），集中承载注册、心跳、派发、查询、产物代理等接口，包括 /register、/heartbeat、/dispatch、/workers、/tasks、/proxy/artifact、/stats。**security-guard** 作为只读安全检验 agent 始终驻留大脑本地，由主会话通过 Agent 工具直接派发，不跨主机。

worker 主机上运行 worker_api（FastAPI 服务），对外提供 /task（接受任务）、/task/{id}（查询状态）、/artifact/{id}（回传产物文件）三个接口，内部委托给 AgentRunner 执行体；后者有 Fake（测试用，不调真实 SDK）与 Sdk（基于 claude-agent-sdk 加载 executor.md 起真实会话）两种实现。

两类主机之间形成三条数据通路。其一为**派发通路**：brain_api 的 RemoteDispatcher 选定 worker 后，向 `http://{worker_host}:{port}/task` 发起任务并轮询 /task/{id} 获取结果。其二为**注册与心跳通路**：worker 启动时主动向 brain_api 的 /register 注册自身地址，此后周期性发送 /heartbeat 保活。其三为**产物回传通路**：brain_api 经 /proxy/artifact 代理向 worker 的 /artifact/{id} 拉取文本类产物，供安全关卡②检验。其中 worker 注册时上报的 host 字段是大脑反向连接 worker 的依据，跨主机部署时必须填 worker 的真实局域网 IP，否则大脑无法回连拉取产物。

关键设计决策：**派发动作在 brain_api 进程内完成**（RemoteDispatcher 与 worker 注册状态同进程），`dispatch_cli` 仅作为主会话到 brain_api 的转发桥，避免注册状态与派发逻辑跨进程不一致。

#### 2.1.3 关键流程设计

**流程一：V2 远程任务派发**（[dispatcher.py](../workspace/agent/orchestrator/runtime/dispatcher.py) RemoteDispatcher）

```
dispatch(prompt)
  ├─ select_worker(role, strategy)          # round_robin / least_load
  ├─ 写 pending 任务记录
  ├─ POST {worker}/task {task_id, prompt}   # worker 立即返回 accepted
  ├─ 标记 running
  ├─ 轮询 GET {worker}/task/{id} (每 0.5s, 上限 1000 次)
  │     ├─ status=done   → 触发产物检验 → 更新记录 → 返回
  │     └─ status=failed → 更新记录 → 返回
  └─ 超时 → 标记 failed
```

worker 端采用**异步执行**：`POST /task` 起后台线程跑 runner，立即返回 `accepted`；`state` 先占位 `running` 供大脑轮询，完成或异常时覆盖（[worker_api.py:84](../worker/worker_api.py)）。这避免了长任务阻塞 HTTP 连接。

**流程二：两层安全检验**（[security_guard.py](../workspace/agent/orchestrator/runtime/security_guard.py)）

```
check_with_llm(content)
  ├─ rule_v = check(content)            # 正则规则引擎（确定性）
  │     ├─ 命中 block 规则 → 直接返回 block（省 LLM）
  │     ├─ 命中 warn 规则  → 返回 pass（reason 记录）
  │     └─ 无命中          → 返回 pass
  ├─ 若 rule_v=block → 直接返回（不调 LLM）
  ├─ 若 use_llm 且 rule pass → 调 haiku 只读会话补判
  │     ├─ LLM 不可用/异常 → 降级返回规则结果（graceful）
  │     └─ LLM 判 block    → 合并为 block（reason 标注 LLM 判断）
  └─ 否则返回规则结果
```

安全关卡在两处强制接入 brain_api 的 `/dispatch`：派发前检验**指令**（block 则不创建任务，返回 `status=blocked`）；派发拿到结果后检验**产物**（合并 output + 文本类 artifacts 内容，verdict 持久化到任务记录，产物 block 时任务仍 `done` 但前端显示橙色警告，不与 `failed` 混淆）。`force=true` 可跳过指令检验用于放行。

**流程三：共识记忆写入**

核心记忆复用 Claude Code 内置记忆文件，但写入受三方共识约束：大脑提炼候选条目 → 并行派三个独立投票子 agent（大脑/executor/security 视角，互不可见）→ 三票全 `pass` 才写入，任一 `block` 即丢弃。大脑是核心记忆的**唯一写入者**，executor 与 security-guard 只投票不写文件，从机制上杜绝误写。

**流程四：worker 注册与保活**

worker 启动时 `ORCH_AUTO_REGISTER=1`（默认）开启后台心跳线程：先向大脑 `/register` 注册（失败重试 3 次），再每 15s 发一次 `/heartbeat`。大脑注册表以 45s 为超时阈值剔除失联节点，`select_worker` 在轮询时跳过已失联的 worker。

#### 2.1.4 安全规则设计

默认规则集（[default.yaml](../workspace/agent/skills/orchestrator/security-rules/default.yaml)）覆盖五类风险，分 `block`（否决停给用户）与 `warn`（记录但放行）两级：

| 类别 | 规则示例 | 级别 |
|------|---------|------|
| 危险命令 | `rm -rf /`、强制推送主干、hard reset 远程 | block |
| 路径越界 | `../../`、访问 `/etc`、`C:\Windows` | block |
| 注入 | `eval()`/`exec()`、`shell=True`、SQL 拼接 | block / warn |
| 密钥泄露 | 硬编码 api_key/token/password | block |
| 数据外发 | curl/wget 携带凭证 | block |

规则支持用户覆盖（`overrides/user.yaml`，同 id 覆盖、新 id 追加），无需改框架代码即可定制安全策略。

#### 2.1.5 部署形态与配置体系

整个框架由**环境变量驱动配置**，关键变量如下：

| 变量 | 默认 | 说明 |
|------|------|------|
| `ORCH_MODE` | local | local 单机 / remote 跨主机 |
| `ORCH_BRAIN_HOST` | 127.0.0.1 | 大脑监听地址，跨主机设 0.0.0.0 |
| `ORCH_BRAIN_URL` | http://127.0.0.1:7000 | 大脑地址 |
| `ORCH_WORKER_ID` | worker-local | worker 唯一标识 |
| `ORCH_WORKER_HOST` | 127.0.0.1 | worker 监听/上报地址（跨主机须填真实 IP） |
| `ORCH_RUNNER` | fake | fake 测试 / sdk 真实执行 |
| `ORCH_PERMISSION_MODE` | bypassPermissions | sdk 执行权限模式 |
| `ORCH_SELECT_STRATEGY` | round_robin | worker 选择策略 |
| `ORCH_SECURITY_LLM` | 0 | security-guard LLM 增强开关 |

前端支持两种运行方式：开发模式（vite dev server 监听 5173，通过 proxy 转发 API 到大脑 7000）；生产模式（`npm run build` 产出 `web/dist`，由 brain_api 同源托管在 `/`，单端口提供服务）。

#### 2.1.6 运行验证

本实验中实际部署并验证了完整链路：

1. **启动三服务**：大脑（`ORCH_MODE=remote`，7000）、worker-A（`ORCH_RUNNER=fake`，8001，自动注册）、前端 dev server（5173）。三者均正常就绪，worker-A 注册成功并通过心跳保活。
2. **端到端派发测试**：经 `dispatch_cli` 派发"用一句话说明 1+1 等于几"，返回 `task-73712e42`，`status=done`，`product_verdict=pass`，确认"派发→执行→产物检验→回传"全链路打通。
3. **跨主机接入验证**：发现大脑原硬编码 `host="127.0.0.1"`（[brain_api.py:222](../workspace/agent/orchestrator/runtime/brain_api.py)）导致外部主机不可达。将其改造为可由 `ORCH_BRAIN_HOST` 环境变量控制（默认仍 127.0.0.1 保持向后兼容），重启大脑为 `0.0.0.0` 后，用本机局域网 IP `172.16.2.95:7000` 访问 `/stats` 返回 200，证明第二台主机已可接入。并据此整理出 worker-B 跨主机部署步骤（拷贝 worker 目录、装依赖、设置 `ORCH_BRAIN_URL` 与 `ORCH_WORKER_HOST` 为真实 IP、放行防火墙）。
4. **单元测试**：runtime 53 passed、worker 6 passed、security-rules 6 passed，验证核心逻辑正确性。

## 3 总结与体会

通过本次部署与验证，对多 Agent 编排框架的设计有以下几点体会：

**（1）职责物理隔离是安全可控的根基。** security-guard 仅拥有 Read/Glob/Grep/WebFetch 四个只读工具，从工具层面物理剥夺了其"改文件/执行命令/派发子 agent"的能力。这种"能力受限"比"靠 prompt 自律"可靠得多--即使 guard 的判断被绕过，它也无法造成任何破坏。同时大脑不自行放行安全否决、不亲自执行业务，三个角色互不直连、所有协作经大脑编排，形成了清晰的信任边界。

**（2）"规则 + LLM"两层检验兼顾确定性与覆盖面。** 纯规则引擎确定、同步、零外部依赖，但覆盖面有限；纯 LLM 判断灵活但不可控。框架用规则引擎兜底（命中 block 直接返回，省 LLM 调用），规则 pass 时再可选调 LLM 补判"规则之外"的可疑情况，且 LLM 不可用时优雅降级到规则结果。这种分层设计在安全性与成本间取得了平衡。

**（3）共识写入机制值得借鉴。** 核心记忆写入要求三方独立投票全 pass，从机制上防止了单点误写--executor 不会因执行偏差写错记忆，security 不会因漏判放过敏感信息。这种"多视角独立投票"思路可推广到任何需要高可信写入的场景。

**（4）环境变量驱动 + 同源托管简化部署。** 全部配置走环境变量、零配置文件，单机与跨主机仅需切换 `ORCH_MODE`；生产模式下 brain_api 同源托管前端 `web/dist`，一个进程同时提供 API 与界面，部署极简。但这也暴露了一个问题：本次实验发现大脑监听地址原硬编码 127.0.0.1，跨主机接入时必须改代码，说明"环境变量驱动"的覆盖还不彻底。改造为 `ORCH_BRAIN_HOST` 可控后，跨主机能力才真正可用。这提示我：**配置外置要彻底，任何硬编码的地址/端口都是扩展时的隐患**。

**（5）现存的局限与改进方向。** 其一，worker 的 `listen_host` 同时用作监听绑定地址与注册上报地址，跨主机且 worker 有多网卡时不便（理想是分离为 `advertise_host`）。其二，任务取消当前仅标记意图，无强保证。其三，TaskStore 与 WorkerRegistry 均为内存/JSON 文件，大脑重启会丢已注册 worker（worker 需重启重注册，本实验中已验证此行为）。其四，V2 假设内网可信，未做 TLS 与鉴权，上生产需补齐。后续可沿"接口化"方向将存储换为 Redis/DB、补 TLS 鉴权、实现 worker 监听/上报地址分离，进一步提升可用性与安全性。

总体而言，该框架通过"三角色分离 + 强制双安全关卡 + 共识记忆 + 可扩展执行"的设计，较好地解决了单 Agent 在职责、安全、扩展三方面的痛点，V1/V2 双形态兼顾了易用与可扩展，是一次结构清晰、安全意识强的多 Agent 系统设计实践。
