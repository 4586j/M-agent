# 多 Agent 编排系统 · 使用手册

> 重构后的**统一 Agent 内核**（`agent_core`）+ 四种入口形态 + 集群编排。
> 一套内核，单机与集群共用；CLI / HTTP / MCP / 本地执行四种接入方式按需选择。

---

## 概述

本系统以 `agent_core` 为**统一 Agent 执行内核**：把「人设（persona）加载、系统提示拼装、技能扫描、MCP 挂载、记忆工具注入、单发/多轮/流式执行、经验沉淀、规划与反思」收敛到一处实现。内核之上派生出四种入口形态——交互式 CLI、HTTP 服务、MCP 服务、集群本地执行器——它们共享同一份 `AgentConfig` 与 `AgentKernel`，因此单机自足运行与集群编排的行为一致、配置一致。当需要跨主机协同时，`brain`（大脑）+ `worker` 组成集群，通过 HTTP 注册/心跳/派发调度多台执行节点。

### 单机模式 vs 集群模式

| 维度 | 单机模式 | 集群模式 |
|------|----------|----------|
| 定位 | 一台机器上把 Agent 当工具用（CLI/HTTP/MCP），或 brain 进程内直接执行 | 跨主机协同，大脑调度多台 worker 执行 |
| 触发 | `agent_cli.py` / `agent_core.service` / `agent_core.mcp_agent_server` / brain + `ORCH_LOCAL_EXEC=1` | `ORCH_MODE=remote` 启动 brain + 多台 worker |
| 执行位置 | 本进程内 `AgentKernel.run_oneshot()` | 派发到远程 worker（HTTP + Agent SDK） |
| 记忆后端 | `memory_backend=local`（直连本地 store） | `memory_backend=remote`（经 brain HTTP API） |
| 安全检验 | 本地执行模式仍走 security-guard 产物裁决 | security-guard 常驻大脑本地，指令 + 产物双层检验 |
| 适用 | 个人开发、脚本/CI、把 agent 挂进别的 MCP 客户端 | 需要并发、隔离、多机的生产编排 |

## 升级注意事项（破坏性默认值变更）

以下默认值在近期版本发生变更，从旧版本升级或在新环境部署前务必逐条核对：

### 1. 鉴权默认收紧：未配 key 仅放行环回（auth）

- 旧行为：不配 `ORCH_API_KEY` 时 API 全开放。
- 新行为：**未配 key 时仅放行环回地址（127.0.0.1/::1）请求，非环回一律 403**；配置了 key 则所有非 public 请求须携带正确的 `X-API-Key` 头（或 `?api_key=` 查询参数）。
- 三条鉴权路径（详见 `docs/跨主机SDK部署手册.md` §3.2.1）：① 双侧配置 `ORCH_API_KEY`（Web 控制台在「状态总览 → 连接设置」填入）；② 临时 `ORCH_ALLOW_UNAUTHENTICATED=1` 全开放（仅受控环境）；③ 全链路环回。
- **反向代理场景**：经 nginx/frp 等代理后，brain 看到的请求来源是代理机而非环回，环回豁免失效，必须显式配 key，否则全站 403。

### 2. permission_mode 默认改为 default（无人值守必改）

- 旧行为：内核权限模式默认 `bypassPermissions`。
- 新行为：`agent_core` 内核默认 `default`（SDK 权限门控生效）——写文件/执行命令等需确认操作会**等待确认，无人值守派发会卡住**。
- 无人值守场景（brain 本地执行 `ORCH_LOCAL_EXEC=1`、单机 CLI/HTTP、经 brain 派发的单机执行）须显式设置：`AGENT_PERMISSION_MODE=bypassPermissions` 或 `ORCH_PERMISSION_MODE=bypassPermissions`。
- worker 侧 `ORCH_PERMISSION_MODE` 默认仍为 `bypassPermissions`（worker_config.py），跨主机部署无需改动。

### 3. security_llm 默认开启（每次派发多一次 LLM 调用）

- 旧行为：`ORCH_SECURITY_LLM` 默认 0（纯规则引擎）。
- 新行为：**默认开启**——security-guard 规则 pass 后再调 haiku 只读会话补判「规则之外」的可疑情况，需 brain 侧装 `claude-agent-sdk`，**每次派发多一次 LLM 调用**（成本/延迟）；SDK 缺失或调用异常自动降级回规则引擎，不影响主流程。
- 显式关闭：`ORCH_SECURITY_LLM=0`。

### 4. .env 自动加载（dotenv）

- 新行为：`load_agent_config` 启动时自动把项目根 `.env`（或 `AGENT_ENV_FILE` 指定文件）并入 `os.environ`，CLI / HTTP / MCP / worker / brain 各入口一致生效，无需每次手动 export。
- 规则：已存在的真实环境变量优先于文件值（不覆盖，可在 shell 里临时覆盖）；`AGENT_ENV_FILE` 指定路径优先于项目根 `.env`。

### 5. 配置迁移：~/.claude/settings.json → 项目根 .env

- 此前依赖 `~/.claude/settings.json` 的 `env` 字段（如 `ANTHROPIC_API_KEY`、模型配置）注入 Claude Code 子进程的部署，请把所需变量**迁移到项目根 `.env`**（或系统环境变量）。新版各入口统一从 `.env` + 真实环境变量装配配置，不再依赖 settings.json。

### 6. 依赖升级：claude-agent-sdk >= 0.2

- `agent_core/pyproject.toml` 与 `worker/requirements.txt` 均声明 `claude-agent-sdk>=0.2`；旧环境若装的是 0.1.x 旧版，执行 `pip install -U "claude-agent-sdk>=0.2"` 后再运行。

### 7. worker 人设走 `ORCH_WORKER_ROLE`；人设路径改 `ORCH_WORKER_PERSONA_DEF`

- worker 人设由 `ORCH_WORKER_ROLE`（默认 `executor`）决定，加载 `.claude/agents/{role}.md`。同机多节点各设不同 role 即可（见「单机多节点」）。
- 人设路径环境变量由 `ORCH_EXECUTOR_DEF` 改名为 `ORCH_WORKER_PERSONA_DEF`（**旧名保留兼容**，新配置请用新名）。

### 8. worker 默认挂载节点 Agent 面板（`ORCH_WORKER_PANEL=1`）

- 每个 worker 节点默认挂载与单机相同的 Agent 面板（`/panel`、`/agent/*`、`/agent/terminal` WS），即 **`http://host:port/` 直接可打开该节点控制台**（详见「集群模式 → 节点 Agent 面板」）。
- 无面板需求的节点可用 `ORCH_WORKER_PANEL=0` 关闭（不挂面板路由，`/panel` 返回 404）。
- 面板页 `/panel` 与 `/` 为 public 路径（无需 key 即可加载）；页面内全部 `/agent/*` 请求与终端 WS 仍受鉴权（`?api_key=` 为既有通道，浏览器凭 `localStorage.orch_api_key` 自动带参）。

## 快速开始

### 环境要求

- **Python ≥ 3.11**（`agent_core/pyproject.toml` 声明 `requires-python = ">=3.11"`）。
- 真实执行任务需要 `claude-agent-sdk`（内核延迟导入，仅查看 `--help` 无需安装）。
- HTTP 服务额外需要 `fastapi` + `uvicorn`；MCP 服务需要 `mcp`（项目已装 1.28.1）。

安装依赖：

```bash
# 方式 A：作为可编辑开发包安装（推荐，自动带上核心依赖）
pip install -e ./agent_core            # 核心：claude-agent-sdk / pyyaml / httpx
pip install -e "./agent_core[service]" # 追加 HTTP 服务依赖：fastapi / uvicorn
pip install -e "./agent_core[dev]"     # 追加测试依赖：pytest

# 方式 B：直接装依赖
pip install claude-agent-sdk pyyaml httpx fastapi uvicorn requests pytest
```

### 配置文件（.env，推荐）

不想每次启动都手动 `export` 环境变量？把配置写进项目根的 `.env` 文件即可——
`load_agent_config` 启动时自动读取（CLI / HTTP / worker / brain 各入口一致生效）。

```bash
# 1) 从模板创建（.env 已被 .gitignore 忽略，密钥不会提交）
cp .env.example .env          # bash
Copy-Item .env.example .env   # PowerShell

# 2) 编辑 .env，至少填入大模型 Key：ANTHROPIC_API_KEY=sk-ant-你的真实key
```

`.env` 最小示例：

```dotenv
# 大模型鉴权（必填）——claude-agent-sdk 靠它认证
ANTHROPIC_API_KEY=sk-ant-你的真实key
# 模型（可选，不设走 SDK 默认；也可用 --model 覆盖）
AGENT_MODEL=sonnet
```

规则与优先级：

- **发现顺序**：环境变量 `AGENT_ENV_FILE` 指定的文件 > 项目根 `.env`。
- **不覆盖**：已存在的真实环境变量优先于 `.env`（可在 shell 里临时覆盖文件值）。
- **命令行 > .env > 默认值**：如 `--model` 覆盖 `.env` 里的 `AGENT_MODEL`。
- 格式：`KEY=VALUE` 逐行；`#` 注释；值可加引号；允许行首 `export` 前缀。

> ⚠️ 别混淆两个 Key：`ANTHROPIC_API_KEY` 是大模型鉴权（SDK 直接读环境变量）；
> `AGENT_API_KEY` 只用于本地 HTTP 服务的 `X-API-Key` 校验与调用远程 brain。

### 30 秒上手

**① 单机 CLI（最简）**

```bash
python agent_cli.py                       # 进入交互 REPL（默认 executor 人设）
python agent_cli.py "统计 data.csv 的行数" # headless 单发，跑一轮即退出
```

**② 单机 HTTP 服务（最简）**

```bash
python -m agent_core.service --port 8000  # 启动后 POST /agent/run 即可执行

```

## 单机 Agent 模式

单机模式下有四种把内核跑起来的形态，全部共用 `AgentConfig` 与 `AgentKernel`。

### 交互式 CLI（agent_cli.py）

`agent_cli.py` 是单机模式下用户直接使用的 Agent 命令行，交互体验对标 Claude Code / Aider。底层委托 `AgentKernel` + `AgentSession` 实现**真正的多轮会话**（长连接客户端维持上下文），而非「query + resume 单发拼接」。

#### 完整命令行参数

| 参数 | 默认值 | 环境变量 | 说明 |
|------|--------|----------|------|
| `prompt`（位置参数，可选） | 无 | — | 单发任务；省略则进入交互 REPL |
| `--persona` | `executor` | `AGENT_PERSONA` | 人设名（executor / security-guard / orchestrator 等） |
| `--model` | 无（走 SDK 默认） | `AGENT_MODEL` | 覆盖模型（如 sonnet / haiku） |
| `--max-turns` | `50` | `AGENT_MAX_TURNS` | 单任务最大轮次，防失控循环烧 token |
| `--permission-mode` | `default` | `AGENT_PERMISSION_MODE` | 权限姿态（default / acceptEdits / bypassPermissions） |
| `--planning` | 关 | `AGENT_PLANNING_ENABLED` | 启用规划模式（先产出结构化计划再执行） |
| `--resume` | 关 | — | 续接最近一次会话（优先读 `.agent_sessions/` 目录，兼容旧 `.agent_session`） |
| `--rag` | 关 | `AGENT_RAG_ENABLED` | 启用 RAG 检索增强 |
| `--doctor` | 关 | — | 只读环境自检（SDK/鉴权/MCP/persona/.env），打印报告后退出 |

> 命令行参数优先级最高，覆盖环境变量与 `load_agent_config` 的默认值。
> `--planning` 的默认值与内核 `planning_enabled` 同读 `AGENT_PLANNING_ENABLED`，两端一致；命令行显式传 `--planning` 时以命令行为准。

其余会话级环境变量（经 `load_agent_config` 生效）：`ORCH_MCP_CONFIG`（挂载 MCP 工具）、`AGENT_MAX_THINKING_TOKENS`、`AGENT_TASK_BUDGET_USD` 等，详见「配置参考」。

#### Slash 命令清单

REPL 中以 `/` 开头的输入被当作命令，其余输入作为消息发给 Agent（长对话由内核自动压缩）。

| 命令 | 作用 |
|------|------|
| `/help` | 查看命令帮助 |
| `/new` | 开新会话（核心记忆保留，上下文清空，重连客户端） |
| `/sessions` | 列出历史会话（`.agent_sessions/` 多槽记录，含 persona/摘要/累计 cost） |
| `/switch <序号>` | 关闭当前会话，续接 `/sessions` 列表中选中的一项 |
| `/session` | 显示当前会话元数据（session_id/persona/首条消息/累计用量） |
| `/cost` | 显示本次会话累计 turns、cost 与 input/output tokens |
| `/usage` | 把本会话逐轮用量（时间/turns/cost/tokens）追加写入 `.agent_usage/<session_id>.jsonl` |
| `/tools` | 列出人设工具、技能、MCP 服务与记忆工具 |
| `/plan` | 显示当前规划进度（仅 `--planning` 模式下有意义） |
| `/memory` | 查看核心记忆清单；`/memory <名>` 按名查看正文；`/memory set <名>` 交互式写入一条 |
| `/retry` | 重发上一条失败消息（fatal 后提示可用） |
| `/interrupt` | 中断当前正在执行的一轮（在 turn 边界停下） |
| `/exit` `/quit` | 退出（会话已持久化，可 `--resume` 续连） |

#### 会话管理（多槽目录制）

- 每轮结束后，会话元数据（session_id、persona、时间戳、首条消息摘要、累计 turns/cost）写入 `.agent_sessions/<session_id>.json`，支持多个会话并存与切换。
- `--resume` 取最近一次会话续接；目录为空时兼容读取旧单文件 `.agent_session`。
- `/switch <序号>` 关闭当前会话后续接选中会话；续接失败（如 SDK 会话已失效）自动降级为开新会话，并明确告知历史上下文不可恢复。
- `/new` 关闭当前会话并重连一个全新会话，核心记忆仍然自动加载，但对话上下文清空。
- 规划模式下，CLI 的进度文件落在 `.agent_progress/`（每个 session 一个 JSON）。
- 任务失败时 CLI 会提示可用 `/retry` 重发上一条消息（内核侧错误已翻译为「原因 + 建议」人话）。

### HTTP 服务（agent_core.service）

把内核的 Agent 能力暴露为 HTTP API，供前端 / 脚本 / 其他进程调用。**不含** brain 注册/心跳逻辑——那是集群 worker 的职责；本服务只专注单机 Agent 执行。

#### 启动方式

```bash
# 方式 A：模块入口（支持 --host/--port/--persona/--reload）
python -m agent_core.service --port 8000 --persona executor

# 方式 B：uvicorn 直接引用模块级 app
uvicorn agent_core.service:app --host 127.0.0.1 --port 8000
```

| 参数 | 默认值 | 环境变量 |
|------|--------|----------|
| `--host` | `127.0.0.1` | `AGENT_HOST` |
| `--port` | `8000` | `AGENT_PORT` |
| `--persona` | `executor` | `AGENT_PERSONA` |
| `--reload` | 关 | — |

#### API 端点清单

| 方法 路径 | 请求体 | 响应体 |
|-----------|--------|--------|
| `GET /health` | — | `{status, service, checks:{total, ok, warn, fail, items[]}}`（doctor 自检汇总） |
| `POST /agent/run` | `{prompt, persona?, context_memory?, cwd?}` | `KernelResult` JSON：`{output, turns, is_error, usage, cost_usd, duration_ms, session_id, artifacts, cancelled, error_type}` |
| `POST /agent/run/stream` | 同上 | SSE（`text/event-stream`）：六类事件 `text_delta / tool_use / tool_result / budget_warning / result / error`，`data` 为 JSON，payload 超 2000 字符截断 |
| `POST /agent/run/async` | 同上 | `202 {run_id}`；后台执行，结果查 `GET /agent/run/{run_id}` |
| `GET /agent/run/{run_id}` | — | `{run_id, status: running/completed/failed/cancelled, result?}` |
| `DELETE /agent/run/{run_id}` | — | 触发协作式取消（`cancel_event`，turn 边界生效） |
| `POST /agent/session` | `{persona?, cwd?}` | `{session_id, persona, cwd}` |
| `POST /agent/session/{id}/message` | `{prompt, timeout?}` | `{output, turns, is_error, usage, cost_usd, duration_ms, session_id, error?, budget_warnings?}` |
| `POST /agent/session/{id}/message/stream` | 同上 | SSE：转发会话流式事件（同 run/stream 六类事件，含 budget_warning 预算软预警） |
| `POST /agent/session/{id}/interrupt` | — | `{status:"interrupt_requested", session_id}` |
| `DELETE /agent/session/{id}` | — | `{status:"closed", session_id}` |
| `GET /agent/sessions` | — | `{sessions[], count}`（活跃会话元数据） |
| `GET /agent/memory/core` | — | `{memories[{name,size,updated_at}], count, backend, dir}` |
| `GET /agent/memory/core/{name}` | — | `{name, content}`；不存在返回 404 |
| `PUT /agent/memory/core/{name}` | `{content}` | `{status:"written", name, path?}` |
| `GET /agent/tools?persona=` | — | `{persona, tools, skills[], mcp_servers[], memory_tools[]}` |
| `GET /agent/status` | — | `{active_sessions, default_persona, model, memory_backend, session_usage:{sessions,total_cost_usd,total_turns}, oneshot_usage:{runs,errors,total_cost_usd,total_turns}, total_cost_usd, total_turns}`（后两项旧字段兼容保留） |

> `cwd` 省略时，服务在内核 `work_dir`（默认 `<项目根>/.agent_work`）下开一个带随机后缀的独立子目录，避免多次调用产物互相污染。会话不存在返回 404；会话连接失败返回 500。
> 错误响应统一形状 `{"code","message","detail"}`（含 FastAPI 原生 HTTPException 也被转换为该形状）。`session message` 支持可选 `timeout`（秒）：单轮墙钟超时转为 error 事件而非悬挂。

### 本地执行模式（brain local + ORCH_LOCAL_EXEC）

让 brain 在 `local` 模式下也能真正执行任务：`/dispatch` 端点直接在 brain 进程内跑 `AgentKernel`，而非返回「未配置」。**单机 = brain_api(local) + LocalExecutorDispatcher + AgentKernel**。

#### 启动方式

```bash
cd workspace/agent/orchestrator/runtime
ORCH_LOCAL_EXEC=1 python -m brain_api      # ORCH_MODE 缺省即 local
```

装配逻辑（`brain_api._build_app`）：当 `cfg.mode == "local"` 且 `ORCH_LOCAL_EXEC ∈ {1, true, True}` 时，注入 `LocalExecutorDispatcher`，其内部持有一个 `AgentKernel`。派发流程为：写 `pending` 任务 → `run_oneshot()` 同步执行 → 产物 security-guard 裁决 → 更新 TaskStore（done/failed）→ 记经验 → 回写上下文记忆。`role` 即人设名（executor / security-guard）。

#### 与纯 CLI 的区别

| 维度 | 纯 CLI（agent_cli.py） | 本地执行模式（brain + ORCH_LOCAL_EXEC） |
|------|------------------------|------------------------------------------|
| 入口 | 终端直接对话 | HTTP `/dispatch`（可被 dispatch_cli / MCP / Web 调用） |
| 任务持久化 | 无（仅 `.agent_session`） | 写入 TaskStore（`.tasks/`），可查询/取消/重派 |
| 安全检验 | 无独立裁决 | 产物经 security-guard 规则引擎裁决，verdict 持久化 |
| 经验/记忆 | 内核自动记经验 | 记经验 + 回写任务上下文记忆（与集群一致） |
| 调度可见性 | 单会话 | 有 `/stats`、`/tasks`、`/workers` 等编排端点 |

#### MCP dispatch_task 可用性

本地执行模式下，`runtime/mcp_server.py`（已在 `.mcp.json` 注册为 `orchestrator`）的 `dispatch_task` / `dispatch_task_async` / `get_task_status` 等工具经 HTTP 打到 brain 的 `/dispatch`，因此**在单机上也能用 MCP 客户端派发任务并真正执行**——无需任何 worker。这为「单机当集群用」提供了平滑升级路径：日后加 worker、切 `ORCH_MODE=remote` 即可，客户端调用方式不变。

### 子代理派发开关 + AI 推荐/解释顾问

单机大脑（orch CLI / brain HTTP / Web 控制台）新增两项能力：**① 子代理派发可开关**（全局默认 + 每次请求覆盖），**② AI「推荐并解释」顾问**（预检建议 / 任务拆解 / 结果解释）。顾问**运行于完全独立的上下文**，绝不污染任务会话——这是本特性的核心红线。

#### 子代理派发开关

子代理派发指大脑把 orchestrator 人设的 `sub_agents`（`.claude/agents/*.md`）映射为 SDK `options.agents` 从而派生 executor / security-guard 等子 agent。开关分两级，均为**附加式**、默认保持既有行为：

| 层级 | 入口 | 取值 |
|------|------|------|
| 全局默认（env） | `ORCH_SUBAGENTS_ENABLED` / `AGENT_SUBAGENTS_ENABLED` | `1`（缺省，启用）/ `0`（禁用） |
| 每次请求覆盖 | orch CLI `--subagents` / `--no-subagents`；REPL `/subagents on\|off\|default`；`POST /dispatch` 请求体 `enable_subagents`；Web「启用子代理派发」三态 | `true` / `false` / 省略=跟随全局 |

- 单一闸在 `kernel._build_options`：仅当 `persona.sub_agents` 存在**且** `config.subagents_enabled` 为真时才挂 `agents`，覆盖全部执行入口。
- `enable_subagents=None`（省略）= 跟随全局 env；`true`/`false` = 本次请求强制覆盖（双向：全局关时也能单请求开）。
- **作用域说明**：每次请求覆盖对单机路径（orch CLI、brain 本地派发、`/recommend` auto-apply）生效；远程 worker 遵循**全局** env 闸（`worker/agent_runner.py` 经 `_build_options`），这是有意的范围界定，日后可通过在 worker 请求中转发该字段扩展。

#### AI 推荐/解释顾问

顾问是一个独立的 `AdvisorService`（`agent_core/advisor.py`），对一段任务文本给出「是否建议派发子代理 + 推荐角色 + 拆解计划 + 解释 + 风险」的严格 JSON 结论。四种模式：

| 模式 | 产出 |
|------|------|
| `pre_flight` | 是否派发 + 推荐角色 + 解释 + 风险 |
| `plan` | 经 PlanEngine 校验的任务拆解（可选，见 `ADVISOR_USE_PLAN_ENGINE`） |
| `explain` | 对**已完成产出**的解释/总结/风险（需传 `finished_output`） |
| `all`（缺省） | 以上并集 |

三个入口：

```bash
# ① orch CLI：headless 只建议不执行
python orch_cli.py --recommend "分析 workspace/data.csv 并汇总"
python orch_cli.py --recommend --advisor-mode plan "重构认证模块"
# REPL 内：/recommend <任务>   、   /subagents on|off|default
```

```bash
# ② brain HTTP API
curl -X POST http://127.0.0.1:7000/recommend \
     -H "Content-Type: application/json" \
     -d '{"task":"分析数据并汇总","mode":"all","auto_apply":false,"enable_subagents":null}'
# 响应：{status, recommendation:{should_dispatch,roles,plan,explanation,risks}, auto_applied, dispatched:[]}
```

③ Web 控制台「指令」页：「推荐并解释」按钮渲染建议面板（是否派发徽标 / 角色 / 计划 / 解释 / 风险），并含「启用子代理派发」「自动执行推荐」两个开关。

**执行姿态**：默认**仅建议**（advisory）——顾问只输出建议，由人再决定是否派发。开启 auto-apply（`ORCH_/AGENT_ADVISOR_AUTO_APPLY=1` 或请求体 `auto_apply:true` 或 CLI `--auto-apply`）后，若 `should_dispatch` 为真则自动派发**首要推荐角色**（`roles[0]`，缺省 `executor`）。

> **auto-apply 绝不绕过安全关卡**：自动派发复用既有 `/dispatch` 管线，仍先过 `security_check`（规则 + 可选 LLM）与审批；被拦截的指令返回 `dispatched:[{status:"blocked"}]` 而不执行。

#### 相关环境变量

| 变量（`ORCH_` / `AGENT_` 前缀皆可） | 缺省 | 说明 |
|------|------|------|
| `SUBAGENTS_ENABLED` | `1` | 子代理派发全局闸 |
| `ADVISOR_ENABLED` | `1` | 是否启用顾问端点/命令 |
| `ADVISOR_AUTO_APPLY` | 空（=关） | 顾问建议后是否自动派发（默认仅建议） |
| `ADVISOR_MODEL` | 空 | 顾问专用模型（空=跟随 `MODEL`） |
| `ADVISOR_WORK_DIR` | 空 | 顾问隔离工作目录（空=派生 `<work_dir>/.advisor_work`） |
| `ADVISOR_USE_PLAN_ENGINE` | 空（=关） | `plan`/`all` 模式是否复用 PlanEngine 产出校验过的拆解 |

#### 隔离保证（核心红线）

顾问是一次**独立的 `AgentKernel.run_oneshot` 调用**，与任何任务零交叉污染：

- **全新会话**：`run_oneshot(resume=False)`（不传 `resume_session_id`）——新建 SDK 会话，绝不复用任务会话。
- **独立一次性 cwd**：`<advisor_work_dir>/adv-<uuid8>`（默认 `<work_dir>/.advisor_work`），绝不复用任务的 `base/task_id` 目录。
- **不读经验**：顾问路径传 `context_memory=""`，从不调用 `enrich_experience`。
- **不写经验**：`run_oneshot(record_experience=False)`，且隔离配置再关一次 `auto_record_experience`。
- **不回写记忆**：AdvisorService 从不调用 `write_result_note` / memory 写入。
- **只读输入**：顾问只拿到任务文本（explain 模式另加已完成产出），不获得任务累积的记忆/经验；其人设 `.claude/agents/advisor.md` 工具收窄为只读（Read/Glob/Grep/WebFetch），无写入/执行/派发工具。
- **不绕过守卫**：auto-apply 复用既有 `/dispatch` 管线（`security_check` + 审批），推荐无法偷渡被拦截的指令。

> 核心记忆以**只读**方式注入顾问自身的系统提示属于共享大脑知识（读，不写），允许；顾问无法回写。

### 结果翻译（思考英文 / 结果中文）

单机大脑新增**结果翻译**能力：模型的思考过程保持英文（不干预），仅把**最终结果**翻译成目标语言（缺省简体中文）。翻译复用顾问同款**完全独立上下文**——绝不污染任务会话/记忆/经验，这是本特性的核心红线。

#### 触发方式（自动 + 按需，均附加式、默认关）

| 方式 | 入口 | 说明 |
|------|------|------|
| 自动翻译 | env `RESULT_TRANSLATE_ENABLED=1` | 在 `kernel.run_oneshot` 结果边界统一翻译（覆盖单机 CLI 派发 / brain 本地派发 / worker）；默认**关** |
| 按需·CLI | REPL `/translate <文本>` | 把任意结果文本翻成中文（独立上下文） |
| 按需·HTTP | `POST /translate` | `{text, target_lang?}` → `{status, translation}` |
| 按需·Web | 「指令」页「翻译成中文」按钮 | 结果面板出现后一键翻译并渲染译文面板 |

- **统一作用域**：自动翻译只挂在 `run_oneshot` 的结果边界一处，翻译发生在**记录经验与反思之后**——存下的经验/反思始终是模型真实的英文产出，仅返回给用户的 `result.output` 被替换为译文。
- **原文保留**：英文原文存于 `result.meta["original_output"]`，翻译状态存于 `result.meta["translated"]`（`changed` / `skipped` / `error`）。
- **思考不翻译**：`stream()` 流式过程与 orch CLI 交互轮（直连 `sdk.query`）不自动翻译；CLI 用 `/translate` 按需翻译。
- **已中文跳过**：目标语言为 `zh` 且文本 CJK 占比 ≥ 50% 时跳过再翻译（`skipped="already_target_lang"`），省成本。

#### 模型选择（回退链）

翻译模型按 `translate_model` → `advisor_model` → `model` 回退：优先用专用翻译模型，未配则复用「推荐/解释」顾问模型，再未配则跟随主模型。

```bash
# ① orch CLI（REPL 内按需翻译）
/translate Done: 42 rows, 3 errors

# ② brain HTTP API
curl -X POST http://127.0.0.1:7000/translate \
     -H "Content-Type: application/json" \
     -d '{"text":"Done: 42 rows","target_lang":"zh"}'
# 响应：{status:"ok", translation:{translated,target_lang,changed,skipped?,error?}}
```

③ Web 控制台「指令」页：结果出现后点「翻译成中文」，译文面板渲染中文结果（含错误/跳过降级与隔离提示）。

#### 相关环境变量

| 变量（`ORCH_` / `AGENT_` 前缀皆可） | 缺省 | 说明 |
|------|------|------|
| `RESULT_TRANSLATE_ENABLED` | 空（=关） | 结果边界自动翻译全局闸 |
| `TRANSLATE_MODEL` | 空 | 翻译专用模型（空=回退 `ADVISOR_MODEL`→`MODEL`） |
| `TRANSLATE_TARGET_LANG` | `zh` | 目标语言（zh / en / ja / ko / zh-TW） |
| `TRANSLATE_WORK_DIR` | 空 | 翻译隔离工作目录（空=派生 `<work_dir>/.translate_work`） |

#### 隔离保证（核心红线）

翻译是一次**独立的 `AgentKernel.run_oneshot` 调用**（`TranslatorService`，`agent_core/translator.py`），与顾问同款、与任务零交叉污染：

- **全新会话**：`run_oneshot(resume=False)`——新建 SDK 会话，绝不复用任务会话。
- **独立一次性 cwd**：`<translate_work_dir>/tr-<uuid8>`（默认 `<work_dir>/.translate_work`）。
- **不读经验**：翻译路径传 `context_memory=""`，从不调用 `enrich_experience`。
- **不写经验**：`run_oneshot(record_experience=False)`，隔离配置再关一次 `auto_record_experience`。
- **不回写记忆**：TranslatorService 从不调用 memory 写入。
- **防递归**：翻译自身的隔离配置强制 `result_translate_enabled=False`（译文不会再被翻译）；顾问隔离配置同样置 `result_translate_enabled=False`（顾问的严格 JSON 结论绝不被翻译）。

## 集群模式

### 架构

```
大脑主机                          worker 主机（可多台）
┌─────────────────────┐          ┌──────────────────┐
│ brain_api (:7000)    │          │ worker_api (:8000+)│
│  /register /heartbeat│◀─注册+心跳│  /task /task/{id}  │
│  /dispatch           │─────────▶│  /artifact/{id}    │
│  /workers /tasks     │  HTTP     │                    │
│  /stats /memory/*    │          │ AgentRunner        │
│  RemoteDispatcher    │◀─结果回传 │  Fake / Sdk        │
│  security-guard(本地) │          │  (claude-agent-sdk)│
│  Web 控制台(同源托管)  │          │                    │
└─────────────────────┘          └──────────────────┘
```

- **brain（大脑）**：负责注册/心跳/派发/记忆/安全检验，`RemoteDispatcher` 与 worker 注册状态同进程。
- **worker**：接受任务、执行（Fake 或真实 SDK）、回传产物；主动向 brain 注册并定期心跳。
- **security-guard 始终在大脑本地**（不跨主机），对指令与产物做检验。

### 启动 brain

```bash
cd workspace/agent/orchestrator/runtime
export ORCH_MODE=remote
python -m brain_api                 # 监听 http://127.0.0.1:7000
# 跨主机对外：ORCH_BRAIN_HOST=0.0.0.0 python -m brain_api
```

### 启动 worker

```bash
cd worker
export ORCH_WORKER_ID=worker-A
export ORCH_WORKER_PORT=8001
export ORCH_RUNNER=fake             # fake 验证链路 / sdk 真实执行
python -m worker_api                # ORCH_AUTO_REGISTER=1 时自动注册 + 心跳
```

使用真实 SDK 执行（消耗 API 调用）：

```bash

export ORCH_WORKER_PERSONA_DEF=.claude/agents/executor.md   # 旧名 ORCH_EXECUTOR_DEF 等价可用
python -m worker_api
```

手动注册 / 派发（不经自动注册时）：

```bash
# 注册 worker
curl -X POST http://127.0.0.1:7000/register \
     -H "Content-Type: application/json" \
     -d '{"worker_id":"worker-A","role":"executor","host":"127.0.0.1","port":8001,"capabilities":{}}'

# 派发任务
curl -X POST http://127.0.0.1:7000/dispatch \
     -H "Content-Type: application/json" \
     -d '{"prompt":"统计 CSV 行数","role":"executor"}'

# 定点派发：指定目标节点（自动按 role 轮询以外的最精确控制）
curl -X POST http://127.0.0.1:7000/dispatch \
     -H "Content-Type: application/json" \
     -d '{"prompt":"统计 CSV 行数","worker_id":"worker-A"}'
```

> **定点派发语义**：`worker_id` 非空时按 ID 精确寻址（不再按 role 轮询）。节点从未注册 / 心跳超时 → 任务直接 `failed`，不静默回退。定点时 `role` 由节点真实 role 决定（任务记录的 role 是节点的实际 role，成本/经验聚合以此为准）。非法 id（含特殊字符）→ 400。

### 单机多节点：一机 N 个不同人设 worker

一台机器即可跑多个不同人设的节点（`ORCH_WORKER_ROLE` 决定人设，人设文件走 `.claude/agents/{role}.md`）：

```bash
# 大脑
cd workspace/agent/orchestrator/runtime
ORCH_MODE=remote python -m brain_api            # :7000

# 同机三个不同人设的节点（分别开终端）
cd worker
ORCH_WORKER_ID=worker-a ORCH_WORKER_ROLE=executor        ORCH_WORKER_PORT=8001 python -m worker_api
ORCH_WORKER_ID=worker-b ORCH_WORKER_ROLE=executor        ORCH_WORKER_PORT=8002 python -m worker_api
ORCH_WORKER_ID=worker-g ORCH_WORKER_ROLE=security-guard  ORCH_WORKER_PORT=8003 python -m worker_api
```

- 不传 `worker_id` 时按 role 轮询负载均衡（executor 请求落在 worker-a/b 之一）。
- 传 `worker_id` 时精确打击目标节点；wait 审批通过的派发会**继承 pin**，重派（redispatch）也继承（`meta.pinned` 为判别位）。
- 节点掉线时定点派发报错并列出当前活跃节点，产物 `error` 含「节点心跳超时」。
- 面板 `/nodes` 可对任意节点点「派发到此节点」；`/command` 的「目标节点」下拉可定点（选中后自动回填真实 role，role 输入随之禁用）。

### 节点 Agent 面板（点击节点进入该节点的 Web 面板）

每个编排 worker 节点内部跑的就是与单机 Agent 面板同一套 `agent_core.kernel.AgentKernel`。自 `ORCH_WORKER_PANEL` 起默认开启，节点直接托管一个**单 agent 控制台**：

```bash

http://127.0.0.1:8001/        # → 302 到 /panel，该节点自己的 Agent 面板
```

**能力**（完整单 agent 面板，与 `agent_core.service` 契约一致）：
- 流式运行 / 规划引擎分步执行、历史运行回放、产物预览、工作区切换。
- 内嵌终端（WebSocket）：`cd` 保持会话目录；越界访问先回 `confirm` 帧、授权后才执行。
- 同节点上与 brain 派发的 `/task` 执行**并行无串扰**——面板 run 与派发 run 各自 new kernel（同一 `build_worker_kernel` 配方，人设/权限/预算/经验库一致）。

**编排面板入口**（`#/nodes`「节点管理」）：

- 面板页 `/panel`、`/` 为 **public**（无需 key）；`/agent/*` 与终端 WS 保持既有鉴权——未配 key 仅环回直通，配 key 时页面 fetch 与终端均凭浏览器 `localStorage.orch_api_key` 自动带 `?api_key=`（连接管理器会自动写入该键，单机部署无需配置）。
- **跨主机暴露须受控网络**：面板带内嵌终端 = 该节点任意命令执行能力。跨主机部署请配置 `ORCH_API_KEY`（循环安全），或经内网/VPN 访问。

#### 多 brain 连接切换

顶栏 🔑 打开连接管理器，可保存多个大脑（名称 + 地址 + API Key）并切换：

- 连接存 `localStorage.orch_connections`（活动连接 id 在 `orch_active_connection`）；首次打开从旧 `orch_api_key` 播种默认连接，**单 brain 部署零配置**。
- **地址留空 = 相对路径**（dev 走 vite 代理 / prod 同源直调，行为与旧版一致）。多 brain 用绝对地址，如 `http://127.0.0.1:7001`。
- 切换连接后全部视图（总览/节点/任务/命令台…）自动跟随新 brain 重拉，无需刷新页面；SSE 任务事件流同步重订阅。
- 「测试连接」区分 200（正常）/ 401（Key 错）/ 403（可达但被拒）/ 网络不可达。

**多 brain 部署要点：**
1. 跨源时把面板 origin 加进**每个 brain** 的 `ORCH_CORS_ORIGINS`（默认 `http://localhost:5173`）；漏配的表现是浏览器跨域预检失败（不是 401）。
2. 非回环 brain 未配 `ORCH_API_KEY` 会被 `auth` 拒（403 设计行为）——连接须带 Key。
3. **dev 模式的坑**：`baseUrl: ''` 的相对路径在 dev 下不是「面板同源」，是被 vite 代理到 `vite.config.ts` 里单一 `ORCH_BRAIN_URL`。多 brain 请用绝对地址。

brain 启动时向上逐级查找 `web/dist`，找到即托管在 `/`；可用 `ORCH_WEB_DIST` 指定绝对路径。

## 可观测性（阶段三）

### trace_id 链路追踪

任务创建（`/dispatch`、`/dispatch/async`、定时派发）时由 brain 生成短格式 `trace_id`（`trc-` + uuid 截断），存入 TaskRecord 并随派发 payload 下发 worker；worker 日志携带该 ID，结果 callback 时作为顶层字段回传。brain 侧 dispatcher / async_dispatcher / task_scheduler / retry_manager 的关键日志（派发、状态迁移、轮询、重试、终态）统一带 `[trace=trc-xxxx]` 前缀，可按前缀 grep 关联全链路：

```bash
# worker / brain 日志中按 trace 关联一次派发的完整生命周期
grep "trc-1a2b3c4d5e6f" brain.log worker.log
```

旧任务文件缺 `trace_id` / `meta` 字段时兼容读取为 null / 空 dict，无需迁移。

### worker 执行元数据（meta）

worker 执行完成后将 `usage`（token 明细）、`cost_usd`、`num_turns`、`model` 等 meta 随 callback 回传；brain 在任务终态化时合并写入 TaskRecord（callback 同名字段以 worker 为准），并经 `GET /tasks/{id}` 与 `GET /tasks` 原样透出。`eval/run_eval.py` 按 `meta.usage / meta.cost_usd / meta.num_turns` 提取，透出后自动生效。

### SSE 实时事件流

```bash
# 订阅任务事件流（EventSource / curl 均可）
curl -N http://127.0.0.1:7000/tasks/{task_id}/events
```

- 事件类型：`status`（状态迁移 / 轮询进展，首帧为快照）、`callback`（worker 回调到达，摘要截断 2000 字符）、`done`（终态，服务端发送后关闭流）。
- `data` 为 JSON：`task_id / trace_id / state / timestamp`（+ `summary` / `snapshot`）。
- 每 15s 发送 keepalive 注释帧防止代理断连；订阅队列满（100 条）时丢弃最旧事件。
- 鉴权与其它端点一致（`X-API-Key` 头）；因 EventSource 无法携带自定义 header，额外接受 `?api_key=` 查询参数。

Web 控制台任务详情弹窗自动订阅该事件流：实时展示状态变化与事件时间线，`EventSource` 失败时自动降级为 5s 轮询（弹窗顶部徽标指示「● 实时 / ○ 已降级轮询 / 已结束」）。

### 成本聚合（/stats.cost）

`GET /stats` 附带 `cost` 字段，从 TaskRecord.meta 聚合 token 与成本：

- `total`：全量累计；`by_day`：近 7 天按日（按 updated_at 归日）；`by_role` / `by_model`：按角色与模型全量聚合。
- 每个桶含 `tasks`（任务数）与 `tokens` / `cost_usd`（无数据时为 null）。

Web 控制台「状态总览」页据此渲染成本看板：近 7 天按日条形 + 按模型占比列表。

## Agent 面板（单机 Agent 运行实况）

类似 ZCode 的深色三栏面板，实时展示单机 Agent 的**思考过程、执行的命令、工具/skill/MCP

### 启动与访问

```bash
# 本地默认（模型/权限沿用 agent_core 配置）
python -m agent_core.service --port 8100
# 浏览器打开
http://127.0.0.1:8100/panel          # 或 http://127.0.0.1:8100/ （自动跳转）

AGENT_PERMISSION_MODE=bypassPermissions python -m agent_core.service --port 8100
```

### 三栏布局

| 栏 | 内容 |
|---|---|
| 左 | 运行历史（`/agent/runs`，状态徽标）+「+ 新任务」；点击历史条目进入**回放模式** |

### 内嵌终端（WebSocket）

面板中栏「⌨ 终端」标签提供可直接操作的终端，支持真实命令执行、cd 保持会话目录、
命令历史（↑↓）、Ctrl+C 中断、Ctrl+L 清屏：

- **端点**：`WS /agent/terminal`（鉴权与 HTTP 同口径：`AGENT_API_KEY` 或仅环回；
  带 key 时经 `?api_key=` 传入）
- **协议**：客户端发 `{"type":"run","cmd":"dir"}` / `{"type":"interrupt"}` /
  `{"type":"ping"}`；服务端回 `ready`（cwd/shell）/ `output`（流式）/
  `done`（退出码 + 新 cwd）/ `error`
- **实现**：每条命令一个子进程（`shell=True`，Windows 加 CREATE_NO_WINDOW），
  `cd` 特判更新会话 cwd（支持 `/d` 跨盘、`~`、相对路径、引号）；输出经线程读管道
  流式回推，不阻塞事件循环；有命令在执行时拒绝并发新命令
- **配置**：`AGENT_TERMINAL_SHELL` 覆盖默认 shell（Windows 默认 cmd.exe，
  类 Unix 取 $SHELL）
- **安全**：终端等于任意命令执行能力，默认仅环回可连；跨主机暴露时必须配
  `AGENT_API_KEY`，并建议置于受控网络

### 工作区边界（agent 默认操作范围）

面板顶栏「📁 工作区」显示并可切换当前工作区；**agent 的任务产物与终端默认 cwd 都限定
在工作区内，访问工作区外需要用户显式授权**：

- **端点**：`GET /agent/workspace`（当前工作区）、`PUT /agent/workspace`（切换，须为已存在目录）
- **配置**：`AGENT_WORKSPACE` 环境变量指定初始工作区（缺省用 `project_root`）
- **任务目录**：任务工作目录固定在 `<工作区>/.agent_work/<run-id>/`；请求显式传入
  工作区外的 `cwd` 直接 400 拒绝（HTTP 无交互确认通道）
- **终端越界确认**：`cd` 到工作区外、或命令中出现工作区外的绝对路径时，终端先回
  `confirm` 帧；面板弹出授权框，用户可选「拒绝 / 允许一次 / 本次会话允许」
  （会话级授权仅在当前 WS 连接内有效，断开即恢复严格模式）
- **检测口径**：识别 Windows 盘符路径与类 Unix 绝对路径；宁可多问一次，不放过越界
  写入；授权粒度取越界路径本身（文件取其父目录）

### 事件模型与端点

面板消费的事件来自内核 `AgentEvent`（v1.1 新增 `thinking`/`thinking_delta`/`plan_update`）：

- **实时**：非规划任务走 `POST /agent/run/stream`（SSE，逐事件推送）；勾选「规划引擎」则走
  `POST /agent/run/async` + 轮询 `/agent/run/{id}/events`（计划步骤实时可见）
- **持久化**：每次 run 全量事件落 `<work_dir>/runs/<run_id>.jsonl`（不截断，展示层截断），
  meta sidecar 记 cwd/prompt/status
- **回放**：`GET /agent/run/{run_id}/events` 按 seq 重放；面板左栏点击历史条目即回放
- **产物**：`GET /agent/artifact/{run_id}?path=` 只读回传该 run 工作目录内文件（防路径穿越）
- **trace**：`GET /agent/trace/{run_id}`（流式路径无 trace 树，返回终态统计说明）

配套修复：流式 run 现在会写入 `/agent/history`（此前只有同步 `/agent/run` 入历史）。

## 能力增强

内核内置三项可开关的增强能力：规划模式、经验 RAG、自我反思。它们默认关闭，失败均静默降级、不拖垮主流程。

### 规划模式（--planning）

**工作原理**：借鉴 Plan-then-Execute。启用后，`build_planning_prompt` 在原始 prompt 前注入指令，要求 Agent 先以 JSON 产出结构化计划（`{goal, steps[{id, action, depends_on}], risks}`），再按步骤顺序执行。内核/CLI 用 `parse_plan_from_output` 从输出中解析计划（兼容纯 JSON、```json 围栏、混在自然语言中的 JSON），交由 `PlanningManager` 持久化。

启用方式：
- CLI：`python agent_cli.py --planning`（默认值读 `AGENT_PLANNING_ENABLED`）
- 内核配置：`AGENT_PLANNING_ENABLED=1`（对应 `AgentConfig.planning_enabled`，作用于 `run_oneshot`）

**进度文件**：`PlanningManager` 把每个 session 的计划写成一个 JSON。
- CLI 落地目录：`.agent_progress/<session>.json`
- 内核 `run_oneshot` 后处理落地目录：`<项目根>/.orch_progress/<session>.json`

计划含步骤状态（pending / in_progress / done / failed）与依赖，可跨轮次/重启恢复。

**`/plan` 命令**：REPL 中查看当前计划的人类可读进度视图，每步用状态标记（`[✓]` 完成、`[→]` 进行中、`[✗]` 失败、`[ ]` 待做，附依赖），并列出目标与风险。

```text
你> /plan
当前计划：
  目标：重构登录模块
  步骤：
    [✓] 1. 梳理现有调用链
    [→] 2. 抽取统一入口 (进行中)
    [ ] 3. 补单元测试 (待做，依赖: 2)
  风险：旧接口存在隐式依赖
```

### 经验 RAG（--rag）

**工作原理**：启用后，内核在把 prompt 发给 Agent 前（`run_oneshot`、`stream` 与 `AgentSession.send` 三条路径统一），用 `ExperienceStore.search(prompt, successful_only=True, limit=3)` 检索相似历史**成功**经验，拼成「[历史经验参考]」块（含任务摘要与产出摘要）注入 prompt 前。经验块限幅 3000 字符，防噪声注入撑爆上下文。检索失败或无相似经验时静默回退到原 prompt。

> RAG 逻辑已下沉至内核（`AgentKernel.rag_enrich`）：CLI、HTTP、MCP 三种入口同等受益，关闭 `AGENT_RAG_ENABLED` 时行为与未开启完全一致（不注入任何经验块）。

启用方式：CLI `--rag`（或 `AGENT_RAG_ENABLED=1`，对应 `AgentConfig.rag_enabled`）。

**何时启用**：当任务与历史任务高度相似、希望复用前人做法与踩坑记录时（如反复处理同类数据、重复的代码模式）。全新领域或一次性任务无需开启，避免无谓检索开销。

> RAG 依赖 `runtime` 的 `ExperienceStore`，会延迟把 runtime 目录加入 `sys.path`；经验库目录由 `AGENT_EXPERIENCE_STORE_DIR` 控制（默认 `runtime/.experiences`）。

### 自我反思（AGENT_REFLECTION_ENABLED）

**工作原理**：`AgentConfig.reflection_enabled` 为真且任务**未报错、未取消**时，`run_oneshot` 收尾会用同一 persona 额外跑一轮轻量单轮查询（`max_turns=1`），让 Agent 用 `REFLECTION_PROMPT` 自评产出质量，输出 `{complete, quality(high|medium|low), issues[], suggestions[]}`。反思输入限幅 4000 字符。反思文本随后写入任务上下文记忆（`memory_context_dir/<session_id>/reflection.md`）。任何异常静默返回 None，不影响任务结果。

启用方式：环境变量 `AGENT_REFLECTION_ENABLED=1`。

### 输出质量守卫（AGENT_OUTPUT_GUARD_ENABLED）

**工作原理**：内核在普通单轮执行（`run_oneshot`）产出结果后，用 `agent_core/output_guard.py` 的 `detect_degenerate` 对文本输出做纯规则检测（零依赖、中文友好、判定保守——宁可漏判不可误伤）：

| 规则 | 默认阈值 | 信号强度 |
|------|---------|---------|
| 字符级重复：同一字母/数字/CJK 字符连续出现（`=-_#~*` 等装饰字符不计入） | 60 次 | 强 |
| n-gram 重复率：前 5 个 4-gram 覆盖率（中文按字/英文按词） | 40% | 强（可单独触发退化） |
| 乱码特征：控制字符/私有区占比（排除换行制表符，emoji/中文不受影响） | 30% | 强 |
| 重复行循环：同一行（≥15 字符）重复 ≥8 次**且**占输出字数过半（≥50%） | 8 次 / 50% | 强 |
| 长度异常：长 prompt（>100 字）换来极短输出（<10 字且非「好的/完成」类短答案） | —— | 弱（仅 warn） |

检测前会剥离 ``` 围栏内的代码文本（只参与字符重复与乱码两条规则），代码骨架天然重复不再误判 n-gram 与重复行规则。

**兜底闸门与三级兜底**（默认开启）：单条强规则（n-gram 除外）命中只降级为 warn（score 0.9，不触发重试）——需 ≥2 条独立强规则同时命中、或 n-gram（复读机特征）命中才判退化。判退化后自动重试，最多 `output_guard_max_retries`（默认 1）次——第 1 次重试在用户消息**末尾**追加纠偏提示（稳定前缀不动，保住 prompt caching）；第 2 次重试若配置了 `AGENT_FALLBACK_MODEL` 且与当前模型不同则换模型再试。重试成功则正常返回并在 `meta` 记 `degenerate_recovered=true` 与尝试次数；耗尽仍退化则熔断：`is_error=True`、`error_type="degenerate_output"`，保留最后一次原始输出并在 `meta["degenerate"]` 记录详情（attempts/reasons/models_tried），经验沉淀按失败口径处理，绝不谎报成功。各次尝试的 turns/cost/duration 全部累加进最终结果。

**任务级预算守卫**：每次重试前检查本任务累计花费（跨轮聚合），已达 `task_budget_usd` 的 80% 时不再重试，按退化口径收场并在 `meta["degenerate"]` 记 `budget_guard_stop=true`（重试轮各自得完整 per-query 预算，不设闸门最坏 3× 预算放大）。

**多轮会话路径**（`AgentSession.send`）只做轻量检测：检出时在该轮 `result` 事件的 data 附 `degenerate` 标记（SSE/CLI 可见），本轮经验按失败口径沉淀；不做自动重试（多轮上下文由用户接管），异常输出不从 SDK 会话历史中删除（SDK 无此能力）。

**配置项**：`AGENT_OUTPUT_GUARD_ENABLED`（默认 true）、`AGENT_OUTPUT_GUARD_MAX_RETRIES`（默认 1）、`AGENT_FALLBACK_MODEL`（默认空）。检测仅针对文本输出，tool 调用密集而无文本的轮次自动跳过；Plan-Execute 模式的摘要输出为模板文本且引擎自带步骤级重试，不走此兜底。

**观测**：集群模式下退化标记经 worker 透传入 `TaskRecord.meta`，`GET /stats` 的 `quality` 键按 model 聚合退化任务数与比率（`{"by_model": {model: {"tasks": n, "degenerate": n, "rate": x}}}`，model 缺失的任务归入空键）。

**升级注意事项**（检测规则保守化后）：

- 守卫默认开启，无需配置即生效。集群模式下 worker 同样读取 `AGENT_OUTPUT_GUARD_ENABLED` / `AGENT_OUTPUT_GUARD_MAX_RETRIES` / `AGENT_FALLBACK_MODEL`（`AGENT_` 前缀优先、`ORCH_` 兜底）并透传给内核——集群与单机行为一致（此前集群模式这三项配置不生效，guard 无法关闭、fallback_model 不换模型）。
- 关闭开关：`AGENT_OUTPUT_GUARD_ENABLED=false`（或 `ORCH_OUTPUT_GUARD_ENABLED=false`），关闭后检测/重试/熔断全部不生效，行为与旧版完全一致。
- 防误伤设计：检测前剥离代码围栏；pytest 分节线、重复日志行、去重任务的重复记录、代码骨架的重复 raise、文档重复小节标题等合法输出不再误判；单条强规则命中只降级为 warn（score 0.9，不触发重试）。
- 误判排查：单任务看返回结果 `meta["degenerate"]`（`reasons` 为命中规则详情，`recovered`/`attempts`/`models_tried` 记兜底过程；超时收场的任务也透传最近一次检出摘要，`note="timeout"`）；集群看 `GET /stats` 的 `quality.by_model` 退化率，定位到具体模型后可调 `AGENT_FALLBACK_MODEL` 或按上文阈值调参。
- 检测器自身异常不会吞掉正常结果：内核按「放行 + 告警日志」处理，重试轮检测异常按 recovered 口径返回（`note="detection_error_pass"`）。

### 错误人性化与预算软预警

**错误人性化**：内核把 SDK/底层异常翻译为「中文一句话原因 + 一条建议动作」（`agent_core/errors.py`），按特征分类：未装 SDK / 鉴权失败（401）/ 端点不通 / 模型名不存在 / 预算熔断 / 超时 / 未知。`run_oneshot` 的异常收敛与 HTTP 错误路径均已接入；CLI 单轮 fatal 后提示可用 `/retry` 重发上一条消息。

**会话墙钟超时**：`AgentSession.send(prompt, timeout=秒)` 可选参数，超时转为 error 事件返回而非悬挂/裸抛；HTTP 端点 `/agent/session/{id}/message` 已暴露 `timeout` 字段。超时后内核先向底层客户端下发 `interrupt()`，再限时排空本轮残留消息（单条 5 秒保护，防底层卡死时排空无限阻塞），防止残留消息污染下一轮。

**预算软预警**：会话累计 cost 达到 `task_budget_usd` 的 **80% / 95%** 时，内核发出 `budget_warning` 事件（CLI 界面打印预警行，HTTP 会话响应附 `budget_warnings`），SDK 的硬熔断行为保持不变。

### 记忆工具

内核通过 `build_memory_tools` 注入 **4 个进程内记忆工具**（工具名与 `runtime/mcp_server.py` 对齐）：

| 工具 | 参数 | 说明 |
|------|------|------|
| `search_experiences` | `query, role?, successful_only=True, limit=5` | 关键词+语义混合检索历史任务经验（返回已剥离 embedding） |
| `read_core_memory` | `name` | 读一条核心记忆 |
| `write_core_memory` | `name, content` | 写核心记忆（持久、跨任务共识的高价值内容） |
| `write_task_context` | `task_id, key, content` | 写任务上下文记忆笔记（中间产物路径、已试方案、临时决策等过程信息） |

**Agent 如何自主使用**：系统提示末尾附加「记忆与经验（自主使用）」指引块（`build_memory_guidance_block`），引导 Agent 在推理循环中：任务开始先 `search_experiences` 检索经验 → 执行中用 `write_task_context` 记录关键中间结论 → 任务结束评估是否 `write_core_memory` 写入高价值发现。

**单机 vs 集群后端差异**（由 `AgentConfig.memory_backend` 决定）：

| 后端 | 触发 | 实现 |
|------|------|------|
| `local` | `memory_backend=local`（默认） | 直连本地 `FileMemoryStore` / `ExperienceStore`（延迟导入 runtime） |
| `remote` | `memory_backend=remote`（或 `ORCH_MODE=remote`） | 经 brain HTTP API（httpx 异步）：`/experiences/search`、`/memory/core/{name}`、`/memory/context/{task_id}/{key}`，带 `X-API-Key` |

两种后端工具名与语义一致，屏蔽底层传输差异；后端不可达时以工具错误（`is_error`）返回，不抛出。

## Persona 系统

### 什么是 Persona

Persona（人设）定义了一个 Agent「是谁、能用什么工具、用什么模型、系统提示是什么」。在 `agent_core/persona.py` 中，`Persona` 是一个 dataclass：

```python
@dataclass
class Persona:
    name: str                      # agent 名（如 executor）
    description: str = ""          # 一句话职责，供大脑路由/展示
    model: str | None = None       # 覆盖模型；None 走上层/SDK 默认
    tools: list[str] | None = None # 允许的工具名；None = 放开全部工具
    system_prompt: str = ""        # 正文，即系统提示主体
    sub_agents: dict = {}          # SDK options.agents 形状的子 agent（可选）
```

内核 `_build_options` 组装 SDK 选项时：`model` 优先 `persona.model`，其次 `config.model`；`persona.tools` 非空则收窄 `allowed_tools`；`persona.sub_agents` 非空则作为 `agents` 注入（大脑姿态，用 Agent 工具派发子 agent）。

### 内置 Persona

| 人设 | 定义位置 | model | tools | 职责 |
|------|----------|-------|-------|------|
| `executor` | `.claude/agents/executor.md` | sonnet | 全部工具 | 执行子任务，产出代码/文件/结论；可调用 data-expert/web-expert/back-expert 技能 |
| `security-guard` | `.claude/agents/security-guard.md` | haiku | `Read, Glob, Grep, WebFetch`（只读） | 对指令/产物做安全检验，返回 `{verdict, reason, matched_rules, suggestion}` 结构化裁决；只审查不执行 |
| `orchestrator` | 无定义文件，运行时构造 | 上层默认 | 全部 | 编排大脑：加载 `skills/orchestrator/SKILL.md` 正文作系统提示 + 把 `.claude/agents/` 下 executor/security-guard 注册为子 agent |

> `orchestrator` 在 `resolve_persona` 中特殊处理：`persona_dir` 下找不到 `orchestrator.md` 时，回退用 `_build_orchestrator_persona` 构造（SKILL.md 正文 + `parse_subagents`）。其余未知名给最小人设兜底，避免崩溃。

### 自定义 Persona（.claude/agents/ 下新建 .md）

在 `.claude/agents/` 下新建 `<name>.md` 即可，无需改代码。例如新增一个 `code-reviewer`：

```markdown
---
name: code-reviewer
description: 代码审查 agent。只读检查代码质量、风格与潜在缺陷，给出改进建议。
model: haiku
tools: Read, Glob, Grep
---

你是 code-reviewer，一个只读的代码审查 agent。

## 职责
- 阅读指定文件/目录，检查代码质量、风格一致性、潜在缺陷
- 不修改任何文件，只输出结构化的审查意见

## 输出格式
按文件列出：问题级别（blocker/major/minor）、位置、说明、建议。
```

随后即可用：`python agent_cli.py --persona code-reviewer`，或 HTTP/MCP 传 `{"persona":"code-reviewer"}`。

> **worker 与 persona 的关系**：worker 启动时 `ORCH_WORKER_ROLE`（默认 `executor`）决定加载哪个人设文件 —— `.claude/agents/{role}.md`。所以单机多节点 = 多份不同 role 的 `.md`，每个 worker 设不同的 `ORCH_WORKER_ROLE`。人设文件缺失时 worker 在 sdk 分支**启动即报错**（列出 `.claude/agents/` 可用清单），不静默回退。

### Persona 文件格式（YAML frontmatter + 正文）

```markdown
---
name: <agent 名，缺省取文件名主干>
description: <一句话职责>
model: <可选，覆盖模型，如 sonnet/haiku>
tools: <可选，逗号分隔字符串或 YAML 列表；缺省 = 全部工具>
---

<正文 = 该 agent 的系统提示主体>
```

解析规则（`_split_frontmatter` / `_normalize_tools`）：
- frontmatter 用 `---` 分隔；不以 `---` 开头或不足三段时，元数据为空、全文作正文。
- YAML 解析失败按空元数据处理，正文尽量保留，避免整体加载失败。
- `tools` 支持逗号分隔字符串（`"Read, Write"`）或列表；空/缺省 → `None`（放开全部工具）。
- `parse_subagents` 批量解析 `.claude/agents/*.md` 为 SDK `agents` 形状：缺 `name` 或 `description` 的条目跳过，单个文件损坏不拖垮整体。

## 技能系统

### 技能目录结构

技能位于 `workspace/agent/skills/<skill-name>/`，每个技能目录含一个 `SKILL.md` 及配套资产：

```
workspace/agent/skills/
├── orchestrator/     # 大脑工作流（被 scan_skills 排除，非 executor 执行能力）
│   ├── SKILL.md
│   ├── security-rules/
│   └── memory/
├── data-expert/      # 数据分析技能
│   ├── SKILL.md
│   └── run_analysis.py
├── web-expert/       # 前端页面技能（workflow/pipeline.md + gates.md）
│   └── SKILL.md
└── back-expert/      # 后端服务技能
    └── SKILL.md
```

`scan_skills(project_root)` 扫描 `workspace/agent/skills/*/SKILL.md`，解析 frontmatter 的 `name/description/triggers`，返回 `{name, description, path（绝对）, triggers}` 列表。**`orchestrator` 被排除**（它是大脑自身工作流，不属于 executor 的执行能力）。加新技能无需改 worker/内核。

### SKILL.md 格式

```markdown
---
name: data-expert
version: 1.0.0
description: >
  自动化数据分析专家 Skill。接收数据文件（CSV/Excel/JSON/Parquet），
  完成清洗、描述性统计、可视化、质量评分与 Markdown 报告输出。
triggers:
  - 分析数据
  - 数据报告
  - 数据质量
---

<技能正文：工作流、卡点、资产路径说明……>
```

- `name`：技能名（缺省取目录名）。
- `description`：首行用于展示（`scan_skills` 取 `.split("\n")[0]`）。
- `triggers`：触发词列表（最多取前 6 个），注入系统提示的环境块，供大脑/executor 判断何时路由到该技能。

### 技能路由

内核把技能清单注入系统提示的「运行环境块」（`build_env_block`）：
- **executor 姿态**（无子 agent）：列出每个技能的**绝对路径** + 描述 + 触发词，executor 按绝对路径直接调用技能脚本。
- **大脑姿态**（有子 agent）：只列技能名 + 触发词；大脑在派发 prompt 里写 `[技能名]` 标记（如 `[web-expert]`），executor 侧据标记路由到对应技能的 `workflow/pipeline.md` 执行。

| 任务类型 | 技能 | 执行方式 |
|----------|------|----------|
| 数据分析 | data-expert | executor 调用 `skills/data-expert/run_analysis.py` |
| 前端页面（`[web-expert]`） | web-expert | 按 `workflow/pipeline.md` 阶段执行，对照 `gates.md` 卡点 |
| 后端服务（`[back-expert]`） | back-expert | 同上，契约冻结后变更走记录 |
| 其他通用任务 | 不挂技能 | 直接执行 |

### 扩展：添加新工具

进程内记忆工具在 `agent_core/tools.py` 的 `_TOOL_SPECS` 中集中声明（name / description / schema / call）。新增一个工具：

1. 在 local 后端（`_make_local_backend`）与 remote 后端（`_make_remote_backend`）中各加一个同名异步函数，屏蔽底层差异。
2. 在 `_TOOL_SPECS` 追加一条 spec，`call` 用 lambda 绑定后端函数与参数映射。
3. `build_memory_tools` 会自动把它构造成 SDK `@tool`（或降级 dict）。内核 `_build_options` 已把它挂到 `options.tools`。

若要挂载外部 MCP 工具（非进程内），改 `ORCH_MCP_CONFIG` 指向的 JSON 即可，`load_mcp_servers` 会加载并注入 `options.mcp_servers`（缺 `command`/`url` 的条目静默过滤）。

### 扩展：添加新 Persona

见「Persona 系统 · 自定义 Persona」：在 `.claude/agents/` 下新建 `<name>.md`（YAML frontmatter + 正文）即可，无需改代码。若希望它作为大脑的**子 agent**被 Agent 工具派发，只要文件带 `name` + `description` frontmatter，`parse_subagents` 会自动收录。

## 故障排查

| 现象 | 排查 |
|------|------|
| `--help` 正常但一发消息就报 SDK 错 | 未装 `claude-agent-sdk` 或后端连接不可用。`pip install claude-agent-sdk`；确认模型/网络配置。内核延迟导入 SDK，故 `--help` 无需 SDK。 |
| CLI 启动即退出 / `[启动/执行失败]` | 顶层兜底捕获异常。看 stderr 详情；常见为 persona 定义损坏或 runtime 目录不可达。仅查看用法可加 `--help`。 |
| `ModuleNotFoundError: agent_core` | 未从项目根运行，或未 `pip install -e ./agent_core`。CLI 已自动把自身目录加入 `sys.path`；HTTP/MCP 建议 editable 安装。 |
| HTTP 服务全部返回 401 | 设置了 `AGENT_API_KEY` 但请求缺 `X-API-Key` 头（`/health` 除外）。补上正确的头。 |
| `/agent/session/{id}/message` 返回 404 | session_id 不存在或已 `DELETE`。重新 `POST /agent/session` 创建。 |
| 记忆工具报「runtime 不可达」 | `local` 后端需能 import `workspace/agent/orchestrator/runtime` 下的 `memory_store`/`experience_store`。确认 `project_root` 正确；集群下改用 `memory_backend=remote` + 正确 `brain_url`。 |
| 规划模式 `/plan` 显示「无进行中的计划」 | Agent 输出未被解析出计划 JSON。确认已加 `--planning`，且输出含合法 `{goal, steps}` 结构（`parse_plan_from_output` 兼容围栏/裸 JSON）。 |
| RAG 未生效 | 未加 `--rag`（或 `AGENT_RAG_ENABLED=1`）；或经验库无相似成功经验（`successful_only=True, limit=3`）。RAG 失败静默回退原 prompt。 |
| 本地执行模式 `/dispatch` 返回「未配置」 | 未设 `ORCH_LOCAL_EXEC=1`（local 模式默认不注入执行器）。加上后重启 brain。 |
| 集群 dispatch 返回「无可用 worker」 | worker 未注册或心跳超时。`GET /workers` 确认；启动 worker 并确认 `ORCH_AUTO_REGISTER=1` 或手动 `POST /register`。 |
| worker 注册后很快消失 | 心跳超时。确认 worker 存活并定期 `/heartbeat`；或调大 `ORCH_HEARTBEAT_TIMEOUT`。 |
| `ORCH_RUNNER=sdk` 任务 failed | `ORCH_EXECUTOR_DEF` 路径错或 SDK 版本不符；查 worker 日志。 |
