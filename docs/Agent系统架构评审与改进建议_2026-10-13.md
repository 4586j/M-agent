## 一 主要结论

项目已经具备较完整的单 Agent 执行能力，以及集群派发、记忆、审批、预算、可观测性和团队协作的基础。当前最需要投入的是执行正确性与各入口之间的约束一致性。

本次检查确认了七组应优先处理的问题：记忆工具缓存跨配置串读、异步任务状态与记账竞态、重试额度在新任务上重置、部分派发入口绕开统一预算和安全前置检查、旧 Worker 重复执行、Brain 重启后的注册恢复缺口，以及 CI 安装检查引用不存在的模块。

此外，团队协作子系统的协议和数据模型明显比旧编排链路严谨，但默认规划器尚未接入，协作 Worker 命令行也只提供 `none` 和 `fake` 执行器。因此，它目前仍有真实规划和真实执行两处关键接线缺口。旧集群 Worker 已有真实 SDK 执行能力，不能把两个入口混为一谈。

**建议的技术方向：保留统一 AgentKernel；为所有执行入口建立共同的准入与结果提交契约；复用协作子系统已有的 attempt、版本、租约和事务机制，逐步收敛旧链路。** 当前没有足够证据支持为了扩展性立即拆成更多微服务或引入多套中间件。

## 三 当前系统架构

### 3.1 三条运行路径

```text
单机路径
  CLI / Agent HTTP 服务 / 单机面板
    → AgentKernel
      → Claude Agent SDK
        → 模型、内置工具、MCP、记忆工具

旧编排路径
  React 控制面板 / 编排 CLI / 编排 MCP
    → Brain API 与路由
      → 本地 LocalExecutorDispatcher → AgentKernel
      → 远程同步或异步 Dispatcher → Worker /task → SdkAgentRunner → AgentKernel
    → JSON TaskStore、预算账本、经验库、文件记忆、定时器、重试器、SSE

独立团队协作路径
  collaboration/web 界面 / 协作 HTTP API
    → 身份与项目权限、需求版本、计划、工作项、审批、交付验收
    → SQLite、事务、Outbox、SchedulerHost、租约与版本校验
    → 独立协作 Worker、执行日志、冻结任务包与结果上报
      → 默认 none / 可选 FakeRunner
      → 真实规划器和真实执行器尚待接入
```

协作路径拥有独立入口和权限模型，并非旧 Brain 面板上的一组普通路由。两者目前没有共享完整的任务生命周期与执行协议。

### F01 记忆读缓存会在不同配置之间串读

**触发条件：** 同一个 Python 进程中，两套记忆配置使用相同工具名和参数。例如 A、B 两个核心记忆目录均有 `same-name.md`。

`tool_guard.py` 使用模块级 `_tool_cache`，缓存键仅包含工具名和参数哈希。`tools._guarded_run` 未传入后端地址、记忆目录或授权范围。首次读取 A 后，再通过 B 的真实本地后端读取同名记忆，复现结果仍为 `PROJECT_A`，而应为 `PROJECT_B`。

**影响：** 同进程内切换配置或承载多个工作区时，Agent 可能使用错误项目的事实；涉及不同授权范围时还可能形成数据隔离问题。这不是“任意两个独立进程必然共享缓存”的问题。

**建议：** 将缓存绑定到后端实例，或在键中加入稳定的 scope 标识、后端标识和资源版本；避免把原始密钥放进缓存键或日志。写后失效也按相同 scope 执行。考虑多个执行线程共同调用时的并发安全。

**验收：** 两个目录、两个远程后端、两种权限范围的同参查询均不串读；同一范围仍可命中缓存；写后读取与底层状态一致。

证据：[共享缓存](D:/agent/agent/agent_core/tool_guard.py:111)、[缓存键](D:/agent/agent/agent_core/tool_guard.py:198)、[工具接线](D:/agent/agent/agent_core/tools.py:373)。

### F02 异步任务会覆盖取消状态并重复结算

`AsyncRemoteDispatcher._finalize` 先检查状态，再等待产物 HTTP 读取，最后使用无条件 `TaskStore.update` 写终态。等待期间，取消或另一个回调可以先行完成，原有检查已经失效。

本次复现了三种情况：

| 时序 | 期望 | 实际 |
| --- | --- | --- |
| 结果校验等待中取消任务，随后校验完成 | 保持 `cancelled` | 改为 `done` |
| 两个完成回调同时进入产物读取 | 一次提交、一次记账 | 两次记账 |
| Worker 完成回调早于派发 POST 响应返回 | 保持 `done` | 派发尾部改回 `running` |

第三个问题来自 `dispatch_async` 在 POST 返回后直接写 `running`。这会让结果、面板状态、事件流与账本出现矛盾。

**建议：** 所有状态转换使用条件提交；`pending → running` 仅在仍为 pending 时执行，终态写入使用 `finalize_if` 或事务 CAS。只有提交成功的调用方才能记账、发布终态事件和写入经验。后续以 attempt ID 建立结算唯一键，避免进程崩溃后仅靠内存判断去重。同步派发与取消端点也应统一采用相同规则。

**验收：** 上表三个确定性时序全部通过；每个 attempt 只出现一个被接受的终态和一次费用结算，取消后迟到结果只能作为审计证据保存。

证据：[派发尾部](D:/agent/agent/workspace/agent/orchestrator/runtime/async_dispatcher.py:172)、[终态处理](D:/agent/agent/workspace/agent/orchestrator/runtime/async_dispatcher.py:240)、[现有原子提交接口](D:/agent/agent/workspace/agent/orchestrator/runtime/task_store.py:122)。

### F03 自动重试上限无法约束整个任务链

`RetryManager._retry_eligible` 通过 `dispatcher.dispatch` 创建新的 task。新 task 又获得完整的 `max_retries`，默认 retry_count 为零；旧 task 仅增加自己的重试计数，没有共享的逻辑任务总额度。

**复现：** 设置 `max_retries=1`，让模拟 Worker 持续返回失败。初始任务和四轮扫描后的记录数为 `1 → 2 → 3 → 4 → 5`，仍有一条任务可以继续重试。一次逻辑任务本应最多执行两次。

**影响：** 持续失败会沿新 task 无限延长重试链。旧记录在新尝试成功后也未在这条路径中转为“已恢复”，配置多次重试时仍有重复业务动作的风险。

**建议：** 区分 task 与 attempt。task 保持稳定业务身份，attempt 记录第几次执行；对 task 设置总尝试数、绝对截止时间和总费用上限。重试还应判断副作用是否可安全重放，不能仅按 failed/lost 自动重做。

**验收：** `max_retries=1` 时不超过两次执行；成功后停止重试；超时、重启、节点恢复都不能重置总额度。

证据：[重试循环](D:/agent/agent/workspace/agent/orchestrator/runtime/retry_manager.py:125)、[新任务额度初始化](D:/agent/agent/workspace/agent/orchestrator/runtime/dispatcher.py:228)。

### F04 预算与安全前置检查只覆盖部分派发入口

统一的 `_preflight` 由 `/dispatch` 和 `/dispatch/async` 调用，内含预算、指令安全检查和上下文装配。定时器的自动与手动触发直接调用 `dispatcher.dispatch`；自动重试、部分手动重派路径也直接进入派发器。旧派发器本身没有等价的预算准入依赖。

**复现范围：** 临时预算账本已耗尽、`check()` 返回 false 时，按照生产相同依赖关系构造的 TaskScheduler 仍调用了假 Dispatcher 一次。该实验验证的是调度接缝和装配缺口，没有消费真实模型额度。代码检查同时确认定时任务创建/触发路由未复用指令安全前置检查。

此外，旧预算只检查已发生费用，没有预留在途费用；多个并发任务可以在余额耗尽前同时获准。即使补齐入口，也不能立即宣称这是严格的总费用硬上限。

**建议：** 将准入移入应用服务层，所有手动、定时、重试、恢复、审批后执行入口共同调用。按 task/attempt 预留预算，结算时释放预留并幂等记实际费用。授权放行可以针对具体操作，但应绑定已批准内容和版本。

**验收：** 预算为零时，所有入口均无法新增执行；被安全阻断的内容无法通过定时入口改变执行结果；并发准入时预留总额受限。

证据：[HTTP 前置检查](D:/agent/agent/workspace/agent/orchestrator/runtime/brain_routers.py:377)、[定时触发](D:/agent/agent/workspace/agent/orchestrator/runtime/task_scheduler.py:50)、[手动定时触发](D:/agent/agent/workspace/agent/orchestrator/runtime/task_scheduler.py:99)、[预算检查](D:/agent/agent/workspace/agent/orchestrator/runtime/budget_store.py:113)。

### F05 旧 Worker 缺少幂等接收与有界准入

`POST /task` 每次先写 running，再启动一个后台线程，未原子判断同 task 是否已经接收或执行。

**复现：** 同一个 task_id 连续提交两次，两次均返回 HTTP 200，假 runner 实际启动两次。

**影响：** 上游超时重发、重复请求或恢复逻辑可能重复执行有副作用的任务。每个请求直接创建线程，旧 Worker 入口也没有可见的队列容量与执行槽位限制。Brain 的异步信号量限制的是后台轮询，不能替代 Worker 执行并发上限。

**建议：** 接收协议使用 attempt ID 与输入哈希，先持久化原子占位，再执行。同 ID 同输入返回已有状态，同 ID 不同输入返回冲突。设置有界等待队列、节点执行槽位和清晰的过载响应。

**验收：** 并发重复提交只执行一次；请求响应丢失后重发不再次执行；重启后仍识别已接收尝试；队列满时明确拒绝或排队，不无限创建线程。

证据：[旧 Worker 任务入口](D:/agent/agent/worker/worker_api.py:186)、[后台线程创建](D:/agent/agent/worker/worker_api.py:205)。协作 Worker 已有持久占位思路，可借鉴其协议而非另造第三套去重机制。

### F06 Brain 重启后旧 Worker 心跳不会恢复注册

旧 Worker 心跳线程只在循环开始前调用注册；后续只发送 heartbeat。Brain 的 WorkerRegistry 在内存中，未知 worker 的 heartbeat 被静默忽略，HTTP 路由仍返回正常响应。

**复现与推导：** 创建空注册表模拟 Brain 重启后状态，发送原 worker 的 heartbeat，节点仍不存在。结合心跳循环，可确定在没有其他重新注册操作时，这条链路无法自行恢复。Brain 尚未就绪时初始有限重试耗尽，也会遇到类似问题。

远程异步轮询任务保存在进程内 `_tasks` 中；旧 sweeper 依赖注册表中的失联节点集合。重启后注册表和轮询同时丢失，部分持久任务可能长期停在 running，尤其当完成回调丢失时。此次没有执行真实生产进程重启演练，后一影响依据代码链路判断。

**建议：** 未注册心跳返回明确的注册需求，Worker 自动重新注册；采用退避和抖动。Brain 启动时重建远程在途任务对账，并区分 running、不可确认和已终止，不能直接重放未知副作用。

**验收：** Brain 先于/后于 Worker 启动、单独重启 Brain、回调丢失三种场景都能在有界时间内恢复或进入明确的对账状态。

证据：[心跳线程](D:/agent/agent/worker/worker_api.py:67)、[未知节点心跳处理](D:/agent/agent/workspace/agent/orchestrator/runtime/worker_registry.py:44)、[HTTP 心跳路由](D:/agent/agent/workspace/agent/orchestrator/runtime/brain_routers.py:467)。

## 五 功能边界与架构风险

以下内容与上面的可复现缺陷分开处理，其中一部分是尚未完成的能力，一部分是部署规模扩大后需要治理的风险。

### 5.1 团队协作真实规划与执行尚未闭环

协作 `PlanService` 默认 `planner=None`，实际规划时会抛出 `Planner is not configured`。默认 HTTP 服务和调度宿主都按这个默认值装配。协作 Worker CLI 只允许 `none` 和 `fake`，后者明确输出模拟产物。

这说明需求、审批、任务包、结果协议已经建立，但“审核通过后真实拆解，再由真实 Agent 完成”的默认运行路径尚未接通。接口、假 runner、真 HTTP 协议测试各有价值，但需要与真实模型验收分开表述。

建议先接通一个最小纵向场景：一条需求、一个工作项、一个真实执行实例、一个明确可验证的产物。复用 AgentKernel，并将 scope、工具允许范围、预算、取消和产物提交作为适配器契约。协作实例的隔离声明和 owner 核验记录应与真实执行环境配套，不能只靠配置值代替执行边界。

证据：[默认规划器](D:/agent/agent/workspace/agent/orchestrator/runtime/collaboration/planning.py:154)、[协作 Worker 参数](D:/agent/agent/worker/collaboration_app.py:835)、[执行器装配](D:/agent/agent/worker/collaboration_app.py:880)。

### 5.2 多套状态存储应明确各自的权威范围

当前有旧 JSON TaskStore、可选 RunStore、单机运行历史/会话文件、协作 SQLite、协作 Worker 执行日志。它们并存有历史原因，但必须明确：哪个存储决定业务任务状态，哪个记录执行事实，哪个只是查询投影。

旧 TaskStore 直接打开目标 JSON 文件覆写，没有原子替换；`get` 读路径不与写锁统一；全量加载遇到损坏 JSON 没有逐条隔离。写入中断或冷缓存并发读取可能造成解析失败。实例内 RLock 和缓存也不能提供跨进程一致性。此处为代码风险，未进行真实断电实验。

短期可补原子写和坏记录隔离；中期以 repository 接口封装存储，逐条迁移到明确的事务存储。每个业务实体只保留一个写入权威，其他结构由事件投影产生。尚未完成迁移前，应将旧 Brain 的单进程运行边界写入部署说明。

证据：[TaskStore 写入](D:/agent/agent/workspace/agent/orchestrator/runtime/task_store.py:73)、[全量加载](D:/agent/agent/workspace/agent/orchestrator/runtime/task_store.py:165)、[日志开关默认值](D:/agent/agent/agent_core/config.py:148)。

### 5.3 旧控制面权限不宜直接充当团队身份系统

旧 Brain/Worker 共用 API Key；审计操作者优先取客户端 `X-Operator`，程序记忆投票的 voter 来自请求体。持有同一 Key 的调用者仍能自行填写身份名称，不能据此证明不同人员分别审批。

前端将 API Key 存在 localStorage，SSE URL 使用 `api_key` 查询参数；旧 Brain 到 Worker 的地址按 `http://host:port` 构造。这些是源码可见的信任与传输边界，不等于已经发生凭据泄露。跨主机和多人使用时，应评估日志记录 URL、代理配置及同一 Key 权限过大的影响。

建议继续将旧面板定位为受信任运维控制面；面向团队的人员身份、角色授权与审计归属复用协作权限系统。机器身份、人员身份和模型 Provider 凭据分别管理，审批绑定服务端认证身份与操作摘要。

证据：[旧认证中间件](D:/agent/agent/workspace/agent/orchestrator/runtime/auth.py:86)、[操作者来源](D:/agent/agent/workspace/agent/orchestrator/runtime/brain_routers.py:199)、[SSE URL](D:/agent/agent/web/src/api/client.ts:248)。

### 5.4 内核与运行时存在反向依赖和职责集中

AgentKernel 名义上是可复用内核，但 `agent_core/tools.py` 会修改 sys.path 来导入 runtime 记忆模块。配置默认路径也依赖仓库布局。这会降低独立安装、不同部署目录和多工作区场景的可预测性。

建议内核依赖 MemoryReader、ExperienceRepository、ExecutionJournal、ToolPolicy 等小接口，由 CLI、服务、Worker 在装配层传入实现。将 SDK 适配、执行循环、计划执行、结果验证和经验写回从大型内核文件中逐步拆开。先以契约测试固定行为，再移动代码，避免一次大重构同时改变语义。

证据：[运行时导入辅助](D:/agent/agent/agent_core/tools.py:131)、[默认路径配置](D:/agent/agent/agent_core/config.py:17)。

### 5.5 记忆质量与工具边界需要更明确的约束

经验写入通常以 `status == done` 或 `not is_error` 作为成功；产物安全 verdict 被另行保存。经验检索的 successful_only 仅按 success 筛选。因此，应明确“执行完成”“产物安全”“业务验收通过”分别是什么，避免把未经认可的结果自动提升为可信经验。

核心记忆默认可全量进入系统提示；相关性检索无命中时也会回退全量。建议增加可配置的上下文总预算、来源、作用范围、时效与批准状态，并将普通检索内容明确作为参考资料。跨项目共享知识必须显式授权，不能只靠 prompt 提醒。

工具守卫当前主要接在内置记忆工具上，不能由此推断所有 SDK 内置工具与外部 MCP 都受同一策略约束。显式无人值守模式会生成较宽的工具允许清单。真实团队执行应采用执行时强制的路径、命令、网络和工具范围限制；危险操作审批绑定参数摘要。

产物收集还会扫描工作目录下的文件，只排除少数目录；共享或长期工作目录中的旧文件可能被一并列为产物。建议使用任务级输出目录及显式 manifest，记录来源 attempt、大小和摘要。

证据：[经验筛选](D:/agent/agent/workspace/agent/orchestrator/runtime/experience_store.py:246)、[核心记忆加载](D:/agent/agent/agent_core/context.py:48)、[无人值守设置](D:/agent/agent/agent_core/kernel.py:768)、[产物扫描](D:/agent/agent/agent_core/kernel.py:103)。

## 六 建议的目标架构

建议形成六个职责清楚的层次，并保留当前能工作的入口。

| 层次 | 负责的事情 | 从当前代码演进的方式 |
| --- | --- | --- |
| 接入层 | CLI、HTTP、MCP、UI、定时触发 | 只解析请求与身份，统一调用应用服务 |
| 应用服务层 | 准入、预算预留、安全审批、重试和取消 | 将 `_preflight` 与分散入口规则收敛到共同服务 |
| 任务与尝试层 | Task、Attempt、状态转换、租约、输入版本 | 复用协作协议和 RunStore 的经验，明确定义适配关系 |
| 执行层 | 真实 SDK 执行、工具范围、工作区、取消 | 保留 AgentKernel，通过执行适配器接旧 Worker 与协作 Worker |
| 持久化层 | 原子提交、结算去重、Outbox、恢复 | 先完成一致性，再根据实际负载决定是否更换数据库 |
| 查询与知识层 | 面板、审计、指标、经验与检索 | 查询状态由权威数据派生，记忆访问携带 scope 与来源 |

需要统一的关键契约：

1. **Task 是用户请求，Attempt 是一次执行。** 失败重试创建 attempt，业务 task 身份不变。
2. **输入版本固定。** attempt 绑定 prompt/context/工具策略的版本或摘要，审批与结果均引用该版本。
3. **状态提交原子化。** 迟到、重复或旧租约结果可以留证据，但不能改写当前有效状态。
4. **费用按 attempt 幂等结算。** 准入预留与终态结算有明确对应关系，重试共享 task 总预算。
5. **取消请求与停止确认分开。** 用户提出取消不等于外部执行已停止；无法确认的尝试进入对账。
6. **记忆与缓存带授权范围。** 本地路径、远端实例、项目和权限版本都参与隔离设计。
7. **通知可重放。** 终态通知通过持久事件驱动，SSE 只是传输方式，不是任务真相来源。

旧 API 可继续提供兼容适配，新能力优先建立在统一契约上。SQLite、文件、远端执行器的替换应隐藏在接口之后，避免前端和 Agent 提示词承担存储迁移细节。

### 第二阶段 补齐准入与恢复

处理 F04、F06，并完成预算预留、有界队列、重启对账、坏记录隔离和部署边界说明。统一手动、定时、重试、恢复入口；在真实进程中验证取消和重复回调。

**完成标准：** 预算耗尽后所有入口阻止新增执行；Brain/Worker 任意启动顺序可恢复；正在执行时强制退出后不会无条件重复副作用；并发提交不会产生重复 attempt 或重复费用。

### 第三阶段 完成真实团队协作闭环

为协作 PlanService 接入受控规划器，为协作 Worker 接入统一内核适配器；使用真实受限工作区，完成从需求、计划、执行到产物验收的最小纵向流程。随后再推广多成员、多节点和更复杂的计划。

**完成标准：** 至少一条真实模型任务完整通过；另有失败、退回返工、取消、节点失联、结果响应丢失五类场景留下可核对证据。协议测试、模型测试和业务验收分别报告。

### 第四阶段 依据指标做结构优化

拆分集中职责、替换 sys.path 依赖、统一查询接口、完善记忆治理与发布依赖管理。是否引入队列服务、共享数据库或对象存储，由等待时长、并发量、锁等待和产物规模决定。

建议先建立基线，再设置目标值：

| 指标 | 用途 |
| --- | --- |
| 被接受的重复执行次数、终态冲突次数、重复结算次数 | 验证正确性修复，目标应为零 |
| 未对账 attempt 数量与最长滞留时间 | 判断恢复机制是否收敛 |
| 队列等待时间、执行时长、在途数量 | 决定并发和节点容量 |
| 预算预留、实际费用、缺失结算记录 | 判断费用控制可靠性 |
| 任务验收通过率、返工率、总尝试数 | 评估 Agent 的实际完成质量 |
| 记忆命中质量、跨 scope 命中次数、上下文开销 | 评估记忆收益与隔离效果 |
