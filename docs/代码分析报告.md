# 多 Agent 编排框架 代码分析报告

> 分析日期：2026-07-12
> 分析范围：大脑运行时 9 文件、worker 3 文件、前端 15 文件
> 方法：三路并行子代理审查 + 人工核验去伪

---

## 一、整体架构评价（优点）

1. **三角色职责分离清晰**。大脑（编排）/ executor（执行）/ security-guard（只读审查）能力边界明确，security-guard 仅配 Read/Glob/Grep/WebFetch 四个只读工具，从工具层物理剥夺破坏能力，比 prompt 自律可靠。
2. **派发抽象设计良好**。`Dispatcher` 抽象基类 + `LocalDispatcher`（V1 单机）/ `RemoteDispatcher`（V2 跨主机），本地与远程切换干净，是优秀的扩展点。
3. **安全检验分层合理**。规则引擎（确定性、零依赖）+ 可选 LLM 增强（haiku 补判），LLM 不可用时优雅降级到规则结果，不阻塞主流程。
4. **路径无关设计**。`_default_web_dist()`、`_default_task_store_dir()`、`_default_executor_def()` 均基于 `__file__` 定位，避免运行目录漂移。
5. **配置全环境变量驱动**。`ORCH_MODE`/`ORCH_RUNNER`/`ORCH_PERMISSION_MODE` 等切换形态与行为，零配置文件。
6. **worker 依赖注入可测**。`register_to_brain`/`start_auto_heartbeat` 支持 `http_post` 注入，`AgentRunner` 接口 + Fake/Sdk 双实现，单测覆盖良好（runtime 53、worker 6、rules 6 passed）。
7. **前端工程化规范**。组件职责单一、`usePolling` 用 ref 持最新回调避免闭包陈旧、统一 `request<T>()` 提取错误、JSX 默认转义防 XSS、类型与后端对齐。

**总评**：架构思路清晰、安全意识强、可扩展性好；但存在若干**高危的真实缺陷**（路径穿越、线程安全、同步阻塞、无认证），在跨主机/生产场景下需优先修复。

## 三、分维度分析

### 3.1 安全性

**核心风险：输入校验缺失 + 无认证。** 框架自带 security-guard 审查"任务内容"的安全，但**自身 API 的安全防护薄弱**：

- **路径穿越（高）**：产物链路两端都未充分校验。大脑 `/proxy/artifact` 的 `path` 直传 worker（`brain_api.py:177`），worker 端只校验 `full.relative_to(base)`（`worker_api.py:120-122`，base=work_dir），**未校验是否在 `base/task_id/` 内**。`path=../other-task/secret.md` 解析后仍在 base 内、校验通过，可读其他任务产物。`memory_store.py` 的 `name/task_id/key` 同样无校验，可 `../../` 读写删任意文件（当前未直接暴露为 HTTP 端点，但是不安全接口）。
- **SSRF（高）**：`RegisterReq.host` 无格式校验（`brain_api.py:19`），worker 可注册内网地址，`RemoteDispatcher` 会向该 host 发 POST/GET（`dispatcher.py:104,109,116`）。
- **无认证 + force 绕过（高）**：全部端点无鉴权，`DispatchReq.force=true`（`brain_api.py:31`）可跳过 security-guard 指令检验。跨主机 `ORCH_BRAIN_HOST=0.0.0.0` 暴露后，任何能连到 7000 端口的客户端可注册恶意 worker、派发危险指令、读取任意任务产物。
- **CORS**：默认 `localhost:5173` 安全；但 `allow_methods=["*"]`/`allow_headers=["*"]` 在生产偏松。

### 3.2 可靠性

**核心风险：同步阻塞轮询、线程安全、取消不传播。**

- **同步阻塞轮询（高）**：`RemoteDispatcher.dispatch` 在 FastAPI 同步 handler 内用 `time.sleep(0.5)` 循环最多 1000 次（约 500s，`dispatcher.py:115-133`）。FastAPI 把同步 handler 丢线程池，一次派发独占一个线程最长 500s，QPS 受线程池大小限制；且轮询期间**不检查任务是否已取消**，`/tasks/{id}/cancel` 后仍轮询到超时。
- **线程不安全（高）**：`WorkerRegistry._workers`/`_rr` 是裸 dict（`worker_registry.py:23-24`），`_alive()` 遍历时若并发 `register`/`unregister` 修改，可触发 `RuntimeError: dictionary changed size during iteration`。
- **任务取消不传播（中）**：`cancel` 只改本地 `task_store` 状态（`brain_api.py:105-112`），不通知远程 worker 停止，worker 继续执行到完成。
- **asyncio.run 脆弱（中）**：`security_guard._llm_judge`（`:124`）与 `agent_runner.SdkAgentRunner.run`（`:113`）在同步上下文调 `asyncio.run()`。当前因同步 handler 在独立线程、无运行 loop 而能工作；一旦这些路径进入 async 上下文即 `RuntimeError`。
- **异常静默（中）**：`_check_product` 的 `except Exception: continue`（`dispatcher.py:147`）、心跳的 `except Exception: pass`（`worker_api.py:53-55`）使失败不可见。
- **JSON 反序列化无校验（中）**：`TaskRecord(**json.load(f))`（`task_store.py:44`），文件损坏或字段变更即崩溃。
- **worker state 无限增长（中）**：`state` 字典随任务累积无清理/过期，长期运行内存泄漏。
- **SDK 执行无总超时（中）**：`max_turns=50` 只限对话轮数，不限总时长，卡死任务可长期占用线程。
- **进程退出丢任务（中）**：心跳/任务线程均 `daemon=True`，worker 崩溃重启后内存 state 全丢，brain 永远查不到已完成的任务。

### 3.3 性能

- **同步轮询阻塞线程池（高）**：见 3.2，500s 占一线程。
- **task_store 全量扫描（中）**：`_all()` 每次读并反序列化目录下全部 JSON（`task_store.py:69-74`），`list_all/by_status/by_worker/list_lost` 均调它，任务数增长时线性恶化。
- **`/stats` 全量遍历（低）**：每次遍历全部任务计数+排序取 top10（`brain_api.py:151-169`）。
- **前端轮询放大（低）**：Dashboard 双 5s 轮询 + 每个 WorkerCard 展开时额外 `api.tasks(workerId)`，N 节点展开时约 `2+N` 请求。

### 3.4 可维护性

- **死代码（中）**：`agent_runner.py:45-51` 的第一个 `SdkAgentRunner` 骨架被第二段覆盖；`worker_api.py:43` 的 `http_post = http_post` 无操作语句。
- **硬编码常量（低）**：`_POLL_MAX=1000`（`dispatcher.py:12`）、`_http_call timeout=30`（`brain_api.py:193`）、`dispatch_cli timeout=120` 均不可配置。
- **路径脆弱（低）**：`_RULES_DIR` 三级 `..`（`security_guard.py:17`）、`_default_web_dist` 最多八级 `..`，打包/调结构后失效。
- **rules 合并丢序（低）**：`merge_rules` 覆盖时规则位置变为 override 位置，丢失默认排序（`rules.py`）。
- **前端重复 UI（中）**：`TaskDetail` 与 `Command` 的 security-guard 警告框结构相同，可抽 `SecurityVerdictAlert` 组件。
- **前端无测试/无 ErrorBoundary/可访问性不足（低）**：模态无 `role=dialog`/focus trap、图标按钮无 `aria-label`、label 未关联 input。

## 四、改进建议（按优先级）

### P0 -- 跨主机/生产前必须修复
1. **产物路径穿越**：worker 端 `relative_to(base)` 改 `relative_to(base / task_id)`（`worker_api.py:120`）；brain `/proxy/artifact` 对 `path` 做白名单（拒绝 `..`、绝对路径）。
2. **WorkerRegistry 加锁**：`threading.Lock` 保护 `_workers`/`_rr` 全部读写。
3. **API 认证**：至少加 `ORCH_ADMIN_TOKEN` 校验 `/dispatch`/`/register`/`/workers`/`/proxy/artifact` 等敏感端点；`force` 参数要求 admin。
4. **worker 注册校验**：`worker_id` 限 `[a-zA-Z0-9_-]+`，`host` 做 IP/域名格式校验，禁私有 IP（除非显式允许），闭合 SSRF。

### P1 -- 高优先级
5. **异步轮询 + 取消感知**：`dispatch` 改 `async def`，`asyncio.sleep` 替代 `time.sleep`，每轮查 `task_store.get(task_id).status`，`cancelled` 即返回；`poll_interval`/`poll_max` 可配。
6. **二进制产物**：`read_bytes()` + base64 返回，或按扩展名判文本/二进制。
7. **memory_store 路径校验**：`resolve()` 检查在 base 内，或白名单字符集。
8. **删除死代码**：`agent_runner.py:45-51` 重复定义、`worker_api.py:43` 无操作行。

### P2 -- 中优先级
9. **任务取消传播**：cancel 时向 worker 发取消请求。
10. **异常日志**：`except: pass/continue` 改 `logging.warning`。
11. **task_store 优化**：按 status 分目录或内存索引或 SQLite；反序列化加 try/except。
12. **worker state 过期清理** + **SDK 总超时**。
13. **worker 上报真实 load**：让 least_load 策略生效。
14. **前端**：WorkerCard 加错误处理、fetch 加 `AbortSignal.timeout`、修 usePolling loading bug、加 ErrorBoundary。

### P3 -- 低优先级
15. config `int()` 容错、硬编码常量可配、rules 合并保序、路径用 `importlib.resources`。
16. 前端抽 `SecurityVerdictAlert`、补可访问性、统一 API 代理前缀、加前端测试。

## 六、结论

该框架在**架构设计**上成熟可圈：三角色职责分离、派发抽象、安全检验分层降级、配置外置、可测试性好，是一个结构清晰、安全意识强的多 Agent 系统实践。

短板集中在**工程化健壮性与生产安全**：路径穿越、线程安全、同步阻塞轮询、无认证四大高危问题在单机本地测试中不暴露，但一旦跨主机（`ORCH_BRAIN_HOST=0.0.0.0`）或上生产即成实际风险。P0 四项（产物穿越、注册表加锁、API 认证、注册校验）建议在跨主机部署前优先修复，P1 的异步轮询改造是性能与可靠性的根本改善。修复后该框架可具备生产可用基础。
