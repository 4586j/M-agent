# 开发与文档维护规范

> 文档类型：持续执行的开发约定；最后核对：2026-10-18。适用于代码、配置、测试、文档与交付记录。

## 1. 资料如何保持可信

以用户最新明确要求、当前代码/配置、相应验证证据核实事实。当前主文档应及时同步；日期报告和历史设计保留当时上下文，不能反过来覆盖最新边界。

记录时区分：目标设计、代码已实现、模拟测试通过、真实模型联调通过、业务验收通过、已提交、已发布、已部署。每一种状态有各自证据，未发生就不写已经完成。

主入口是 [文档中心](README.md)，仓库级执行规则是 [AGENTS.md](../AGENTS.md)。后续开发持续更新文档，不通过定时任务自动改写事实。

## 2. 每批开发流程

1. 阅读相关主文档和问题记录，检查 Git，识别用户已有改动；明确任务范围和人员/模式边界。
2. 在 [开发计划](开发计划.md) 记录工作项状态、依赖、负责人和验收条件；没有被分配的负责人标待指派，不虚构日期。
3. 对行为变化、数据迁移或重要选择先写简短方案/决策；实现时保留旧数据和回滚边界。
4. 进行与改动相称的验证；Bug 测试验证可观测行为或真实故障，不只重复实现细节。文档变更无需重跑全部模型/应用测试。
5. 同步下表所列资料；新增记录加入文档中心，较大修复另建日期记录。
6. 执行文档检查和差异检查，审阅是否泄露密钥或把计划写成事实；交付说明列出完成项、测试范围、资料链接、剩余限制和提交/部署状态。

## 3. 变更到文档的映射

| 变更 | 应同步的资料 |
| --- | --- |
| 产品定位、可用能力、入口、模式范围 | 项目介绍、README、必要的专题说明、CHANGELOG |
| 模块/调用链、持久化、权限、预算、上下文边界 | 系统架构、必要的架构决策、开发计划和问题台账 |
| API 路径/请求/响应/错误、环境变量、启动默认值 | 使用手册或对应专题、README 示例、架构中的关键边界 |
| Bug 修复、故障恢复、回滚方法 | 问题台账，必要的日期修复记录和验证证据，CHANGELOG |
| 开发开始、完成、受阻或范围变化 | 开发计划，相关问题状态和验收说明 |
| 新增/替换文档 | 文档中心；替代旧资料时给旧文档加导航说明 |
| 纯排版或不影响行为的内部整理 | 只更新受影响资料，不制造全套无意义更新 |

主文档包含文档类型和最后核对日期。核对日期不是部署时间。记录源码基线时说明是否包含未提交工作区，不能捏造新提交号。

## 4. 环境、运行与配置

从仓库根目录安装：

```bash
python -m pip install -e "./agent_core[service,dev]"
python -m pip install -r workspace/agent/orchestrator/runtime/requirements.txt
python -m pip install -r worker/requirements.txt
npm --prefix web ci
```

- 个人 CLI：`agent`；个人服务：`python -m agent_core.service --port 8000`。
- Brain：进入 `workspace/agent/orchestrator/runtime` 后执行 `python -m brain_api`，默认 7000；远程派发配置 `ORCH_MODE=remote`，本地执行另需 `ORCH_LOCAL_EXEC=1`。
- Worker：进入 `worker` 后执行 `python worker_api.py`，默认 8000；默认 `ORCH_RUNNER=fake` 为模拟执行，真实执行需 `ORCH_RUNNER=sdk` 和对应模型/人设/权限配置。同机不要与个人服务占相同端口。
- 前端开发：`npm --prefix web run dev`；生产：`npm --prefix web run build`。

团队服务需独立数据目录和认证；以下在 `workspace/agent/orchestrator/runtime` 执行：

```bash
python -m collaboration bootstrap --data-dir ./collab-data --username admin --display-name 管理员
python -m collaboration serve --data-dir ./collab-data --port 7400 --origin http://127.0.0.1:7400
```

bootstrap 交互输入密码，不能把密码直接拼入命令或文档。服务启动不代表真实 Planner/Runner 已配置。真实接线须向服务和 scheduler 显式传 `--planner-config`，Worker 传 `--runner sdk --sdk-config`；步骤、工具和预算边界见 [团队接通说明](团队真实规划与执行接通_2026-10-18.md)。实例协议历史设计见 [团队专题](团队协作功能开发文档.md)。

个人/旧编排配置见 [.env.example](../.env.example)；团队服务不沿用旧控制面的配置与认证。只复制模板、按实际填写本机环境，不覆盖用户现有 `.env`，不提交真实配置与密钥。

## 5. 验证命令及范围

### 文档与静态检查

```bash
python docs/check_docs.py
git diff --check
python -m ruff check <改动的Python文件>
```

`docs/check_docs.py` 检查当前主文档、模板与仓库入口的必需文件、日期、标题、代码块和本地链接；历史报告不纳入完整递归门禁，以免把临时联调证据或历史路径错误伪装成当前承诺。它不会验证自然语言语义或真实运行能力。

### 后端确定性回归

```bash
python -m pytest agent_core/tests worker/tests workspace/agent/orchestrator/runtime/tests -q
# 按本次修改选取专项，而非所有小改动都重复全量：
python -m pytest agent_core/tests/test_understanding_service.py agent_core/tests/test_understanding.py -q
python -m pytest workspace/agent/orchestrator/runtime/tests/test_understanding.py -q
```

后一项验证 Brain 未挂载个人核验路由，不是让 Brain 参与答题。评测纯逻辑可运行 `python -m pytest eval/tests -q`，`python eval/run_eval.py --dry-run` 不派发任务。

在 Windows 沙箱中，pytest 临时目录或本机事件循环可能受限。可把 TEMP/TMP 与全新的 `--basetemp` 指向仓库 `.tmp`，避免修改系统目录。若 socket/event-loop 权限仍被限制，应按宿主权限流程执行合规测试，不能把环境失败记作通过。不要让 pytest 清理用户真实数据目录。

### 前端与浏览器

```bash
npm --prefix web test
npm --prefix web run build
npm --prefix web run test:e2e:panel
npm --prefix web run test:e2e:personal
npm --prefix web run test:e2e:layout
npm --prefix web run test:e2e:proxy
npm --prefix web run test:e2e:orchest
```

Playwright 需要浏览器环境；安装命令为 `npx playwright install chromium`（在 web 目录执行）。个人新流程使用 8130，既有个人面板 8100，布局 8126，开发代理 8128/8129；编排集成测试使用 7000，本地配置可能复用已运行服务，运行前应确认目标与数据隔离。用户当前业务服务不应被测试随意重启或覆盖。

### 真实模型与业务验收

真实 SDK 冒烟默认关闭，CI 仅显式选择后开启。真实调用需要用户授权和独立预算；不在普通文档检查、单元测试中消耗模型额度。不得把模拟模型的 cost=0 当作真实未知费用为零。本轮沿用用户要求的 Ark 纯文本测试约束，不发送图片。

真实业务验收需要产物、验收条件、人员决定和失败/恢复证据，不能用“模型返回成功”替代。

## 6. 结果记录格式

每份验证记录写明日期、源码/工作区范围、命令、测试类型、结果、跳过/告警、是否真实模型、是否涉及部署，以及产物所在位置。

最近代码批次（2026-10-18）的已有证据：

| 范围 | 结果 | 使用限制 |
| --- | --- | --- |
| agent_core/tests + runtime/tests + worker/tests/test_agent_panel.py | 1724 passed、2 skipped | 未包含完整 worker/tests；两项真实 SDK 默认跳过 |
| 个人 service/panel/understanding 最终专项 | 110 passed | 是该批代码的复测，不能与上一行相加作覆盖率 |
| 前端单元测试 | 72 passed | 不等于真实后端/模型验收 |
| 个人旧面板 / 新个人沟通 / 编排布局隔离 | 18 / 2 / 14 passed | 各自浏览器范围，主要使用模拟 API |
| 构建、增量静态与差异检查 | 通过 | 不宣称全仓库 Ruff 全绿 |

这些是前一代码批次的历史证据。本次文档批次执行文档门禁与只读审阅，结果另记 CHANGELOG，不声称重跑上述全套。

## 7. 模板与历史资料

使用 [开发任务](templates/开发任务模板.md)、[修复记录](templates/修复记录模板.md)、[架构决策](templates/架构决策模板.md) 模板。大修复文件可按主题和日期命名；主文档持续原地更新，历史报告不批量覆盖。

旧报告中的部署/测试/提交状态是当时事实；给它增加“历史参考”和最新入口，不改写成今天已完成。临时文件链接应明确是本机证据，不作为可移植主文档必需项。

## 8. 完成标准

相关代码、测试和资料一致；本地链接有效；没有真实凭据；模式与权限边界准确；已知限制和计划状态同步；交付说明明确文档、验证和发布状态。

根 AGENTS.md 与 PR 模板会提醒后续开发同步资料，CI 文档检查覆盖结构和链接；事实正确性仍需开发者根据代码与证据审阅。
