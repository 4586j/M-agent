# ADR-004：装扮换装采用分层 Sprite + 挂点，不用 Spine 换装

- 日期：2026-09-05
- 状态：accepted

## 背景

用户已选定「**预设部件换装**」路线（非 UGC 上传、非参数化生成）：官方美术资产按部位分层，玩家自由组合。需要决定客户端的换装**渲染实现**。

部件槽位共 5 个：`bg / back / body / head / hand`；Demo 期 18 个部件，正式版预期扩展到数百个。宠物本体有待机/进食/开心三段动画。

调研（`knowledge/research/20260905-...md` 要点 2）发现 Spine 换装的三条路线各有硬性代价，其中「外部贴图换装」的代价对本项目**不可接受**：
- 原生端需**定制引擎并重编译**（改 `SkeletonRenderer.cpp` / `Attachment.cpp` 等）；
- 改引擎后在微信小游戏端**无法使用「分离引擎」优化**，直接拉长首屏加载时间。

## 决策

采用**分层 Sprite + 挂点表**：宠物本体为独立动画节点，装扮部件为挂在固定锚点上的独立 Sprite 节点，用 `siblingIndex` 控制 Z 序（`bg -10 / back -5 / body 10 / head 20 / hand 30`）；**换装只替换 Sprite 的 `SpriteFrame`，不重建节点树**；部件图打进自动图集以合批控制 DrawCall。

**升级路径已明确保留**：若正式版需要部件随骨骼动画形变（贴合类服饰），切 Spine **socket 挂点**方案——把 Cocos 节点挂到指定骨骼上，该方案**无需改引擎**、不影响小游戏分离引擎优化，且挂点表的语义可直接迁移（槽位→骨骼名）。

## 备选方案（为什么没选）

- **Spine 整体换装 `setSkin()`**：实现最简单、三端统一。放弃原因：需要 m×n 套完整皮肤——5 个槽位各 20 种部件就要 20^5 组合，实际做法是为每套搭配出一份完整皮肤，部件一多**工程臃肿、图集失控、内存与加载双爆**，无法支撑"自由组合"这一核心需求。
- **Spine 局部换装（皮肤附件替换）**：可自由组合、部件可参与 Spine 合图。放弃原因：仍需在 Spine 工程内为每个部位维护 n 个局部皮肤与占位符，美术维护成本高；且引入 Spine 编辑器授权与美术骨骼工程依赖，Demo 期用占位图无法验证。
- **Spine 外部贴图换装**：部件可用引擎 texture、与 UI 共用。放弃原因：见背景节——需定制引擎重编译，且**丧失小游戏分离引擎优化**；与 ADR-003「保留后续补做小游戏能力」直接冲突。
- **3D 换装（骨骼网格 + 材质替换）**：表现力最强。放弃原因：美术资产量级与包体完全超出 Demo 与技术验证目标，且移动端低端机性能风险高。

## 后果

- **正面**：零引擎改动、零 Spine 授权、零美术骨骼工程；部件可**懒加载**（按 `resource_key` 单独加载），支撑数百部件规模；Demo 期用程序生成的占位图即可完整验证换装与实时广播链路；同图集部件可合批，DrawCall 可控。
- **代价**：
  - 部件**不随骨骼动画形变**——贴合躯干的服饰在宠物做动作时会有穿帮（Demo 期用宽松造型与占位图规避，正式版需美术按"部件在动画中保持刚性"的约束出图）；
  - Z 序与挂点表需自行维护，槽位增多时是复杂度来源（已在 `02-架构说明.md` §3.3 固化为表格契约）；
  - 分层 Sprite 的 DrawCall 合批依赖"同一图集"，跨图集部件会打断合批 → 已落为 T-34 完成定义（图集文件数 ≤3）。
- **影响范围**：`02-架构说明.md` §3.3（挂点表）；`03-契约定义.md` §2.11 `dress_item.resource_key` 字段语义、§2.14 `slots` 的 key 枚举；`05-tasks.md` T-34 / T-37；客户端 `OutfitRenderer.ts`。
- **复评触发条件**：① 美术提出需要服饰随动画形变 → 切 Spine socket 挂点；② 部件数超过 500 且首屏加载超标 → 引入远程资源包（调研笔记第 7 节）。
