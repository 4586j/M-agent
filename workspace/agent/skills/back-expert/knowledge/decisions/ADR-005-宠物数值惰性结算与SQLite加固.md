# ADR-005：宠物数值用「参考值 + 服务端时间戳」惰性结算，不用定时任务写库；并沿用 SQLite（附 WAL 加固与迁移触发条件）

- 日期：2026-09-05
- 状态：accepted

## 背景

养成玩法的核心是「**离线期间数值也在变化**」：饥饿/清洁/心情随时间衰减，体力随时间恢复，成长值有每日上限。两名监护人共养同一只宠物，且各自可能在任意时刻上线、任意时长离线。

需要决定两件事：① 时间驱动的数值**怎么算、什么时候算、算完存哪**；② 承这套写并发的**数据库选型**（ADR-001 已为 blog-backend 选定 SQLite，但其前提是"写 QPS < 1"，本项目存在双人同时写的场景，前提不完全成立）。

调研依据（`knowledge/research/20260905-...md` 要点 3）：离线时长若用客户端时间计算会被改系统时间绕过；离线收益需设上限截断防挂机刷；断线 2s 内快速重连不要重复校验（时间差过小易误判）。

## 决策

### 决策一：惰性结算（lazy settle）

**不存"当前值"，只存"参考值 + 结算时刻 + 速率"**，任意时刻的当前值由**闭式纯函数**算出：

```
dtMin   = max(0, (now_server - last_settled_at) / 60000)     // 时钟回拨按 0 处理 + WARN 日志
current = clamp(ref ± rate_per_min * dtMin, STAT_MIN, STAT_MAX)  // 衰减取 -，恢复取 +
```

- **读路径**（`GET /pets/:id/state`）：结算后直接返回，**不落库**（避免每次读都产生写，这对 SQLite 尤其重要）；
- **写路径**（`POST /pets/:id/interactions`）：在单个事务内结算 → 校验 → `ref = current`、`last_settled_at = now_server` 与业务变更一并提交；
- `now_server` 一律取服务端 UTC；**契约中不存在任何客户端时间入参**（spec 验收 11）；
- 结算逻辑抽为**领域层纯函数** `SettleService`（无 IO、无框架依赖），100% 单测覆盖，登记为 **R-007**；体力恢复复用同一函数（方向相反），验证其通用性；
- 客户端用**同一公式**做显示插值（数值条平滑下降），但任何写操作返回后**以服务端结果整体覆盖**本地，本地计算值**绝不回传**。

### 决策二：沿用 SQLite，但强制 WAL 加固并写明迁移触发条件

沿用 ADR-001 的 NestJS + Prisma + **SQLite**，附加两条硬性加固（已落为 T-03 完成定义）：
- `PRAGMA journal_mode=WAL`（读写不互斥，读不阻塞写）；
- `PRAGMA busy_timeout=5000`（写冲突时等待而非立即抛 `SQLITE_BUSY`）。

并把并发写压力从数据库层**上移到应用层化解**：Redis 短锁 `pet:lock:{petId}`（TTL 3s）把同一宠物的并发写串行化 + `pet.version` 乐观锁兜底正确性 → 实际到达 SQLite 的并发写已被收敛为**每宠物近似串行**。

## 备选方案（为什么没选）

- **定时任务扫表写库**（每 N 分钟对所有宠物结算并 UPDATE）：放弃原因：① 需要全表扫描，宠物数增长后是持续的背景负载；② 精度受调度间隔限制（间隔 5 分钟则数值最多滞后 5 分钟）；③ 服务重启期间的调度空窗会造成数值跳变；④ 制造大量无业务意义的写，与 SQLite 写并发弱的特性正面冲突。
- **只存当前值 + 客户端上报经过时间**：放弃原因：客户端时间可被改系统时间伪造（调研要点 3 的直接踩坑记录），等于把数值权威性交给客户端，作弊零成本。
- **读时也落库（每次 GET 都 UPDATE last_settled_at）**：放弃原因：把只读接口变成写接口，读多写少的场景下无谓放大 SQLite 写压力，且并发读会互相触发 version 冲突。
- **直接上 PostgreSQL**（toolchain 默认项）：放弃原因：Demo 期数据量与并发极小（数个宠物 × 2 人），额外运维一个数据库进程收益为零；Prisma 保留了改 `provider` 即迁库的能力。**但本项目已突破 ADR-001 的"写 QPS < 1"前提**，故必须写明迁移触发条件（见下）。
- **Redis 作为数值主存储**：放弃原因：数值是唯一事实，必须落在有关系与唯一约束的持久层；Redis 只承担 CD/锁/幂等键等**可重建**数据（patterns 第 5 组：缓存只放可重建数据，不缓存唯一事实）。

## 后果

- **正面**：
  - 天然支持**任意时长离线**（30 天与 30 秒的计算成本相同，闭式公式 O(1)）；
  - 零背景任务、零调度依赖，服务重启不影响数值正确性；
  - 客户端**无法伪造**（无客户端时间入参、无本地权威值）；
  - 读路径不写库，把 SQLite 的写压力压到最低；
  - `SettleService` 是通用能力：养成衰减、体力恢复、会员到期、积分过期等场景均可复用（R-007）。
- **代价**：
  - 数据库里存的**不是当前值**，直接用 SQL 查库看到的是参考值，运维排查需知道要配合 `last_settled_at` 手算（已写入 `02-架构说明.md` §1.2 统一语言）；
  - 每次读都要计算，但成本是常数级可忽略；
  - 时钟回拨需要显式处理（已定为 dtMin=0 + WARN 日志，宁可不衰减也不允许数值倒涨）；
  - **SQLite 并发写风险未完全消除**：WAL + 短锁 + 乐观锁把风险降到可接受，但极端并发下仍可能出现 `RESOURCE_002` 比例升高（用户体验为"操作冲突请重试"）。
- **迁移 PostgreSQL 的触发条件**（满足任一即必须迁移，写入 `02-架构说明.md` §7）：
  1. 同时在线宠物数 > 100；
  2. 出现 `SQLITE_BUSY` 且 `busy_timeout` 重试后仍失败；
  3. 需要多实例部署（届时 WS 房间表也需迁 Redis Pub/Sub）。
- **影响范围**：
  - `03-契约定义.md` §1（`pet` 表的 `*_ref` / `last_settled_at` / `version` 字段、`pet_guardian.stamina_ref`）、§4.1（结算公式契约）、§6（速率类配置项）；
  - `02-架构说明.md` §4.2、§5、§7；
  - `05-tasks.md` T-03（WAL 配置）、T-06（SettleService 测试先行）、T-15（读不落库）、T-16（三重防护）；
  - `components/registry.md` 待登记 R-007；
  - **不修改 ADR-001**：本 ADR 是其在"写并发前提变化"下的项目级补充，二者并存，迁移触发条件以本 ADR 为准；
