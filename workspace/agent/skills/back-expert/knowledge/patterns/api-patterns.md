# API / 后端模式库

设计服务与接口时的"先查库再动手"资产：每类接口/场景给出**核心模式**（照着做）与**常见坑**（S4 走查逐条核对）。
使用时机：S0 spec 判断接口类型 → S1/S2 设计引用模式 → S4 走查核对常见坑。发现新模式/新坑按积累规则追加。

## 1. CRUD 资源接口

**适用**：绝大多数管理后台、业务数据的增删改查。

**核心模式**
- 资源导向路径：`/api/v1/{resources}`，复数名词；动作用 HTTP 方法表达，不用动词路径
- 读接口必分页（conventions.pagination），支持排序与筛选
- 写操作明确幂等策略：PUT 天然幂等；POST 创建类用幂等键（客户端生成请求唯一码）
- 软删除优先（is_deleted + 过滤），物理删除需二次确认与审计日志
- 乐观锁：并发更新的资源带 version 字段，更新时校验

**常见坑（S4 核对）**
- [ ] 列表接口未分页，全量返回
- [ ] 循环内逐条查库（N+1）：应批量查询或 JOIN
- [ ] 删除未检查关联引用，产生孤儿数据
- [ ] 更新接口未校验资源归属（越权：拿别人 ID 直接改）
- [ ] 筛选参数拼 SQL 而非参数化查询（注入风险）

## 2. 认证鉴权

**适用**：登录、注册、令牌签发与校验、权限控制。

**核心模式**
- 无状态令牌：JWT（短期 access）+ 刷新令牌（长期，可吊销）；密钥只放环境变量
- 密码存储：bcrypt/argon2 加盐哈希，永不存明文、永不回显
- 权限校验放中间件 + 资源归属校验放服务层，双层防御
- 登录失败限速 + 错误信息不区分"账号不存在/密码错误"（防枚举）

**常见坑（S4 核对）**
- [ ] 令牌无过期时间或过期时间过长
- [ ] 仅靠前端隐藏按钮做权限控制，后端未校验
- [ ] 接口只验登录态不验资源归属（横向越权）
- [ ] 错误响应泄露"用户不存在"（账号枚举）
- [ ] 密钥/盐值硬编码进仓库

## 3. 幂等写操作（支付/下单/扣减）

**适用**：涉及钱、库存、状态机推进等不可重复执行的写操作。

**核心模式**
- 幂等键：客户端生成唯一请求码，服务端记录并去重（唯一索引兜底）
- 状态机推进：状态变更只在合法迁移上执行，非法迁移返回冲突错误码
- 扣减类操作用条件更新：`UPDATE ... SET stock = stock - 1 WHERE stock >= 1`，靠数据库原子性防超卖
- 失败可重试：明确哪些错误可重试（超时/网络），哪些不可（业务校验失败）

**常见坑（S4 核对）**
- [ ] 重复提交未去重：同一订单被创建两次
- [ ] 状态回退未拦截（已支付订单被重新"待支付"）
- [ ] 先查后改非原子（并发下超卖/超扣）
- [ ] 超时后重试未带幂等键，产生双份效果

## 4. 异步任务与消息

**适用**：耗时操作、削峰、跨服务通知（发邮件/生成报表/同步数据）。

**核心模式**
- 接口先返回"已受理"，任务入队后台执行；提供查询任务状态接口
- 消费端必须幂等（消息至少一次投递是常态）
- 死信队列 + 重试退避：失败消息不无限重试，超限进死信人工处理
- 长事务拆分：跨服务一致性用 Saga（每步带补偿），不用分布式大事务

**常见坑（S4 核对）**
- [ ] 消费端未幂等，重投导致重复执行
- [ ] 无死信处理，毒消息阻塞整个队列
- [ ] 任务失败无告警，静默丢失
- [ ] 同步接口里做重活（超过 300ms 的操作未异步化）

## 5. 缓存

**适用**：读多写少的热点数据、降低数据库压力。

**核心模式**
- Cache-Aside：读时先缓存后库，写时先改库再删缓存（而非更新缓存）
- 过期时间 + 随机抖动：防雪崩；热点 key 防击穿（互斥重建或空值占位）
- 缓存只放可重建数据，不缓存唯一事实

**常见坑（S4 核对）**
- [ ] 写后未失效缓存，读到旧数据
- [ ] 无过期时间，脏数据永久驻留
- [ ] 大 key（>10KB 序列化对象）拖慢网络
- [ ] 缓存与库数据不一致时无兜底（如对账/强制刷新入口）

## 6. 对外第三方集成

**适用**：调用支付、短信、地图、LLM 等外部服务。

**核心模式**
- 防腐层：第三方客户端封装为内部接口，领域层只见内部抽象
- 超时必设（连接/读取分开设）、重试带退避、熔断防雪崩
- 关键回调（如支付通知）：验签 → 幂等处理 → 快速应答

**常见坑（S4 核对）**
- [ ] 无超时设置，第三方慢拖死自身线程池
- [ ] 回调接口不验签（伪造通知）
- [ ] 第三方返回直接透传给前端（泄露内部结构）
- [ ] 无限重试拖垮下游

## 7. 邮箱验证码（注册/敏感操作核验）

**适用**：邮箱注册、密码重置、敏感操作二次确认。

**核心模式**（来源：20260901 调研笔记，多来源交叉印证）
- 6 位数字验证码，**SHA-256 哈希后**存 Redis，`SET EX 300`（5 分钟）；接口永不返回验证码明文；服务重启即全部失效，可接受（重发即可）
- Key 设计：`{业务}:captcha:{场景}:{邮箱}`，场景隔离（注册/重置各自独立）
- 防刷三层：① 60s 发送冷却（TTL Key）；② 每日发送上限（防耗尽邮件额度）；③ 验证尝试限次（如 5 次/10 分钟），超限锁 10 分钟，错误码区分“错误”与“锁定”
- **验证成功即删除**验证码（防重放）；验证失败保留并递增尝试计数（用 INCR + EXPIRE，首次设置时补 TTL）
- 发信失败不落验证码：先发邮件成功再写 Redis，避免“有码但用户收不到”

**常见坑（S4 核对）**
- [ ] 验证码明文存 Redis 或出现在日志/响应中
- [ ] 验证码 Key 无 TTL（内存泄漏）或与其他业务 Key 撞名
- [ ] 验证通过后未删除，同一码可反复使用（重放）
- [ ] 无发送冷却/上限，被刷爆邮件额度或短信费用
- [ ] 验证码错误次数不区分“已锁定”与“码错误”，或锁定后仍允许尝试验证（时序漏洞：应先查锁再验码）
- [ ] 注册接口泄露“邮箱已存在”与否的差异（账号枚举）
- [ ] 先写 Redis 再发邮件，发信失败后留下死码

## 8. 实时房间同步（WebSocket 长连接）

**适用**：随机配对聊天、双人/多人协作、房间制对战、协同编辑、实时状态推送。
（本组兑现 20260902 调研笔记预留的「随机配对聊天模式回写第 8 组」：配对会话与协作房间是同一模式家族——长连接 + 房间/会话表 + 心跳判活 + 限流 + 断连补偿。）

**核心模式**
- 连接鉴权：token 走 **query 参数**（浏览器 WS API 不支持自定义 header）；校验失败用**自定义关闭码**（如 4401）而非通用 1008，便于客户端区分“未登录”与“协议错误”
- 房间表：单实例用内存 `Map<roomKey, Set<conn>>`，**成员上限显式声明**；多实例部署必须迁 Redis Pub/Sub（设计时就标注该限制）
- 心跳判活：服务端主动 ping（25s），90s 无任何入站帧即关闭并**同步清理房间表**；不能只依赖 `onclose`
- 分层限流：单帧长度上限（2000 字节）+ 每分钟条数上限（20 条）；超限回 `error` 帧但**不断连**；低优先级帧（typing 等）可静默丢弃
- 帧协议 `{ type, payload, seq, ts }`；seq 房内单调递增，客户端记录已处理最大 seq 做去重
- **上行不承载写操作**：改变状态的操作一律走 HTTP（需要事务/幂等键/乐观锁），WS 只做通知与全量查询；WS 帧无可靠重试语义，无法承载写幂等
- 断连补偿：重连成功后服务端**必须先推全量快照**再恢复增量；客户端在收到全量前**丢弃一切增量帧**
- 客户端重连：`delay = min(base * 2^attempt, 30s) + random(0, 500)`，**随机抖动必需**（防重连风暴）
- 广播时机：在事务**提交后**执行；广播失败只记日志**不回滚业务**（事实来源永远是数据库，WS 只是通知通道）
- 重复连接：同一用户新连接踢旧连接（旧连接收 `kicked` 后关闭），避免多标签页状态混乱
- 反向代理：必须显式透传 `Upgrade` / `Connection` 头，并放大 `proxy_read_timeout`（≥300s）

**常见坑（S4 核对）**
- [ ] 连接异常关闭时未清理房间表 → 房间泄漏，内存持续增长
- [ ] 只靠 `onclose` 做清理：网络静默断开（切后台/锁屏/换网）可能不触发，必须有心跳超时兜底
- [ ] 重连后直接处理增量帧 → 用断连期间的过期增量污染当前状态
- [ ] 重连退避无随机抖动 → 服务端重启后全部客户端同一瞬间重连（重连风暴）
- [ ] 用 WS 承载写操作 → 无法保证幂等与事务，客户端重试产生双倍效果
- [ ] 广播放在事务内 → 事务回滚了但帧已发出，客户端看到不存在的数据
- [ ] NestJS `@nestjs/platform-ws` **不会自动绑定原始消息监听器**，必须在 `handleConnection` 内手动 `client.on('message', ...)`，否则自定义帧全部收不到
- [ ] 限速直接断连 → 体验灾难，应回 `error` 帧保持连接
- [ ] 帧长上限只在前端校验 → 后端必须独立校验
- [ ] 单实例内存房间表未标注多实例限制 → 扩容后广播静默丢失
- [ ] Nginx 未透传 Upgrade 头 → 握手失败但错误信息不明确，难排查
- [ ] 移动端切后台（小程序/小游戏约 5s、浏览器不定）即断连当作异常处理 → 断连是**常态**，必须设计为自动恢复路径

## 9. 时间驱动的服务端权威数值（惰性结算）

**适用**：养成衰减（饥饿/心情）、体力与行动力恢复、CD 冷却、会员到期、积分过期、放置类离线收益。

**核心模式**
- **不存当前值**，只存「参考值 + 上次结算时刻 + 速率」；当前值用**闭式公式** O(1) 算出（离线 30 天与 30 秒成本相同）
- 时间源只用**服务端 UTC**；接口**不接收任何客户端时间入参**
- 时钟回拨保护：`dt = max(0, now - last_settled_at)`，dt=0 时记 WARN；宁可不变化也**绝不允许数值反向**
- `clamp` 上下限：衰减到下限即止（不产生负值），恢复到上限即止
- **读路径结算不落库**（避免读变写）；写路径在**同一事务**内结算 + 推进 `last_settled_at` + 业务变更
- 累积类设**每日上限**，跨 UTC 日界归零（`day_key` 字段或 Redis `incrDaily`）
- 结算逻辑抽为**纯函数领域服务**（无 IO、无框架依赖）→ 可 100% 单测覆盖，且能在衰减/恢复两类场景间复用
- 客户端可用**同一公式**做显示插值（数值条平滑），但写操作返回后必须以服务端结果**整体覆盖**本地，本地计算值**绝不回传**
- 速率/上限/CD 全部外置配置（环境变量或配置表），禁止硬编码

**常见坑（S4 核对）**
- [ ] 用客户端时间算离线时长 → 改系统时间即可作弊
- [ ] 按天/按小时**循环累加**结算 → 离线 30 天时接口变慢；必须用闭式公式
- [ ] 衰减无下限 → 数值变负，UI 异常或后续计算溢出
- [ ] 未处理时钟回拨（NTP 校正）→ 数值突然倒涨
- [ ] 读接口也写库 → 读多写少场景无谓放大写压力（SQLite 尤其致命）
- [ ] 参考值与 `last_settled_at` 不在同一事务更新 → 两者错位导致重复衰减或漏衰减
- [ ] 浮点参考值在 API 边界反复取整后回写 → 累积取整漂移（应只在边界取整，库内存 Float）
- [ ] 每日上限用**本地时区**判定 → 跨时区用户刷新时点不一致（统一 UTC 日界）
- [ ] CD 只在前端计时 → 绕过前端即可无 CD 刷；服务端必须独立存 CD（Redis TTL）
- [ ] 结算速率硬编码在代码里 → 调数值要发版
- [ ] 断线 2s 内快速重连时重复做时间校验 → 时间差过小易误判为作弊，应设最小校验间隔
- [ ] **时间戳字段为空/不可解析时未做防护** → `Date.parse('')` 得 NaN，而先转数字再相减会得 0（= 1970-01-01），算出几十年的时间差把数值瞬间清零。必须在求时间差前显式判定“任一端不可解析 → dt=0”，方向上宁可不变化也不能误伤存量数据（pet-game 实现期真实命中：schema 的 `last_settled_at String @default("")` 遇上空值就会触发）

## 积累原则

- 新模式追加为新编号小节；既有模式补充"常见坑"直接在清单追加 `- [ ]` 项。
- 每个模式注明适用场景；发现某模式不再适用时标注"已废弃 + 原因"，不删除。
