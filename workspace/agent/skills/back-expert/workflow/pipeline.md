# 流水线定义（S0 ~ S5）· v1.0

后端服务开发制作的六阶段流水线。每个阶段定义：输入 → 工作 → 产出 → 退出卡点。
卡点的具体验收项见 `gates.md`。**卡点未全部通过，禁止进入下一阶段。**
所有阶段共同的上位依据是 `constitution.md`（项目宪法），冲突时按宪法"裁决顺序"处理。

```
宪法 constitution.md（贯穿全程）
      ↓
S0 需求→spec →G1→ S1 领域建模与架构 →G2→ S2 数据与契约设计 →G2b→ S3 任务拆解+开发 →G3→ S4 测试与联调走查 →G4→ S5 上线与复盘 →G5(关闭)
```

> 阶段可跳过但必须记录：例如已有明确接口契约时从 S3 进入，但需在任务记录中写明"跳过 S0~S2 的原因及契约由谁提供"。

---

## S0 需求 → Spec（规格化）

| 项 | 内容 |
|---|---|
| 输入 | 用户/产品方的一句话或文档需求 |
| 工作 | **先调研**（宪法 P11）：上网检索同类系统方案、领域建模参考与已知坑，调研发现落盘 `knowledge/research/YYYYMMDD-主题.md`；随后按 `knowledge/prompts/spec-from-requirement.md` 把原始需求规格化为 spec：用户故事、可测验收标准、非目标、边界异常、开放问题；对照 `patterns/api-patterns.md` 判断服务/接口类型并引用既有模式与调研要点 |
| 产出 | 调研笔记 + `output/<项目名>/01-spec.md`（spec 是后续所有阶段的可执行契约） |
| 退出卡点 | G1 |
| AI 参与方式 | WebSearch/WebFetch 检索同类系统与选型证据、结构化整理、生成疑问清单、对照 `cases/` 与 `patterns/` 找相似经验 |
| 宪法依据 | P3 规格先行、P11 调研先行 |

## S1 领域建模与架构设计

| 项 | 内容 |
|---|---|
| 输入 | 通过 G1 的 spec |
| 工作 | **补充调研**：检索该领域成熟架构方案与中间件选型证据，记入调研笔记；识别领域边界（核心实体/聚合/限界上下文）；确定架构模式（单体分层 / DDD 四层 / 微服务）与技术栈；画架构图（组件、数据流、外部依赖）；**先查 `patterns/api-patterns.md` 该领域的成熟模式**，站在模式上做设计而非从零发明 |
| 产出 | `02-架构说明.md`（领域模型 + 架构决策 + 技术选型 + 引用了哪些模式与调研案例） |
| 退出卡点 | G2（架构评审） |
| AI 参与方式 | 用提示词模板生成多版架构方案供挑选；选型查 `tools/toolchain.json` 的 `framework` 类；架构图可用 Mermaid/Excalidraw 文本生成 |

## S2 数据与契约设计

| 项 | 内容 |
|---|---|
| 输入 | 通过 G2 的架构方案 |
| 工作 | **补充调研**：检索同类数据模型与接口设计惯例（分页/幂等/错误码惯例），记入调研笔记；设计数据库表结构（字段、索引、关系、迁移策略）；按 `conventions/response-and-errors.json` 定义接口契约（OpenAPI/Markdown：端点、方法、入参、出参、错误码、幂等键、鉴权方式）；**契约冻结后即为前后端/服务间的法律合同**（API-First），变更必须走变更记录 |
| 产出 | `03-契约定义.md`（数据库 schema + 接口契约清单 + 错误码映射） |
| 退出卡点 | G2b（数据与契约评审） |
| AI 参与方式 | 按模板生成 OpenAPI 片段与建表 SQL；对照 conventions 自动检查响应格式一致性 |

## S3 任务拆解 + 后端开发

| 项 | 内容 |
|---|---|
| 输入 | 通过 G2b 的契约 + spec |
| 工作 | ① 先按 `knowledge/prompts/tasks-breakdown.md` 把 spec/契约拆成小任务（每任务自带完成定义 = 测试命令或验收脚本，MoSCoW 优先级）→ `05-tasks.md`；② 逐任务实现：数据库迁移 → 领域/业务逻辑 → 接口层，推荐测试先行（先写失败测试再实现）；③ 实现中持续做**偏移检测**：发现 spec/契约未覆盖或矛盾的需求，按宪法 P10 停下更新 spec 与契约，记录到 tasks.md 偏移日志，禁止静默实现 |
| 产出 | `output/<项目名>/` 下可运行服务代码 + `05-tasks.md`（含偏移日志） |
| 退出卡点 | G3（开发自测：单测 + lint + 本地可运行） |
| AI 参与方式 | Vibe Coding：AI 生成 + 人工审核；框架与工具查 `toolchain.json` 的 `dev` 类 |
| 宪法依据 | P4 小步交付、P5 验证内建、P8 幂等与一致性、P10 偏移即停 |

## S4 测试与联调走查

| 项 | 内容 |
|---|---|
| 输入 | 通过 G3 的服务代码 + 契约 + spec |
| 工作 | 按 `knowledge/checklists/backend-qa.md` 逐项走查（安全/性能/一致性/可观测）；**对照 `patterns/api-patterns.md` 该接口类型的"常见坑"逐条核对**；集成测试与边界情况（空数据/非法入参/并发重复提交/依赖服务故障）验证；与前端或上下游按契约联调；修复后回归 |
| 产出 | `04-走查报告.md`（检查项勾选结果 + 测试证据 + 模式核对 + 修复记录） |
| 退出卡点 | G4（测试走查 + 验收） |
| AI 参与方式 | 自动化测试执行、压测脚本生成、日志/报错扫描、清单逐项自检 |

## S5 上线与复盘（含反思环）

| 项 | 内容 |
|---|---|
| 输入 | 通过 G4 的最终版本 |
| 工作 | 构建、部署、线上冒烟验证（核心路径 + 回滚预案）；按 `knowledge/cases/TEMPLATE.md` 复盘，必须回答三个反思问题：① spec 中哪条验收标准被证明最有效/最没用？② 偏移日志里的需求为何当初没进 spec？③ 本项目出现了哪个可复用模式或反模式？ |
| 产出 | 部署记录/接口地址 + `knowledge/cases/YYYYMMDD-项目名.md` |
| 退出卡点 | G5（复盘回写完成） |
| AI 参与方式 | 部署脚本执行、冒烟测试、按积累规则回写积累池 |
| 宪法依据 | P9 积累义务 |
