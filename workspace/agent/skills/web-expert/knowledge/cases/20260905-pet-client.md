## 三个反思问题

### ① spec 中哪条验收标准被证明最有效/最没用？

- **最有效**：后端 spec 验收 29（断线重连先全量后增量 + 退避可观察）与 25（1 秒内实时同步）——它迫使 SocketClient 把状态机（synced 前丢增量/seq 去重/退避公式）做成显式实现而非"能连上就行"，走查时才能用"228ms + 控制台退避序列"这样可测的证据验收。
- **最没用**：验收 30（WS 限长/限速）——客户端上行只有心跳/typing 且 2s 节流，天然远低于限值，前端只能"不触雷"而无法有效验证服务端行为；这类验收实际归属后端侧自测。

### ② 偏移日志里的需求为何当初没进 spec？

- 引擎不可用问题：后端 ADR-003 在设计期无法知道执行端（另一台 AI 工作机）有没有 Cocos 编辑器——**环境约束类信息天然不在需求里**，只能在实现期暴露。教训：跨仓移交任务时应附"执行环境核对单"（工具链是否可用），把环境偏移前移。
- 双标签页会话覆盖：spec 写了"双开标签页可演示双人"，但没规定会话存储语义——直到走查才发现 localStorage 共享会顶号。教训：**涉及多实例/多标签页的验收标准要写清隔离边界**（已回写 visual-qa 第 8 组）。

### ③ 出现了哪个可复用模式或反模式？

- **可复用模式（已登记）**：MockContractServer——"后端契约冻结但未实现时，前端内置逐条对齐契约的浏览器内 Mock（共享库 + 房间广播），用 URL 参数一键切换真实后端"。适用于一切 API-First 前后端并行项目。
- **反模式（已回写清单）**：跨标签页共享 localStorage 的整库"加载一次+写回"——多标签页场景下必然互相覆盖；正确姿势是操作前重读 + 会话用 sessionStorage。
- **反模式**：渲染挂点凭感觉放置（W8 帽子遮眼）——跨仓渲染规格（挂点表）必须逐字核对，配合像素探针走查尽早发现。
